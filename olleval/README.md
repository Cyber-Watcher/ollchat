# olleval — прогон моделей Ollama по наборам задач

Программа гоняет модели одного сервера Ollama по наборам задач и записывает, как
каждая справилась: балл, скорость, цену ответа в токенах, сбои и странности.
Сама она ничего не оценивает на глаз. Её работа — довести каждую задачу до каждой
модели **одинаковым образом**, сохранить сырьё целиком и прогнать машинную
проверку там, где она возможна. Открытые ответы помечаются «нужен разбор
человеком»: балл по ним ставится потом, по чек-листу.

Родня — `olldiagtools`: тот меряет видеопамять нагрузочными загрузками, этот меряет
умения. Оба запускаются на самом сервере.

## Сборка и выкладка

```bash
export PATH=$HOME/sdk/go1.26.5/bin:$PATH
go build -o olleval/olleval ./olleval
go test ./olleval/
scp olleval/olleval сервер:~/bin/
```

Разработка идёт на рабочей машине, на сервер уезжает только собранный бинарь
и файлы задач.

## Команды

```bash
olleval guard                              # свободна ли видеокарта (код 1 — занята)
olleval models                             # модели сервера и кто участвует
olleval run --suite go --until 06:45       # прогон до 06:45 по Москве
olleval report --night 2026-08-22          # сводка по прогону
```

Полезные флаги `run`: `--repeats 3`, `--num-ctx 32768`, `--models a,b`,
`--exclude ...`, `--for 6h`, `--night имя`, `--note "первый прогон"`.

**Запускать только в tmux.** Ночь длинная, ssh рвётся:

```bash
tmux new-session -d -s olleval-2026-08-22 \
  'olleval run --suite devops --until 06:45 2>&1 | tee -a ~/ollevals/runs/2026-08-22/run.log'
```

## Настройки

Расписание ночи и правила проверки занятости лежат в `~/ollevals/olleval.toml`
(создаётся командой `olleval config --init`), а не в коде и не в скриптах: эти числа
правятся чаще всего, и держать их в трёх местах значит однажды развести их между собой.

```toml
[schedule]
timezone = "Europe/Moscow"   # пояс задаётся явно: пояс сервера могут сменить
wait     = "6h"              # сколько ждать освобождения карты
gap      = "15m"             # за сколько до конца окна перестать раздавать задачи

# Расписание на каждый день недели — механизм один и тот же для всех семи.
# Промежутков может быть несколько; "22:00-02:00" относится к дню, где начался;
# пустой список означает «в этот день прогонов нет». Рядом со временем ставится
# порог загрузки карты: "gpu<=10" — десять процентов и ниже считаем простоем.
[schedule.days]
monday    = ["00:00-07:00 gpu<=10"]
tuesday   = ["00:00-07:00 gpu<=10", "13:00-14:00 gpu<=0"]  # ночь и обеденный перерыв
wednesday = ["00:00-07:00 gpu<=10"]
thursday  = ["00:00-07:00 gpu<=10"]
friday    = []                                   # по пятницам не гоняем
saturday  = ["00:00-23:59 gpu<=5"]               # целые сутки
sunday    = ["00:00-23:59 gpu<=5"]

[guard]
free_checks = 3; poll = "1m"; journal_window = "15m"
busy_util_percent = 10; util_samples = 5; util_sample_gap = "1s"
check_gpu = true; check_ps = true; check_journal = true; check_sessions = true

[run]
suites = "all"; repeats = 3; num_ctx = 32768; retries = 2; timeout = "20m"; keep_alive = "1h"
exclude = ["qwen38-szkm:latest"]

[health]
check_spill = true; spill_action = "skip"; restart_after_errors = 2; restart_wait = "5m"
```

Флаги перекрывают конфиг, конфиг перекрывает умолчания. Скрипт прогона берёт оттуда же
(`olleval config --get guard.poll`), а `olleval timers` печатает и расписание недели,
и юниты systemd — так оно остаётся в одном месте. День, не указанный в файле, берётся
из умолчаний: правка одного дня не должна молча отменять прогоны в остальные, а чтобы
день выключить, ему пишут пустой список.

Старый вид настроек (`start`/`until`/`restore` плюс `[schedule.weekend]`) продолжает
работать: при загрузке он разворачивается в расписание по дням.

**Когда правка настроек вступает в силу.** Файл читается при запуске каждой команды,
поэтому тик подхватывает правку не позже чем через четверть часа. Идущий прогон —
особый случай: он **перечитывает расписание перед каждой задачей**. Убрали окно из
настроек — прогон останавливается на ближайшей границе задачи, выгружает модели и отдаёт
сервер (тик возврата откроет его в течение 15 минут); продлили окно — работает дальше
и пишет в журнал новый предел. Остальные настройки — повторы, окно контекста, наборы —
берутся один раз при старте: смена на середине сделала бы половину ночи несравнимой
с другой половиной. Сломанный файл идущую ночь не роняет: она доработает по тому
расписанию, с которым начиналась.

## Расписание и обвязка

Таймеры systemd тикают **раз в четверть часа**, а решают скрипты — так расписание
живёт в конфиге, а не в юнитах:

- `olleval-night.sh` — вне окна выходит сразу, при живом прогоне тоже. Внутри окна
  ждёт свободной карты, закрывает Ollama на localhost, гонит наборы, пишет `gpu.log`,
  выгружает модели и возвращает сервер по `trap` при любом выходе. Тик заодно **поднимает
  прогон обратно**, если тот умер посреди окна: сделанные попытки не переделываются.
- `olleval-restore.sh` — открывает сервер, как только его больше незачем держать закрытым:
  окно кончилось **или** прогон умер (отметка о нём протухла). Без второго условия
  стенд простоял бы закрытым до конца суток субботы.

Команды: `olleval window` (идёт ли окно, `--end`, `--deadline`, `--gpu`), `olleval running`
(жив ли прогон), `olleval pending` (сколько попыток ночи не сделано), `olleval timers`
(юниты по конфигу).

**Сервер не закрывается, когда делать нечего.** Ночь доделывает наборы к утру, а окно
выходного дня длится сутки — тик продолжал бы приходить каждые четверть часа. Поэтому
скрипт спрашивает `olleval pending` **до** изоляции и при нуле выходит, не трогая службу.
Замерено 22.08.2026: без этой проверки за одно субботнее окно случилось 26 заходов
«закрыть — обнаружить ноль работы — открыть», каждый с двумя перезапусками Ollama.

**`KillMode=process` в `olleval-night.service` обязателен.** Служба лишь запускает сессию
tmux: клиент `tmux new-session -d` завершается сразу, отдав работу серверу tmux. При
умолчании `KillMode=control-group` systemd после выхода `ExecStart` гасит весь cgroup
службы — вместе с сервером tmux и прогоном внутри. Со стороны это выглядит как «таймер
тикает, а ночь не начинается»: в журнале `Starting… Deactivated successfully` той же
секундой, сессии tmux нет, каталог ночи не создан, `logs/nights.log` пуст. Замерено
на стенде 22.08.2026.

## Здоровье прогона

Две беды тихие, и обе обесценивают ночь:

- **Выезд модели в оперативную память.** Признак прямой: в `/api/ps` размер модели
  больше того, что лежит на карте. Замерено на стенде — 1.64 ГиБ за пределами карты
  уронили генерацию с 73.9 до 5.4 ток/с, в 13.7 раза. Такая модель пропускается
  (`health.spill_action = "skip"`) или лечится перезапуском Ollama.
- **Зависание.** Попытки одна за другой упираются в таймаут. После
  `health.restart_after_errors` срывов подряд Ollama перезапускается, и прогон
  продолжается с того места, где остановился.

## Правило номер один

Прогон не начинается, пока видеокарта **считает**: на стенде работают люди, и замер
не имеет права отобрать у них карту посреди ответа. Решает загрузка, а не занятая
память — модель остаётся в видеопамяти часами после последнего чужого запроса,
и по занятости стенд выглядел бы вечно занятым, а ночь не начиналась бы вовсе.

`guard` смотрит:

- **загрузку карты** (`nvidia-smi --query-gpu`) — серией выборок (`guard.util_samples`,
  5 штук с шагом `guard.util_sample_gap`), в расчёт идёт наибольшая: один снимок
  попадает в паузу между двумя токенами чужого ответа и врёт про простой. Загрузка выше
  порога промежутка — прогон ждёт;
- свежие запросы в журнале Ollama (`guard.journal_window`, 15 минут): человек мог
  отправить вопрос только что, и карта считает не в момент проверки, а через секунду;
- **состояние службы Ollama**: остановленная служба означает «карту забрали», а не
  «всё свободно». Её гасят руками, когда видеопамять нужна под обучение модели.
  Но её же часто забывают поднять обратно — поэтому, если карта свободна **непрерывно**
  `guard.idle_before_start` (20 минут), прогон поднимает службу сам и начинает работу.
  Считается только наблюдённый простой: занятость и перерыв в наблюдении сбрасывают счёт;
- процессы на карте (`--query-compute-apps`), загруженные модели (`/api/ps`) и занятую
  видеопамять — **к сведению**, в журнал. Забытая в памяти модель прогон не запрещает:
  перед первым замером она снимается с карты сама (`keep_alive: "0s"`).

Чужой сеанс ssh только отмечается — забытое окно `mc` это не работа, и запрещать
по нему ночь значит не запускать её никогда.

**Порог загрузки** пишется рядом с промежутком расписания: `"00:00-07:00 gpu<=10"` —
ночью терпимость одна, `"09:00-14:00 gpu<=0"` — днём другая. Допустимо от 0 (строго ноль)
до 20 процентов; выше — ошибка запуска: такая загрузка это уже чужая работа. Промежуток
без порога берёт общий `guard.busy_util_percent` (10%). Действующий порог печатает
`olleval window --gpu`.

Если загрузку измерить не удалось (нет `nvidia-smi`, непонятный ответ), включается
прежнее строгое правило: старт запрещают и процессы на карте, и занятая память
(`guard.busy_vram_mib`, 1 ГиБ), и загруженная модель. Слепой старт хуже пропущенной ночи.
Проверка службы — `guard.check_service` и `guard.service`.

Скрипт `olleval-isolate.sh on` отдельно отказывается поднимать погашенную службу: правило
номер один защищает автоматический прогон, а этот отказ — ещё и ручной запуск. Службу
поднимает только `olleval guard --start-service` (так её зовёт тик) — и только после
подтверждённого простоя карты.

## Журналы

| Файл | Что внутри |
|---|---|
| `logs/guard.log` | строка на каждую проверку: занято или свободно, видеопамять и загрузка с действующим порогом, состояние службы, накопленный простой, причины |
| `logs/nights.log` | решения тика: вне окна, прогон уже идёт, карта занята, начинаю, закончил |
| `logs/restore.log` | когда и почему сервер возвращали в общий доступ |
| `runs/<ночь>/run.log` | подробный журнал самой ночи |

Пустые тики в журналы не пишутся: служба возврата молчит, пока сервер и так открыт,
иначе настоящие события тонули бы в сотне строк «уже открыт» за сутки.

Первые два отвечают на утренний вопрос «почему прогон не начался» — без них тик
не оставляет следов, а причина занятости живёт секунды.

## Раскладка данных

```
~/ollevals/
├── suites/     наборы задач (*.toml)
├── fixtures/   входные файлы задач
└── runs/2026-08-22/
    ├── run.json      паспорт ночи: версия Ollama, модели с digest, окно, повторы
    ├── index.jsonl   строка на попытку — вход для сводок
    └── qwen3.5_122b/go-u1-median/r1/
        ├── request.json  что ушло в /api/chat
        ├── stream.jsonl  сырой поток ответа
        ├── answer.md     текст ответа
        ├── thinking.md   рассуждения отдельно
        ├── metrics.json  время, токены, скорость, ошибки, балл
        ├── verify.json   что показала проверка
        └── work/         файлы, написанные моделью, и логи сборки
```

Готовность попытки определяется наличием `metrics.json`. Поэтому прогон, прерванный
на середине, **докатывается** следующей ночью с того же места, а не начинается заново.

## Наборы задач

Задача описывается в TOML: постановка, приложенные файлы, способ проверки, эталон.
Устройство — в `suite.example.toml`. Уровни задач: У1 мелочь, У2 правка в чужом
коде, У3 с нуля, У4 разбор. Уровень определяет вес задачи в балле области.

Виды проверки:

- `container` — код из ответа кладётся в рабочий каталог, шаги (сборка, тесты)
  выполняются в контейнере **без сети**, с лимитами памяти и времени. Балл
  складывается из пройденных шагов; первый провал останавливает остальные —
  не собралось, значит тестировать нечего.
- `checklist` — ответ сверяется с пунктами. Совпадение ищется с начала слова:
  пункт «назвал `num_ctx`» иначе засчитывался бы за выдуманную переменную
  `OLLAMA_NUM_CTX`, то есть ровно за ошибку, которую он должен ловить.
  Пункт с отрицательным баллом — штраф за уверенное враньё. Балл всегда
  предварительный, попытка помечается «нужен разбор человеком».

  **Пункты пишутся основами, а не словоформами.** Проверено на первом же прогоне:
  пункт «контекстное окно» не совпал с ответом «размер контекстного окна» —
  русский язык склоняется, и модель получила 0.5 вместо 1.0 ни за что.
  Правильно: `["контекстн", "окн"]`.
- `none` — только сохранить ответ.

**Рабочие наборы и фикстуры в репозиторий не уезжают** (`/olleval/suites/`,
`/olleval/fixtures/` в `.gitignore`). Задача с эталоном, попавшая в открытый
доступ, попадёт и в обучающие выборки: через год модель «решит» её по памяти.
Публичные наборы вроде HumanEval умерли ровно так.

## Что меряется на каждой попытке

Время до первого куска ответа (у первой задачи блока в него входит загрузка
модели с диска — она пишется отдельным полем `load_seconds`), общее время,
скорость по данным сервера, токены
промпта и ответа, объём рассуждений отдельно от ответа, число вызовов
инструментов, смешение алфавитов внутри слова (болезнь `nemotron-3.5-lightning`),
отказ отвечать, сорванные обмены и повторы.

Повтор обмена делается только тогда, когда сорвалось **до первого куска ответа**, —
то же правило, по которому повторяет обмен сам ollchat.
