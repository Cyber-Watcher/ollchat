# ollchat

[![CI](https://github.com/Cyber-Watcher/ollchat/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/Cyber-Watcher/ollchat/actions/workflows/ci.yml)
[![Release](https://github.com/Cyber-Watcher/ollchat/actions/workflows/release.yml/badge.svg)](https://github.com/Cyber-Watcher/ollchat/actions/workflows/release.yml)
[![Go Reference](https://pkg.go.dev/badge/github.com/Cyber-Watcher/ollchat.svg)](https://pkg.go.dev/github.com/Cyber-Watcher/ollchat)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE.txt)

TUI-клиент и агент для серверов Ollama на Go. Один бинарь плюс файл настроек.
Интерфейс построен по образцу Claude Code CLI: лента диалога, подтверждение опасных действий,
индикатор заполнения контекстного окна, слэш-команды.

- Чат с моделями Ollama в потоковом режиме, с разметкой и показом рассуждений.
- Несколько серверов и моделей, переключение на лету.
- Агентный режим: модель работает инструментами в песочнице, опасное — через подтверждение.
- Чтение PDF и EPUB **своим кодом**: ни `pdftotext`, ни `ebook-convert`, ни Python.
- Показ модели картинок из документов — там, где таблица цен свёрстана картинкой.
- Поиск по личной библиотеке книг: по словам и по смыслу, с ссылкой на книгу и страницу.

# Установка

Если в репозитории есть готовые сборки на странице Releases — скачайте файл, положите
в каталог из `PATH` и запускайте. Иначе соберите из исходников: это одна команда.

## Сборка из исходников

Нужен Go 1.26.5 или новее — версия указана в `go.mod`, более старый тулчейн проект не соберёт.
Ставить системный Go не обязательно, достаточно отдельного:

```bash
export PATH=$HOME/sdk/go1.26.5/bin:$PATH
go build -o ollchat ./cmd/ollchat
go test ./... && go vet ./... && gofmt -l .
```

# Первый запуск

```bash
./ollchat --init-config      # создать ~/.config/ollchat/config.toml с комментариями
```

В созданном файле нужно поправить одно — адрес сервера и модель:

```toml
[[servers]]
name  = "lab"
url   = "http://ollama.example:11434"
model = "qwen3.5:122b"
```

Дальше просто:

```bash
./ollchat
```

Первая команда в приложении — `/help`: там та же справка, что и здесь, только короче.

# Флаги командной строки

| Флаг | Что делает |
|---|---|
| `-c <путь>` | другой файл настроек |
| `--init-config` | создать файл настроек и выйти |
| `--server <имя>` | сервер из конфига, важнее `general.default_server` |
| `--model <имя>` | модель, важнее настройки сервера |
| `--cwd <путь>` | рабочий каталог — корень песочницы |
| `--mode <safe\|auto-edit\|noask>` | режим подтверждений |
| `--version` | версия сборки: `v0.1.5 (a6eda30, 2026-09-03, go1.26.5, linux/amd64)` у выпуска, `dev (…)` у сборки из исходников |
| `--kb-index <имя> <путь>…` | собрать коллекцию книг без интерфейса |
| `--kb-sync <имя>` | сверить коллекцию с диском |
| `--kb-embed <имя>` | посчитать векторы(смыслы) (эмбеддинги) |
| `--kb-dry-run` | с `--kb-embed`: только оценить работу |
| `--kb-merge <имя>` | уплотнить коллекцию: дважды переспросит с ответом `ДА` (отклоняется, если собран граф; обход — `--kb-merge-force`) |
| `--kb-yes` | с `--kb-merge`: не спрашивать подтверждений, для скриптов |
| `--kb-list` | показать коллекции и выйти |
| `--graph-build <имя>` | собрать граф понятий по коллекции (см. ниже) |
| `--graph-folder <часть пути>` | с `--graph-build`: только книги, чей путь содержит эту строку — каталог или имя файла (одна книга) |
| `--graph-link-new` | с `--graph-build`, для опытного графа: новое имя сверяется по вектору с понятиями графа и решается арбитром до заведения узла; решения и очередь человеку — в `links.jsonl` |
| `--graph-limit <N>` | с `--graph-build`: разобрать не больше N кусков (замер скорости) |
| `--graph-workers <N>` | с `--graph-build`: сколько кусков разбирать одновременно |
| `--graph-status <имя\|all>` | состояние графа: понятия, связи, охват |
| `--graph-find "вопрос"` | то же, что `/search` в интерфейсе: понятия, связи и выдержки из книг |
| `--graph-collection <имя>` | с `--graph-find`: в какой коллекции искать |
| `--graph-json` | с `--graph-find`: выдать разбираемый JSON |
| `--kb-years <имя>` | проставить книгам год издания без переиндексации |
| `--kb-recount` | с `--kb-years`: перечитать год и там, где он уже стоит |
| `--kb-reindex <имя> <путь>…` | перечитать названные книги заново |

# Ведение диалога

`Enter` отправляет вопрос, `Alt+Enter` (или `Ctrl+J`) переносит строку. `Esc` прерывает ответ,
`Ctrl+C` дважды — выход.

**Стрелка вверх возвращает предыдущий вопрос**, как в оболочке: `↑` листает набранное
за этот запуск от последнего к первому, `↓` — обратно. Вернувшийся вопрос можно править
и отправлять снова. Это нужно, когда вопрос ушёл, а сервер оказался недоступен или модель
не умеет нужного: набирать заново длинный вопрос не приходится. В истории лежит **всё
набранное** — вопросы, слэш-команды и отклонённые вопросы; последние важнее прочего,
ради них она и заведена.

В многострочном вопросе стрелки сперва двигают курсор и уходят в историю только с самого
верха поля (вниз — с самого низа), чтобы длинный вопрос можно было править построчно.
Набранное, но не отправленное, не теряется: уйдя в историю и вернувшись вниз до конца,
вы получите его обратно. История живёт один запуск и на диск не пишется.

| Команда | Что делает |
|---|---|
| `/help` | справка |
| `/clear` | очистить историю диалога |
| `/compact [N]` | оставить последние N сообщений (по умолчанию 6); в чате при заполнении окна на `agent.compact_at` это делается само, сводкой |
| `/system [текст]` | показать или сменить системный промпт |
| `/paste` | вставить изображение из буфера обмена (то же, что `Ctrl+V`) |
| `/search [-f] [-r] [N] <текст>` | искать по графу и книгам, не спрашивая модель |
| `/read <id\|номер>` | показать найденный кусок целиком (`Ctrl+F` — список найденного, `Ctrl+O` — открыть саму книгу) |
| `/think [on\|off]` | режим рассуждений модели |
| `/savetopdf <файл.pdf>` | сохранить видимый ответ в PDF (`F4` — с запросом имени) |
| `/quit` | выход |

## Рассуждения

Модели с возможностью `thinking` показывают ход мысли отдельным приглушённым
блоком. `Ctrl+T` скрывает и показывает его, `/think off` выключает сам режим.

## Прокрутка

| Клавиши | Действие |
|---|---|
| колесо мыши, `PgUp` / `PgDn` | прокрутка, страница вверх/вниз |
| `Ctrl+U` / `Ctrl+D` | полстраницы |
| `Ctrl+Home` / `Ctrl+G` (и `Ctrl+End`) | в начало / в конец ответа |

Прокрутка работает и во время генерации: отлистали вверх — автопрокрутка встала на паузу,
в разделителе видно, сколько строк осталось ниже. `Ctrl+G` возвращает в конец и снова включает
слежение. Бегунок справа можно тянуть мышью, щелчок по полосе переносит в это место.

## Выделение текста мышью

`F2` (или `/mouse off`) отдаёт мышь терминалу — текст можно выделять
и копировать как обычно; колесо и бегунок при этом не работают, прокрутка остаётся на клавишах.
`F2` возвращает мышь приложению. Во многих терминалах то же самое даёт перетаскивание
с удерживаемым `Shift`.

## Копирование ответов

| Клавиша | Что кладёт в буфер |
|---|---|
| `F5` | ответ, видимый на экране сейчас |
| `Shift+F5` | его же вместе с вопросом, в виде записи журнала |

Ответом считается тот, что виден на экране, — не обязательно последний: отлистайте ленту вверх
к нужному месту и нажмите `F5`. Когда на экране видно несколько ответов, берётся занимающий больше
всего места, а при равной доле — нижний. **Копируется он целиком**, даже если помещается на экран
не весь.

Ответ, разорванный вызовами инструментов, склеивается из своих частей. Рассуждения и вывод
инструментов в буфер не попадают — там оказывается чистый текст ответа, тот самый markdown,
без оформления и без переносов по ширине окна.

`Shift+F5` даёт пару в том же виде, в каком запись ложится в журнал чата:

```
2026.08.16 12:35 ----- Вопрос

как работают горутины?

2026.08.16 12:40 (qwen3.5:122b) ----- Ответ

Горутина — это лёгкий поток, которым управляет среда выполнения Go…
```

Нужен `xclip` (X11) или `wl-clipboard` (Wayland) — те же утилиты, что и для вставки картинок
по `Ctrl+V`. Если их нет (например, при работе по ssh), текст отдаётся самому терминалу
последовательностью OSC 52; так умеют не все терминалы, и длинный текст многие обрезают —
об этом приложение предупреждает.

## Сохранение ответа в PDF

| Клавиша | Что сохраняет |
|---|---|
| `F4` | видимый ответ, без служебных заголовков |
| `Shift+F4` | его же вместе с вопросом и шапкой документа |
| `/savetopdf <файл.pdf>` | то же, что `F4`, но имя задано сразу в команде |

Ответ выбирается ровно так же, как при копировании по `F5`: берётся видимый на экране, целиком,
склеенный из частей, если его разрывали вызовы инструментов. Разница в том, что в файл попадает
не голый markdown, а **свёрстанный документ**: заголовки разных уровней, абзацы, маркированные
и нумерованные списки со вложенностью, жирный и наклонный текст, встроенный код, блоки кода
моноширинным шрифтом, цитаты с полосой слева, горизонтальные линии и **таблицы** с границами
и повтором шапки на новой странице. Подсветки синтаксиса нет — код набирается одним цветом.

`Shift+F4` добавляет в начало документа шапку: заголовок по первой строке вопроса, дата, модель
и сам вопрос. По `F4` документ начинается прямо с ответа — так удобнее, когда текст пойдёт дальше
в письмо или отчёт.

**Имя файла.** По клавише открывается окно с полем ввода: имя предлагается по вопросу, правится
как обычно, `Enter` сохраняет, `Esc` отменяет. Расширение `.pdf` дописывается само, если о нём
забыли. Имя **без пути** кладёт файл в рабочий каталог — тот, из которого запущен ollchat.
Если путь указан, файл сохраняется туда, куда сказано, **в том числе за пределы рабочего
каталога**: `~/Документы/ответ.pdf` или `/srv/share/отчёт.pdf`. Путь при этом проверяется —
каталог должен существовать, а цель не может быть каталогом или устройством. Существующий файл
молча не затирается: `Enter` покажет предупреждение и потребует подтверждения, `Esc` вернёт
к правке имени. Команда `/savetopdf` в этом случае просто откажется — подтверждать в ней нечего.

Шрифты вшиты в бинарь, внешние программы не нужны — ни `wkhtmltopdf`, ни LaTeX. Основной —
Liberation Sans и Liberation Mono (лицензия SIL OFL 1.1). К ним добавлен **резервный шрифт**:
в Liberation нет знака рубля `₽`, галочек `✓ ✗`, звёзд, стрелок `⇒`, двойных и жирных рамок
`╔═╗ ┏━┓`, а модель их пишет. Такие знаки берутся из урезанного DejaVu (лицензия Bitstream
Vera, текст — в `internal/pdfout/fonts/DEJAVU-LICENSE.txt`), по одному символу: вид основного
текста от этого не меняется. Того, чего нет и в резерве (эмодзи), заменяет `□`, и приложение
сообщает, сколько таких символов было — потерять символ молча оно не может.

# Файлы, документы и картинки

**Подсказка по командам.** Наберите `/` первым знаком строки — над полем ввода
появится список команд с кратким описанием. По мере набора список отбирается,
стрелки `↑`/`↓` водят по нему, а `Enter`, `Tab` или `→` подставляют выбранное
в строку — вправо принимает подсказку так же, как в fish и zsh. Когда команда
набрана целиком, `→` снова просто двигает курсор.
Именно подставляют, а не выполняют: у половины команд есть доводы, а `/clear`
и `/quit` с одного нажатия — верный способ потерять работу. Отправляет второй
`Enter`, `Esc` убирает подсказку, не трогая набранное.

Хвост ближайшей подходящей команды дописывается затемнёнными знаками прямо
в строке — как в fish и zsh. Это подсказка, а не текст: в отправляемый вопрос
она не попадает.

Подкоманды показываются наравне с командами: наберите `/kb` — увидите и саму
команду, и `/kb add`, `/kb embed`, `/kb merge` с описаниями. Описание, не
поместившееся в ширину окна, сворачивается многоточием.

Сколько команд видно — настройка `input.command_rows` (по умолчанию четыре;
панель занимает на три строки больше — рамка и заголовок).

Косая черта посреди вопроса подсказку не открывает: «что делает /api/chat» —
обычный вопрос, а не команда.

**Выбор файла по `@`.** Наберите `@` — над полем ввода появится список рабочего каталога.
Стрелки `↑↓` выбирают, `Enter` или `Tab` вставляет, `Esc` закрывает. Список фильтруется по мере
набора, каталог подставляется со слешем и список идёт вглубь. За пределы рабочего каталога
не выходит. Вставляется **только путь**; содержимое прикладывает `/add`.

**`/add <путь>`** кладёт файл в контекст. PDF и EPUB прикладываются извлечённым текстом,
а не байтами.

## Чтение документов

`read_file` и `/add` читают PDF и EPUB сами, без внешних программ. Из PDF извлекается текстовый
слой постранично (`── страница N ──`), из книги — главы по порядку чтения
(`── раздел N: заголовок ──`). Формат определяется по содержимому, расширение не важно. Предел
размера свой — `sandbox.max_pdf_mb`: в контекст идёт извлечённый текст, а не файл.

Таблицы в PDF собираются по координатам: ячейки строки остаются в одной строке, столбцы стоят друг
под другом, двухколоночная вёрстка разделяется на колонки. Сканы и документы с нечитаемыми
шрифтами распознаются как таковые и сообщаются прямо, а не отдаются модели в виде мусора.

## Рисунки в тексте документов

В тексте рисунки отмечены меткой `[рисунок 4.1: 1653×2338]` — страница и номер на ней.
Показать такую картинку модели можно двумя способами:

- инструментом `view_image` — модель вызывает его сама, увидев метку;
- командой `/addimg <путь> [страницы]` — например `/addimg книга.pdf 40-60`, картинки вкладываются
  метками `[Image01]`, `[Image02]`.

Обоим нужна модель с возможностью `vision`. Это важнее, чем кажется: таблицы цен в коммерческих
предложениях нередко свёрстаны картинкой целиком, и в текстовом слое их нет вовсе. У сканов
картинка — вся страница, поэтому так читаются и они.

## Вставка большого текста

Вставка из буфера обмена, которая не помещается в поле ввода, сворачивается в метку:

```
[Текст01: 4321 знак]
```

Дальше пишите вопрос обычным текстом рядом с меткой — при отправке она развернётся обратно,
и модель получит вставленный текст целиком. Ленте и журналу тоже достаётся полный текст,
свёрнут он только в поле ввода.

Так сделано потому, что сто строк ползут в трёхстрочное поле у вас на глазах: пока они
прорисуются, проходит заметное время, а видно всё равно последние три строки. Порог — не
число знаков, а место на экране: сворачивается то, что в отведённое полю место не влезает,
поэтому на широком терминале свернётся меньше.

Метка работает как метка картинки: **стёрли метку — отменили вставку**. Меток может быть
несколько (`[Текст01: …]`, `[Текст02: …]`), их можно переставлять местами — разворачивается
каждая на своём месте. Метка, набранная руками, остаётся обычным текстом.

## Картинки из буфера обмена

`Ctrl+V` кладёт изображение в промпт меткой `[Image01]`, дальше
пишите вопрос обычным текстом и ссылайтесь на метку словами. Стёртая метка отменяет вложение.
`F3` открывает панель вложений: видно, что реально приложено, `↑↓` выбирают, `Del` или `Ctrl+D`
убирает картинку вместе с меткой.

Своего доступа к буферу обмена у терминального приложения нет, поэтому нужна утилита графической
сессии: `xclip` в X11, `wl-clipboard` в Wayland. Те же утилиты обслуживают и копирование ответа
по `F5`.

**Если ollchat запущен по SSH.** Буфер обмена остался на вашей машине, и на удалённой его нет —
`Ctrl+V` честно об этом скажет. Забрать картинку через терминал нельзя: `OSC 52`, которым
ollchat отдаёт текст по `F5`, изображения не передаёт. Зато работает проброс X11:

```bash
sudo apt install xclip          # на удалённой машине, один раз
ssh -X пользователь@машина      # для долгих сеансов надёжнее -Y
echo $DISPLAY                   # должно быть непустым, например localhost:10.0
```

Тогда `xclip` на удалённой машине читает буфер вашего локального X-сервера, и `Ctrl+V`
работает как обычно. Проверено: картинка доходит побайтово той же.

Осторожно с `tmux` и `screen`: внутри уже созданной сессии `DISPLAY` остаётся от того
подключения, в котором она создавалась. После переподключения его надо обновить вручную
(`export DISPLAY=localhost:10.0` — значение подскажет свежая сессия), иначе вставка будет
молчать при исправно работающем пробросе.

# Серверы, модели и контекстное окно

| Команда | Клавиша | Что делает |
|---|---|---|
| `/servers`, `/server <имя>` | `Ctrl+S` | список серверов из конфига и переключение |
| `/models`, `/model <имя>` | `Ctrl+R` | список моделей (запрашивается у сервера заново): имя, число параметров, квантование, окно контекста, возможности |
| `/ps` | | что загружено в память сервера |
| `/info` | | подробности о текущей модели: семейство, квантование, возможности |
| `/context` | | сведения о заполнении контекстного окна |
| `/context set <N>` | | поставить окно в N токенов (`/context set 256k`) |
| `/context add <N>` | | прибавить к окну N токенов (`/context add 32k`) |
| `/context max` | | поставить наибольшее окно, какое умеет модель |
| `/calc [N]` | | какое окно дать каждому из N пользователей |
| `/graph tune [что] [знач.]` | | отбор связей на сеанс: `sense`, `pool`, `reset` |
| `/kb tune [что] [знач.]` | | числа поиска по книгам на сеанс: `top_k`, `max_per_book`, `min_cosine`, `semantic_weight`, `reset` |
| `/mix show <вопрос>` | | что подмешалось бы к вопросу — без обращения к модели |

## Индикатор контекста

**Скорость ответа** в строке состояния настраивается `general.token_speed`:
`live` — текущая, пока модель отвечает (со знаком `≈`: считается по кускам потока),
`final` — итог по последнему ответу из счётчиков сервера (по умолчанию),
`full` — и то и другое плюс время до первого токена, `off` — не показывать.
Время до первого токена стоит включать, когда работаете с общим сервером: по нему
сразу видно и загрузку модели с диска, и чужую очередь.

Индикатор в строке состояния показывает заполнение окна. После ответа сервера оно точное,
до него — оценка со знаком `≈`: Ollama не умеет считать токены до отправки запроса.

**Размер окна меняется посреди сеанса** командой `/context`: `set` ставит значение, `add` прибавляет
к нынешнему, `max` берёт наибольшее, какое умеет модель. Число пишется как угодно — `262144`,
`256k` или `256к` с русской буквой: раскладку ради одной клавиши переключать не надо.

**Больше максимума модели поставить нельзя.** Значение молча ограничивается им, и об этом
говорится отдельной строкой-предупреждением: «запрошено больше, чем умеет модель: максимум
40960 токенов, окно поставлено в него». Так сделано потому, что Ollama на завышенный `num_ctx`
не ругается — она берёт своё, а человек остаётся в уверенности, что у него 256k.

В конфиг ничего не пишется, только на текущий сеанс. Ollama берёт размер окна из каждого запроса,
поэтому со следующим вопросом модель перезагрузится с новым окном — это займёт время, а если
не хватит видеопамяти, часть модели уедет в оперативную и скорость упадёт (`/ps` покажет,
что вышло).

**`/calc N`** считает, какое окно можно дать каждому из N пользователей одновременно. Опирается
на замеры `olldiagtools`, если их профиль лежит рядом с конфигом; без профиля считает грубо
и честно об этом говорит. Подробности — в документации проекта, «Как считается цена токена».

# Агентный режим и разрешения

Модель может работать инструментами. Их одиннадцать:

| Инструмент | Что делает |
|---|---|
| `read_file` | читает файл; PDF и EPUB — извлечённым текстом |
| `list_dir` | список каталога |
| `grep` | поиск по содержимому файлов |
| `write_file` | создаёт или перезаписывает файл |
| `edit_file` | точечная правка по образцу |
| `bash` | команда в рабочем каталоге |
| `http_fetch` | забирает страницу по адресу |
| `web_search` | ищет в интернете и возвращает ссылки с выдержками |
| `confluence_connector` | читает страницу Confluence и отдаёт её в markdown |
| `view_image` | показывает модели картинку из PDF или EPUB |
| `kb_search` | поиск по библиотеке книг |
| `kb_read` | читает найденный фрагмент вместе с соседними |

`/tools` показывает включённые **и выключенные**: конфиг, созданный прежней версией, новых
инструментов не знает, и это единственный способ такое заметить.

## Подтверждения

Опасное действие показывается в рамке с четырьмя ответами:

| Ответ | Что значит |
|---|---|
| `y` | выполнить один раз |
| `n` | отклонить |
| `a` | разрешить **это действие** до конца сеанса |
| `t` | разрешить **весь инструмент** до конца сеанса |

Ответ `t` нужен для задач вроде обхода документации, где `http_fetch` иначе спрашивал бы про каждый
адрес. Защиту он не ослабляет: правила `deny` проверяются раньше, песочница ограничивает пути,
составные команды `bash` сеансовым разрешением не покрываются — их пропускают только
правила из настроек, и то лишь при безобидной склейке (см. ниже).

## Режимы

Режимы переключаются `Shift+Tab` по кругу или командой `/mode`:

| Режим | Поведение |
|---|---|
| `safe` | спрашивать про запись и команды |
| `auto-edit` | запись без спроса, команды с подтверждением |
| `noask` | не спрашивать; **запреты действуют**. Прежнее имя `yolo` продолжает работать |

## Правила и песочница

Правила записываются как `Инструмент(шаблон)`: `Read`, `Write`, `Bash`, `Fetch`.
Порядок проверки — **deny → allow → ask → режим**. Правило `deny` не обходится ничем: ни режимом
`noask`, ни ответом «разрешать всегда». Составная команда разбирается на части, и `deny` на любой
из них запрещает всю строку.

**Склейка разрешённых команд вопросов не задаёт** (с 31.08.2026). `grep … | head -50; ls …` —
три чтения, каждое разрешено правилом, и подтверждать тут нечего: человек, отвечающий «да»
по десять раз в час на заведомо безобидное, перестаёт читать, что ему показывают. Условия
строгие: каждая часть разрешена **правилом из настроек** (сеансовые разрешения на склейки
по-прежнему не распространяются), а склеены части только `|`, `||`, `&&`, `;` или переводом
строки. Перенаправление (`>`), подстановка (`$(…)`, обратные кавычки), фон (`&`) и подоболочки
спрашивают **всегда**, сколько бы правил ни стояло: `cat файл > /etc/passwd` состоит из одной
разрешённой части `cat`, а переписывает системный файл.

**Читающая программа с пишущим ключом спрашивает.** `find` и `sort` разрешены целиком,
но `find … -delete`, `find … -exec`, `-execdir`, `-ok`, `-okdir`, `-fprint`, `-fls`
и `sort -o` (`--output`) возвращают вопрос: разрешение выдано чтению, а этими ключами
та же программа удаляет, пишет или запускает чужое. Так же ведут себя `cp`, `mv`, `tee`,
`tar`, `chmod` — им разрешение не даётся вовсе. Похожий по началу ключ вопросом не делает:
`-original` это не `-o`, а файл с именем `*-delete-me*` не ключ `-delete`.
 Посмотреть действующие — `/permissions`.

**Песочница.** Выход за пределы рабочего каталога, `../` и символические ссылки наружу
отклоняются. Настраивается разделом `[sandbox]`.

# Поиск в сети

Инструмент `web_search` ищет в интернете и возвращает ссылки с короткими выдержками; страницу
целиком модель потом берёт через `http_fetch`. Нужен, когда ответа нет ни в её знаниях, ни в ваших
книгах, или когда сведения могли устареть: версии, выпуски, цены, состояние проектов.

## Почему нужен свой поисковик

Публичные поисковики запросы от программ отклоняют, и это **проверено, а не предположено**:

| Источник | Что вышло |
|---|---|
| DuckDuckGo (разбор вёрстки) | первый запрос отдал результаты, **второй — заглушку для роботов** |
| шесть публичных SearXNG | 403, 429 и HTML вместо JSON — ни одного рабочего |

Поэтому основа — **свой экземпляр SearXNG**: метапоисковик, который сам ходит в Google, Bing,
DuckDuckGo и десятки других источников, а наружу отдаёт единый JSON. Никаких ключей, лимитов
и чужих правил.

## Где ставить: на сервере или на этой машине

Поисковик — отдельная служба, и приложение знает о ней только адрес. Ставить можно куда угодно.

| | На сервере (общем) | Локально, рядом с ollchat |
|---|---|---|
| Кто ходит в Google и Bing | сервер, наружу светится его адрес | ваша машина |
| Нужен ли Docker на вашей машине | нет | да |
| Работает без сети до сервера | нет | да |
| Кому достаётся нагрузка | серверу | вашей машине (она невелика) |

Разницы для ollchat нет никакой: меняется одна строка в конфиге.

## Установка поисковика

Скрипт [ollscripts/searxngmanage.sh](ollscripts/searxngmanage.sh) один и тот же в обоих случаях —
он ни к какому серверу не привязан и ставит поиск туда, где запущен.

**На сервер:**

```bash
scp ollscripts/searxngmanage.sh СЕРВЕР:~/
ssh СЕРВЕР 'sudo ./searxngmanage.sh'
```

**Локально** (если Docker ещё не стоит — сначала он):

```bash
sudo apt install docker.io docker-compose-v2
sudo ./ollscripts/searxngmanage.sh
```

Обе команды требуют пароль sudo, поэтому выполнять их надо самому.

Ключи скрипта:

```
sudo ./searxngmanage.sh              поставить, а если стоит — обновить образ
sudo ./searxngmanage.sh -p 8080      другой порт (по умолчанию 8888)
sudo ./searxngmanage.sh -y           не задавать вопросов
sudo ./searxngmanage.sh -del         удалить, сохранив настройки
sudo ./searxngmanage.sh -restore КАТАЛОГ    восстановить настройки из копии
```

### Что делает установка

1. Проверяет root, `docker`, `docker compose`, systemd и что порт свободен.
2. Кладёт в `/opt/searxng` файлы `settings.yml` и `docker-compose.yml`.
3. В настройках включает **`search.formats: [html, json]`** — ради этой строки всё и делается:
   по умолчанию SearXNG отдаёт наружу только HTML, и `web_search` получил бы вёрстку вместо данных.
4. Прежние настройки копирует в `~/searxngbackups/ГГГГММДД-ЧЧММСС` того, кто запустил `sudo`.
5. Заводит службу systemd `searxng`, тянет образ, запускает.
6. **Проверяет, что JSON действительно отвечает**, и печатает готовую строку для конфига.

## Настройка в конфиге ollchat

Два места. Первое — адрес службы:

```toml
[web]
searxng_url = "http://searxng.example:8888"   # или "http://127.0.0.1:8888" для локального
timeout     = "20s"                     # предел ожидания поисковика
```

Пустой `searxng_url` выключает `web_search`: инструмент останется в списке, но объяснит, чего
не хватает, вместо того чтобы молча ничего не находить.

Второе — инструмент должен быть включён:

```toml
[agent]
tools = [..., "web_search"]
```

Проверить — команда `/tools`: она показывает и включённые, и выключенные.

### Подтверждения при поиске

`web_search` проверяется правилом `Fetch`, как и `http_fetch`: запрос уходит наружу.
По умолчанию `ask = ["Fetch(*)"]`, то есть приложение спросит про каждый поиск. Свой поисковик
в своей же сети разумно разрешить навсегда:

```toml
[permissions]
allow = [
  "Read(./**)",
  "Fetch(http://searxng.example:8888/**)",   # свой поисковик — без подтверждений
  ...
]
```

Остальные адреса при этом продолжат спрашивать, а `http_fetch` по чужим страницам — тем более.

### Проверить, что работает

```bash
curl -s 'http://searxng.example:8888/search?q=golang&format=json' | head -c 200
systemctl status searxng          # на той машине, где он стоит
docker logs searxng --tail 30
```

Ответ должен начинаться с `{"query":`. Если приходит `<!doctype html>` — в `settings.yml`
не включён формат JSON.

Замер на стенде: запрос отрабатывает за **1–1.5 секунды**.

### Про секретный ключ

При установке скрипт создаёт `secret_key` и при обновлении **берёт его из прежних настроек,
а не создаёт заново**. Ключ используется SearXNG в четырёх местах:

- подписывает cookie с настройками пользователя (веб-интерфейс поисковика);
- подписывает по HMAC-SHA256 ссылки на картинки через встроенный прокси — по подписи проверяется,
  что адрес не подменили;
- то же для значков сайтов;
- служит паролем к кэшу.

Для работы ollchat это почти безразлично: мы ходим в JSON API из программы, без cookie,
а прокси картинок выключен. Но если ключ менять при каждом обновлении, у людей, открывавших
поисковик браузером, слетят сохранённые настройки, а ранее выданные ссылки на картинки перестанут
проходить проверку. Дешевле сохранить, чем объяснять.

## Удаление поисковика

```bash
sudo ./searxngmanage.sh -del
```

Служба и контейнер удаляются, настройки остаются в `/opt/searxng` и в резервной копии. Образ,
если больше не нужен: `docker rmi docker.io/searxng/searxng:latest`.

# Confluence: чтение страниц корпоративной вики

Инструмент `confluence_connector` читает страницу по адресу или номеру и отдаёт её
**готовым markdown**. Дальше решает промпт: сказали пересказать — модель перескажет,
сказали сохранить в репозиторий — возьмёт `write_file` и запишет полученное.

```
Прочитай http://confluence.example.int:8090/pages/viewpage.action?pageId=66158622
и сохрани в reference/spravochniki.md
```

## Что нужно настроить

Раздел `[confluence]` с адресом сервера и `confluence_connector` в списке
`agent.tools`:

```toml
[confluence]
url     = "http://confluence.example.int:8090"
timeout = "60s"
```

**Токена в конфиге нет и не будет.** Файл настроек копируют, пересылают и кладут
в репозиторий — секрету в нём не место.

## Токен

Проще всего задать командой на сеанс:

```
/confluencetoken <токен>   принять на этот сеанс
/confluencetoken           сказать, задан ли токен, не показывая его
/confluencetoken off       забыть
```

**Токен не оставляет следов.** Он держится в памяти, на диск не пишется, в журнал
чата не попадает и **не сохраняется в истории ввода** — стрелка вверх не покажет его
тому, кто заглянул в экран. Плата за это одна: после перезапуска задать заново.

Если это неудобно, есть три источника постоянного хранения — они перечислены
в порядке старшинства, и команда главнее их всех:

| Настройка | Что в ней |
|---|---|
| `token_file` | путь к файлу; **права проверяются**: файл, читаемый всеми, отклоняется с готовой командой `chmod 600` |
| `token_cmd` | команда, печатающая токен: `pass show work/confluence` |
| `token_env` | имя переменной окружения |

Где взять сам токен: в Confluence Server и Data Center — профиль → Personal Access
Tokens. Заводите **отдельный токен с правами только на нужные пространства**: модель
увидит ровно то, что видит его владелец, и токен администратора открывает ей всё,
включая кадровое и договоры.

## Что приходит в ответ

Страница переводится в markdown вместе с шапкой о происхождении — адрес, номер
страницы, версия, кто и когда правил, предупреждение, что файл собран выгрузкой
и правки руками пропадут при следующей.

Три вещи, которые обычная выгрузка теряет, а эта — нет:

- **свёрнутые блоки раскрываются.** В них лежит то, что автор счёл громоздким, —
  обычно как раз данные, ради которых страницу и читают;
- **блоки кода доезжают дословно**, вместе с управляющими символами: если на странице
  разбирается беда с непечатным разделителем, «поправить» его нельзя;
- **таблицы остаются таблицами.** Многострочная ячейка склеивается в одну строку —
  markdown иначе не умеет, — но данные целы: теряется вёрстка, а не содержимое.

Неизвестный макрос Atlassian не проглатывается молча: его содержимое печатается
с пометкой `_[макрос jira]_`. Тихая пропажа куска страницы — худший исход
из возможных.

В конце перечисляются вложения, а если попросить (`children`) — дочерние страницы
списком, без содержимого: у страницы их бывают десятки, и один вызов иначе вывалил бы
в контекст мегабайт. Нужную читайте отдельным вызовом по её номеру.

## Чего инструмент не делает

**Не пишет в Confluence.** Страницу правит человек в самой вики, а не модель через
инструмент: цена ошибки несопоставима с удобством.

**Не скачивает вложения.** Картинки и приложенные файлы видны в списке, но их
содержимое не тянется. Если суть страницы в приложенном скриншоте — а так бывает, —
это будет видно по списку вложений.

**Не переписывает таблицы своими словами** — и вам не советует просить об этом модель.
Таблица кодов, прогнанная через языковую модель, возвращается с тихо исправленной
опечаткой в коде, и не заметит этого никто. Сохраняйте полученный markdown как есть.

## Разрешения

Запрос идёт через те же правила, что и `http_fetch`: вид разрешения `Fetch`, правило
`deny` на хост действует и здесь. Чтобы не подтверждать каждую страницу отдельно,
добавьте в `permissions.allow` строку вида:

```toml
"Fetch(http://confluence.example.int:8090/*)"
```


# База знаний: книги и документация

Библиотека PDF и EPUB превращается в **коллекцию**, по которой ищет и пользователь, и модель.
Ответ всегда со ссылкой на книгу и страницу, чтобы его можно было проверить.

Коллекция не обязательно про книги. Те же команды индексируют **документацию проекта** —
файлы `.md` и `.txt`: у них единица ссылки не страница, а **строка** («строки 120–140»),
к куску приписывается заголовок раздела, а видеокарта не нужна вовсе — текст не разбирается
моделью. Так собрана коллекция `projectdocs` по документации самого ollchat; устройство —
в документации проекта, «Текстовые документы в базе знаний». Дальше «книга» означает любой
проиндексированный файл.

Поиск двухслойный:

| Слой | Что делает | Когда нужен | Стоимость |
|---|---|---|---|
| **Слова** (BM25) | находит точные термины: `sync.WaitGroup`, номера версий | всегда, работает сразу | ~0.6 МБ на книгу |
| **Смыслы** (эмбеддинги) | находит по описанию своими словами | когда спрашивают не терминами | ~1.3 МБ на книгу, нужна модель эмбеддингов |

Слова индексируются при добавлении книг. **Смыслы считаются только по вашей команде** — это
десятки минут работы видеокарты, и запускать такое самовольно приложение не будет никогда.

Устройство смыслового поиска и все замеры — в документации проекта, «Смысловой поиск по книгам».

## Весь путь от начала до конца

Ниже — связный рассказ: что делается, зачем и чем за это платится. Отдельные команды
разобраны подробнее в разделах после него; здесь важен порядок и смысл.

### Из чего всё состоит

**Книга** — файл PDF, EPUB, `.md` или `.txt` на диске. Библиотека остаётся там, где лежала:
ollchat её не копирует и не двигает.

**Кусок** — примерно 1200 знаков связного текста, около 350 токенов. Книга режется
на куски, потому что искать надо не «в книге на 800 страниц», а в том месте, где
о предмете действительно написано. У каждого куска есть точный адрес: книга и страница.

**Коллекция** — именованный набор книг с построенным по ним индексом. Она **не привязана
к проекту**: коллекции общие для всех ваших проектов и всех запусков, лежат
в `~/.local/share/ollchat/kb/collections/<имя>`.

**Индекс** — то, что делает поиск быстрым. Он бывает двух слоёв, и это важно понимать
сразу, потому что дальше все решения крутятся вокруг них:

- **слова (BM25)** — считается на процессоре при добавлении книг, всегда, бесплатно;
- **смыслы (векторы)** — считаются моделью на видеокарте, **только по вашей команде**.

**Граф понятий** — надстройка над коллекцией, отвечающая на вопрос «как это связано
с тем». Строится отдельно и стоит дорого; о нём в конце.

### Где что лежит на диске

Всё, что относится к коллекции, лежит **в одном каталоге** — и куски книг, и оба
слоя индекса, и граф понятий:

```
~/.local/share/ollchat/kb/collections/books/
  chunks.dat, chunks.idx      куски книг                      103 МБ
  seg-00001 … seg-00007       словесный индекс (BM25)          77 МБ
  vectors.dat, vectors.meta   смыслы кусков                   364 МБ
  graph/                      граф понятий                    183 МБ
  ─
                              коллекция целиком               727 МБ
```

Числа — с настоящей библиотеки: 301 книга, 372 716 кусков. По ним видно, за что
платится место: **смыслы дороже словесного индекса впятеро**, потому что вектор
занимает 1024 байта на кусок независимо от его длины.

Внутри `graph/`:

```
entities.jsonl    93 МБ    реестр понятий: имена, синонимы, типы
entities.vec      78 МБ    векторы понятий — смысловой вход в граф
edges.log          8 МБ    связи между понятиями
mentions.log       5 МБ    в каких кусках какое понятие встречается
communities.json   7 МБ    разбиение на темы и их описания
merges.jsonl              склейки двойников
progress.log              какие куски уже разобраны
LOCK                      признак идущей сборки
```

### Корень коллекции

**Корень — это каталог, из которого добавляли книги.** Он записан в паспорте
коллекции `meta.json`; корней может быть несколько — каждая команда
`/kb add <имя> <путь>` добавляет свой.

```json
"roots": ["/media/user/NVME/Books"]
```

Корень не украшение, он работает в трёх местах:

| где | зачем нужен |
|---|---|
| `--kb-sync` без пути | знает, **что сверять**: обходит корни и ищет новое |
| сообщение при запуске | «появилось 3 новые книги» — сверка по размеру и времени |
| `--kb-list`, `--graph-status`, `--graph-folder` | разбивка по каталогам считается **относительно корня** |

Последнее объясняет, почему `--graph-folder /Coding/Go` вообще работает:
`/Coding/Go` — это путь **внутри корня**, а не абсолютный путь на диске.

**Не путать с `kb.roots` в настройках.** Там — граница безопасности, список
каталогов, откуда вообще разрешено индексировать. Здесь — история того, откуда
книги пришли.

### Реестр книг `docs.jsonl`

Лежит в каталоге коллекции, строка на книгу, только дозапись:

```json
{"id":42, "path":"/media/user/NVME/Books/AI/Книга.pdf",
 "size":4823901, "mtime":1755012345, "kind":"ok",
 "title":"Название", "author":"Автор", "year":2025, "year_src":"имя файла",
 "format":"pdf", "units":412, "unit":"страниц", "chunks":1873}
```

Это **единственное место, где хранятся пути к вашим файлам**. Читаются они не
всегда:

| что делаете | нужен ли файл на диске |
|---|---|
| поиск по книгам, смысловой поиск, граф | **нет** — текст лежит в самой коллекции |
| заголовок в выдаче, отбор по `book:` и `--graph-folder` | нет — берётся строка из реестра |
| `/kb doctor` | да — проверяет, что файлы на месте |
| `--kb-sync`, `--kb-reindex` | да — читает книги заново |

### Коллекция переносима: скопировали каталог — перенесли всё

**Ни в индексе, ни в графе нет путей к вашим файлам.** Скопируйте каталог
коллекции на другую машину — и поиск, и смыслы, и граф поедут вместе с ним.
Пересобирать ничего не нужно, а сборка графа стоит часов работы видеокарты.

Библиотека книг при этом **не нужна**: текст кусков хранится в самой коллекции.
Книги понадобятся только для доливки новых и для `--kb-reindex` — и пути к ним
лежат в единственном файле, `docs.jsonl`. Перенесли коллекцию на машину, где
книги лежат иначе, — поиск, смыслы и граф работают как ни в чём не бывало,
а доливка скажет, что файлов не нашла.

### Если на новой машине книги лежат по другому пути

Тогда есть тихая и дорогая беда. Доливка узнаёт книгу **по точному совпадению
пути**, поэтому `--kb-sync` не признает ни одной старой книги и **проиндексирует
всю библиотеку заново**: коллекция удвоится, а смыслы к копиям придётся считать
часами. `/kb doctor` при этом объявит пропавшими все книги, хотя они на месте.

Лечится одной командой, без переиндексации:

```bash
# сперва посмотреть, что получится
ollchat --kb-rebase books --kb-rebase-to /новый/путь/к/книгам --kb-dry-run

# применить
ollchat --kb-rebase books --kb-rebase-to /новый/путь/к/книгам
```

Она переписывает пути в реестре и корни в паспорте — два файла. Куски,
словесный индекс, смыслы и граф не трогаются вовсе: путей они не содержат.

Старый корень берётся из паспорта, когда он там один. Если корней несколько,
команда покажет их и попросит указать нужный:

```bash
ollchat --kb-rebase books --kb-rebase-from /старый --kb-rebase-to /новый
```

Что она проверяет за вас:

- **совпадение по границе каталога, а не по подстроке** — корень `/books`
  не тронет пути в `/booksold/`;
- **книги не под старым корнем не меняются** и считаются отдельно;
- **если под указанным корнем ничего нет — отказ** со списком настоящих корней,
  а не молчаливое «переписано 0»;
- **файлов нет по новому пути — это предупреждение, а не отказ**: поиск, смыслы
  и граф работают и без библиотеки на диске.

Обратная сторона той же связности: **граф привязан к состоянию коллекции**.
Ссылки в нём — это номера вида `books/12#37`, то есть номер книги и номер куска
внутри неё. Поэтому:

- уплотнение `/kb merge` при собранном графе **отклоняется**: оно меняет число
  кусков, и граф перестал бы открываться. Обход — явный `--kb-merge-force`,
  и тогда граф придётся собирать заново;
- несовпадение состояния — это отказ открыть граф, а не тихий неверный ответ.

Каталоги с другим именем (`graph-старый`, `.compact-books`) программа пропускает,
так что рядом можно держать отставленный граф или прерванное уплотнение.

### Зачем нужны два слоя поиска

Слова находят точное: имя функции, номер версии, код ошибки. Если вы ищете
`sync.WaitGroup`, никакие «смыслы» не нужны — и мешать будут.

Смыслы находят по описанию. Вопрос «как не потерять данные на границе кусков»
не содержит слова «перекрытие», а нужный абзац содержит именно его. Слова тут промахнутся,
векторы — нет.

Отдельный случай, ради которого смыслы и заводились: **библиотека английская, а вопросы
русские**. По словам «горутина» не найдёт `goroutine` никогда — граница языка для BM25
непроходима. Многоязычная модель эмбеддингов эту границу переходит.

Вывод, который стоит запомнить: **смыслы нужны не всегда**. Для документации проекта,
где ищут точные имена файлов и флагов, они бесполезны — а видеокарту занимают.

## Шаг 1. Разрешить каталоги

Книги лежат вне песочницы, и права на них даёт только файл настроек:

```toml
[kb]
dir   = "~/.local/share/ollchat/kb"
roots = ["/mnt/books", "/media/nvme/BooksNOW"]
```

Без этого индексация откажется работать и перечислит, что разрешено. Это не придирка:
команда индексации обходит каталог целиком, и ошибка в пути означала бы попытку
прочитать что-нибудь неожиданное.

## Шаг 2. Собрать коллекцию

```bash
ollchat --kb-index books /mnt/books
```

`books` — имя коллекции, придумываете вы. Каталог обходится вглубь; берутся `.pdf`,
`.epub`, а также `.md` и `.txt`. Каталоги, начинающиеся с точки, пропускаются.

Что происходит внутри: каждая книга читается своим разборщиком (PDF — по координатам,
чтобы таблицы не рассыпались; EPUB — по главам), режется на куски, куски попадают
в словесный индекс. Год издания вытаскивается из имени файла, копирайта и метаданных.

**Сколько это стоит:** 198 книг, 249 тысяч кусков — 2 минуты 21 секунда, 124 МБ на диске.
Видеокарта не нужна вовсе.

Сканы без текстового слоя честно помечаются пропущенными: из них извлекать нечего,
поможет только распознавание.

Проверить, что вышло:

```bash
ollchat --kb-list
```

## Шаг 3. Решить, нужны ли смыслы

Сначала посмотрите, сколько это будет стоить, — команда ничего не считает и карту
не трогает:

```bash
ollchat --kb-embed books --kb-dry-run
```

```
осталось кусков: 21401 из 302211
ориентировочно: 7m22s
на диске ещё: 22 МБ
```

Если решили считать:

```bash
ollchat --kb-embed books
```

Нужна модель эмбеддингов на сервере Ollama — в настройках `kb.embed_model`,
у нас это `bge-m3` (многоязычная, 1024 измерения). Работа идёт минутами, но **занимает
видеокарту**, поэтому запускать стоит отцеплённо:

```bash
setsid nohup ollchat --kb-embed books > ~/kb-embed.log 2>&1 &
tr '\r' '\n' < ~/kb-embed.log | tail -1     # смотреть ход
```

Прервали — не страшно: повторный запуск досчитает недостающее, посчитанное не трогается.

**Смыслы не обязательны.** Коллекция без векторов — законное состояние, а не
недоделка: словесный поиск работает сразу и полностью, и для точных имён —
`sync.WaitGroup`, `OLLAMA_NUM_PARALLEL`, номер версии — он **сильнее** смыслового,
который тянет к похожему по теме, а не к тому же слову. Смыслы нужны, когда спрашивают
своими словами и через границу языка («горутина» → `goroutine`). Видеокарта нужна
только им; коллекции документации обычно обходятся без смыслов. Есть ли у коллекции
смыслы и отвечает ли модель эмбеддингов, видно в `/kb stats` и по цвету имени модели
в строке состояния.

**`--kb-dry-run` работает со всеми командами обслуживания базы:** `--kb-embed`, `--kb-sync`,
`--kb-index`, `--kb-refresh`, `--kb-rebase`. Показывает, что было бы сделано, и не меняет
ничего. Раньше ключ действовал только на `--kb-embed`, а к остальным молча не применялся —
«сухая» синхронизация доиндексировала полсотни книг по-настоящему.

```
ollchat --kb-sync books --kb-dry-run
  добавилось бы книг: 12
  пропавших с диска:  0
```

Оценка времени у `--kb-embed --kb-dry-run` делается настоящим замером на 200 кусках, но
у замера свой предел ожидания в минуту: пока карту занимает сборка графа, сервер эмбеддингов
не отвечает вовсе, и тогда печатаются только счётчики с объяснением, почему времени нет.

**Открытый граф держится в памяти между вопросами.** Открытие стоит 11.5 секунды и до
1.03 ГБ пика памяти, а сам открытый граф удерживает 160 МБ — платить за чтение на каждом
вопросе незачем. Выключается настройкой `graph.cache = false` там, где памяти мало: тогда
граф читается заново на каждый вопрос и сразу освобождается.

При каждом настоящем открытии в ленте появляется строка о том, во что оно обошлось:

```
граф открыт за 11.5 с, занимает 160 МБ, при открытии до 380 МБ
```

Цвет — сигнал: песочный тусклый до `graph.open_slow_seconds` (10 с), светло-оранжевый
до `graph.open_hot_seconds` (20 с), дальше красный. Пороги и цвета настраиваются; цвет
задаётся как в теме — номером ANSI или `#rrggbb`. Обе величины растут вместе с библиотекой,
и по ним видно, когда пора думать о другом хранилище — разбор в документации
проекта, «Как идёт сборка графа».

В строке состояния при открытом графе виден значок **`GR: 160 МБ`** — сколько памяти он
держит; единица выбирается сама, мегабайты или гигабайты. Выключается
`graph.show_memory = false`.

### Предел вызовов инструментов

`agent.max_iterations` — сколько раз подряд модель может попросить инструмент
в одном обмене. Предохранитель от зацикливания: модель, застрявшая в цикле
«прочитать — не понять — прочитать снова», иначе крутится, пока не кончится
контекст.

```toml
[agent]
max_iterations = 25   # умолчание
max_iterations = -1   # без ограничения
```

**-1 снимает предел совсем.** Это нужно для обхода документации и разбора
каталогов, где вызовов заведомо много: ход обрывался на середине работы.
Прервать затянувшийся ход всегда можно `Esc`, а каждый вызов ограничен своим
таймаутом (`agent.bash_timeout`).

Менять, не выходя из программы:

```
/tools                      что включено и какой сейчас предел
/tools iterations 50        поднять предел на этот сеанс
/tools iterations off       снять предел на этот сеанс
```

Сеансовая правка в конфиг не пишется — как `/think`, `/mouse` и `/mode`.

**Замер входа в граф: `ollchat --graph-entry-eval вопросы.toml`.**
Прогоняет вопросы набора через настоящий вход в граф и считает **без модели и без
судьи**: нашлись ли оба понятия, о которых спрашивают, каким по счёту и сколько
в выдаче постороннего. Нужен, чтобы правки отбора принимались числами, а не
впечатлениями. Замер 03.09.2026: оба понятия найдены в 59 случаях из 60, среднее
место 2.45, постороннего 4 понятия на вопрос из шести.

**Уплотнение реестра понятий: `ollchat --graph-compact books`.** Реестр дозаписывается,
и за недели сборки каждое понятие переписывается десятки раз: на библиотеке из 465 тысяч
кусков это 3.2 млн записей на 161 тысячу понятий и 499 МБ файла. Уплотнение оставляет по
одной записи на понятие — файл 25 МБ, открытие графа 41 с → 2.7 с.

Команда осторожна: сперва пишет новый реестр во временный файл, затем загружает оба и
сличает словари поиска до последнего ключа, и **подменяет файл только при полном
совпадении**. Прежний реестр остаётся рядом с отметкой времени — удалите его сами, когда
убедитесь, что поиск в порядке. Ключи `--graph-compact-check` (только сличить) и
`--graph-compact-force` (подменить, несмотря на расхождения).

**Несколько графов над одной библиотекой.** Рабочий граф лежит в каталоге `graph`
коллекции, опытные — рядом: имя `lab` означает каталог `graph-lab`. Книги у них общие,
дублируются только извлечённые понятия и связи. Выбор графа: настройка `graph.name`,
ключ `--graph-name lab` или команда `/graph use lab` (`/graph use -` — вернуться
к рабочему). В паспорте графа хранится его назначение: `production` или
`experimental` — на опытный граф доктор и значок `!граф!` не срабатывают, он неполон
по замыслу.

**Полоса хода открытия графа — в строке ввода.** Граф открывается десятки секунд
(41 с на библиотеке из 465 тысяч кусков), и всё это время в строке ввода бежит полоса:

```
открываю граф · реестр понятий   47% · 19 с [████████░░░░░░░░]
```

Полоса появляется **только на настоящем открытии** — когда граф уже в памяти, её нет.
Открытие идёт в фоне, интерфейс при этом жив: вопрос виден в ленте сразу, `Esc` отменяет.
Сам граф открывается заранее, при запуске программы, чтобы за него не платил первый вопрос.

**Значок `!граф!` в строке состояния** означает, что граф или смыслы требуют внимания:
собраны не по всей библиотеке, устарели векторы, разъехалась разметка тем. При запуске
о том же говорится подробно, а значок висит до тех пор, пока беда не устранена — сообщение
в ленте уезжает вверх и забывается, а граф стоит часов видеокарты и портится молча.
Что именно не так и какими командами чинится — скажет `ollchat --graph-doctor books`.

**Состояние модели эмбеддингов видно в строке состояния** — сразу за именем файла журнала:
имя модели **зелёным**, если она отвечает, **красным**, если нет.

```
лог: chat-2026-08-29_14-02-11.md · bge-m3 · rr
```

Рядом — вторая ступень поиска, коротким `rr`: зелёное — служба переранжирования отвечает,
красное — нет. Имя службы в строку не выносится: там тесно, а важно только «работает или
нет» — имя говорится в сообщении, когда есть что сказать. Значка нет вовсе, если
`kb.rerank_url` пуст: это означает «второй ступени не хотим», и красный значок сообщал бы
о поломке там, где ничего не ломалось.

Индикатор появляется, только когда есть что показывать: смысловой поиск настроен
и векторы(смыслы) посчитаны хотя бы у одной коллекции. На машине без библиотеки книг его нет —
он был бы вечным напоминанием о возможности, которой там не предполагалось.

Обе службы проверяются одинаково и с одним сроком. Разница — в тоне сообщений, и она
по существу: **без эмбеддера нужное не находится вовсе**, а без реранкера находится, только
стоит не на первом месте.

Проверка идёт **не только при запуске**: `kb.embed_check` (по умолчанию `"1m"`) задаёт,
как часто повторять. Модель отваливается посреди работы — сервер перезапустили, модель
выгрузили, место кончилось, — и без повторной проверки человек узнал бы об этом только
по ухудшившимся ответам. `"0"` оставляет одну проверку при запуске.

О поломке говорится **один раз на переход**, а не на каждую проверку: раз в минуту
повторять одно и то же значит приучить не читать предупреждения. Когда модель возвращается,
об этом тоже сообщается — иначе непонятно, можно ли снова доверять поиску.

**Если модель эмбеддингов недоступна, ollchat скажет об этом при запуске.** Проверка идёт
одним коротким запросом в фоне и делается только тогда, когда смысловой поиск вообще
настроен и векторы посчитаны. Не ответила — в ленте появляется предупреждение: что именно
сломалось, чем это обернётся («ищем только по совпадению слов, смысловой вход в граф
не работает») и что проверить — скачать модель или поправить `kb.embed_url`.

Предупреждение не выключается настройкой `general.startup_hints`: та гасит советы
об устройстве конфига, а здесь речь о том, что заявленная возможность не работает прямо
сейчас. Молчание тут дороже: поиск не падает, он тихо теряет половину, и человек ищет
причину в чём угодно, только не в этом.

**Вектор вопроса и векторы кусков обязаны считаться одной и той же моделью.** Это не
пожелание, а условие работы: сравниваются не тексты, а координаты в пространстве, которое
каждая модель строит своё. Вектор от `bge-m3` и вектор от `nomic-embed-text` — числа
из разных систем координат, и расстояние между ними не значит ничего; поиск не сломается
с ошибкой, он просто начнёт выдавать случайное.

Отсюда три следствия, о которых стоит помнить:

- **Сменили `kb.embed_model` — пересчитайте векторы** (`/kb embed <имя> --recount`).
  ollchat замечает расхождение сам: в файле векторов записано, какой моделью они посчитаны,
  и при несовпадении смысловой поиск **выключается** с объяснением «векторы(смыслы) посчитаны
  моделью X, а в настройках Y» — выдача остаётся словесной, но молча неправильной не будет.
- **Модель должна быть на сервере в момент вопроса.** Вектор вопроса считается на каждый
  вопрос; нет модели — нет смыслового поиска, остаётся только BM25.
- **То же касается графа:** векторы понятий (`--graph-embed`) считаются той же моделью,
  и смысловой вход в граф работает по тем же правилам.

**Коллекция без смыслов — законное состояние**, а не недоделка. Если по ней ищут точные
слова, векторы не нужны никогда.

## Шаг 4. Пользоваться

В чате коллекция выбирается один раз:

```
/kb use books
```

Дальше модель ищет сама инструментом `kb_search` и отвечает со ссылками на книгу
и страницу. Руками — `/search <вопрос>`: поиск по графу и книгам без обращения
к модели, с понятиями, связями и выдержками (ниже — «Искать своими глазами»).

**Если коллекций больше одной, обязательно задайте `kb.default`** в настройках. Пока
коллекция одна, она выбирается сама; как только их две, выбирать становится не из чего,
и подмешивание знаний к вопросам **молча перестаёт работать** — без ошибки, просто
перестаёт. Это самая частая беда при заведении второй коллекции.

### Какая коллекция выбирается

Коллекции общие для всех проектов и всех запусков: `/kb use` в одном окне
не влияет на другое. Порядок выбора один и тот же у инструментов модели, у службы
`ollmcp` и у подмешивания:

1. **параметр `collection`** в вызове инструмента (`kb_search`, `kb_read`) — если модель
   его назвала;
2. иначе **`kb.default`** из настроек;
3. иначе **единственная** коллекция в базе.

Коллекций несколько, `kb.default` пуст, параметр не назван — инструмент отвечает
отказом с перечнем коллекций, а подмешивание молчит. В чате `/kb use <имя>` задаёт
коллекцию на сеанс поверх `kb.default`.

### Честное «в книгах нет»

Поиск по книгам всегда возвращает восемь кусков, даже когда спросили о том, чего
в библиотеке нет, — и модель, которой велено ссылаться на книгу и страницу, отвечает
правдоподобной выдумкой с точной ссылкой. От этого есть порог `kb.abstain_score`.

Работает он только при включённом реранкере (`rerank_url`): у реранкера одна шкала
на все запросы — кусок по делу около +1, не по делу около −10. Если даже **лучший**
кусок выдачи оценён ниже порога, `kb_search` ставит сверху предупреждение модели:
по замеру это почти всегда значит, что в книгах об этом нет, не выдавай куски за ответ,
скажи, что в библиотеке не нашлось. Куски при этом всё равно отдаются — модель может
убедиться сама.

Значение снимается замером, а не назначается: `ollchat --kb-eval набор.toml
--kb-eval-rerank` печатает таблицу «воздержание», сколько вопросов промолчали бы честно
и сколько зря. На живой библиотеке порог −2 молчит на 12 вопросах из 457: в 11 нужного
куска и не было, в одном был. Без реранкера параметр не действует, убрать строку —
выключить. На `/search` и подмешивание не влияет.

```toml
[kb]
abstain_score = -2.0
```

## Шаг 5. Доложить книги

Положили новые файлы в тот же каталог — и:

```bash
ollchat --kb-sync books
```

`sync` обходит записанные в коллекции каталоги и берёт **только новое и изменившееся**:
у старых книг сверяются размер и время правки, и они не перечитываются. Отсюда
и скорость — 23 книги за 12 секунд при 221 уже проиндексированной.

Затем — смыслы для новых кусков, если они у этой коллекции считаются:

```bash
ollchat --kb-embed books
```

Считаются **только недостающие**: 21 401 кусок за 6 минут, старое не трогается.

Это и есть ответ на «как добавлять книги»: две команды, и обе берут только дельту.
Полная пересборка не нужна никогда — на этом свойстве вся затея и держится.

## Шаг 6. Перечитать книги заново

Нужно, когда изменился сам разбор — например, в тексте нашлись невидимые якоря
предметного указателя, и разборщик научился их убирать. `sync` такие книги пропустит:
файлы-то не менялись.

```bash
ollchat --kb-reindex books "/путь/книга1.pdf" "/путь/книга2.pdf"
```

Прежние куски этих книг помечаются удалёнными; поиск сразу перестаёт их выдавать.
После этого нужен `--kb-embed`: у новых кусков смыслов ещё нет.

## Шаг 7. Уплотнить, когда мусора накопилось

Удалённые куски остаются на диске: сегменты индекса неизменяемы, и **именно поэтому
доливка книг стоит столько, сколько новых книг, а не пересборку всего**. Плата за это —
место.

```bash
ollchat --kb-merge books
```

Уплотнение переписывает хранилище без удалённого и сливает сегменты в один.
**Поиск от этого не ускоряется** — замер 30.08.2026 на копии живой библиотеки:
18 сегментов дают 28.37 мс на запрос, тот же корпус в одном сегменте — 28.68 мс.
Выигрыш у уплотнения один: место на диске. Само оно не запускается никогда: на большой коллекции это минуты
чтения и записи. Подсказка «пора» появляется в `/kb stats`.

**Если по коллекции собран граф понятий, уплотнение отклоняется.** Не предупреждением,
а отказом: граф после него не открывается вовсе, а стоит часов работы видеокарты.

### Два подтверждения, а не одно

Уплотнение — единственное необратимое действие над базой знаний: прежнего хранилища
не остаётся, отменить нечем. Поэтому команда сначала показывает, что именно произойдёт,
и только потом дважды спрашивает.

```
Уплотнение коллекции books

Что будет сделано:
  · хранилище кусков переписывается заново, остаются только живые книги: 386
  · текст 15 книг, помеченных удалёнными, стирается с диска (18685 кусков)
  · стирается 12277 кусков книг, перечитанных заново: записи о них уже нет
  · 18 сегментов сливаются в один (на скорости поиска это,
    по замеру на этой библиотеке, не сказывается)
  · освободится примерно 72.1 МБ из 1026.7 МБ

Чего нельзя будет вернуть:
  · прежнего хранилища не остаётся — отмены нет ни у команды, ни у программы;
  · сквозная нумерация кусков меняется, и выданные раньше ссылки
    вида «books/12#37» станут указывать не туда;
  · ГРАФ ПОНЯТИЙ ПЕРЕСТАНЕТ ОТКРЫВАТЬСЯ. Он опирается на эту нумерацию.
    Потеряется: 116801 понятий, 587644 связей, 757351 упоминаний.
    Собрать заново — прогнать 112412 кусков через qwen3.8:latest:
    ровно столько же работы видеокарты, сколько уже потрачено.

Уплотнить коллекцию books и стереть с диска 30962 куска без возможности вернуть?
Напишите ДА (заглавными) и нажмите Enter:
```

Ответ — **слово `ДА` заглавными**, и только оно: `y`, `да`, `yes` и Enter означают отказ.
Согласие ценой одного нажатия человек даёт не читая — рука знает, где `y`, раньше, чем
глаз дочитал вопрос. Слово надо набрать, а набрав — на секунду задуматься.

Вопроса два, и они **разные**: первый про коллекцию и стираемые куски, второй — про то,
что дороже всего: про граф (а если графа нет — про ссылки на куски). Два одинаковых
вопроса подряд человек проходит на одном движении, два разных — нет.

Полезные мелочи:

| | |
|---|---|
| `--kb-dry-run` | показать всё то же самое и **ничего не делать** |
| `--kb-yes` | не спрашивать вовсе — для скриптов |
| ввод не с терминала | уплотнение не начинается: спросить некого. Нужен `--kb-yes` |
| `--kb-merge-force` | отказ по графу подтверждением **не снимается** — только этим ключом |

Последнее важно: два `ДА` разрешают уплотнение, а не потерю графа. Потерю графа
разрешает отдельный ключ, и это осознанное действие, а не следствие двух нажатий.

### Как этим пользуется ассистент

Документацию проекта можно не читать целиком, а **искать**: отдельная коллекция
по её каталогу и служба `ollmcp` дают ассистенту (любому клиенту MCP)
инструменты `kb_search` и `kb_read`, и ответ приходит со ссылкой на файл и строки.
Индекс доливается `--kb-sync projectdocs` за секунды без видеокарты; отставший файл
находит `--kb-doctor`. Порядок работы, что для этого нужно и три способа получить
неверный ответ — в документации проекта, «Как ассистент работает с документацией».

## Шаг 8. Граф понятий — если нужен

Всё предыдущее отвечает на вопрос «где про это написано». Граф отвечает на другой:
«как это связано с тем» и «из чего вообще состоит предмет».

Он **не обязателен**. Заводить его стоит, когда вопросы пошли про связи, сравнения
и обзоры, а не про факты.

```bash
# 1. Извлечение понятий и связей — самое дорогое во всём проекте
setsid nohup ollchat --graph-build books --graph-folder /AI/ --graph-workers 4 \
  > ~/graph.log 2>&1 &

# 2. Разбиение на темы — секунды, карта не нужна
ollchat --graph-communities books

# 3. Описание тем моделью — один запрос на тему
ollchat --graph-summaries books

# 4. Проверка самых рыхлых тем честной моделью — минуты
ollchat --graph-recheck books

# 5. Векторы понятий — смысловой вход в граф, 20 минут на 60 тыс. понятий
ollchat --graph-embed books

# 6. Разбор важных тем — что именно про них известно, минуты
ollchat --graph-findings books
```

### Проверка состояния: `--graph-doctor`

Одна команда отвечает на вопрос «всё ли в порядке с графом» и **называет команды**,
которыми это чинится. Видеокарту не занимает и разбиение не пересчитывает, но
**дешёвой не является**: замер 02.09.2026 на графе в 161 тыс. понятий — **44 секунды
и 1.5 ГБ памяти**. Столько стоит открыть граф целиком и обойти все куски коллекции
ради разбивки остатка по каталогам. Это команда, которую зовут осознанно, а не
в цикле.

Ход работы виден: в терминале строка перерисовывается на месте («открываю граф»,
«читаю разметку тем», затем полоса обхода кусков) и стирается перед отчётом, чтобы
он начинался с чистого места. Когда вывод перенаправлен в файл, каждая стадия
печатается отдельной строкой — стирать там нечего. **Ход идёт в поток ошибок**,
поэтому сам отчёт остаётся пригодным для разбора скриптом:

```bash
ollchat --graph-doctor books
```

```
коллекция books · граф
  понятий 161239, связей 820760, упоминаний 1065498
  разобрано кусков 158535 из 464767 (34%), осталось 306232
    с понятиями 156376, пустых 2106, пропущено 53
  векторы понятий: посчитаны все 161239 (bge-m3)
  векторы кусков: посчитаны все 464767
  темы: 34280 (нижнего уровня 32799), с описанием 4391 из 6496 кандидатов
    понятий вне тем: 7733 (4%) — обзор тем их не видит

что сделать:
  1. разобрать оставшееся — по каталогу за раз:
     ollchat --graph-build books --graph-folder /Coding   (116229 кусков)
     ollchat --graph-build books --graph-folder /DevOps   (67359 кусков)
     ollchat --graph-build books --graph-folder /OS   (45845 кусков)
     … и ещё 4 каталога
     разбор — единственный шаг, который нельзя доделать задним числом дёшево
  2. ollchat --graph-summaries books
     описать темы без описания — без него обзор знает тему по имени, но не
     по содержанию (карта)
```

**`--graph-folder` — это папка библиотеки, а не место графа.** Граф лежит рядом
с коллекцией, и путь к нему берётся из настроек; указывать его не нужно и негде.
Ключ отбирает **книги**: собрать граф по `/AI`, потом по `/Infosec`, а не всю
библиотеку разом. Отбор идёт по вхождению строки в путь книги, поэтому годится
и `/AI`, и `/Coding/Go`. Доктор называет настоящие каталоги вашей библиотеки
с числом неразобранных кусков — их не надо вспоминать и не надо смотреть на диске.

**Главная строка здесь — «понятий вне тем».** Разметка тем считается по составу
графа на момент запуска, и всё, что добавилось позже, не входит ни в одну тему:
`graph_overview` таких понятий не видит и об этом не говорит. Замер 02.09.2026:
101 тысяча понятий из 161 оказалась вне тем — обзор работал по трети графа,
и заметить это по одной доле «61% тем перекроилось бы» было нельзя.

Пересчёт советуется, когда вне тем оказалась **десятая часть понятий и больше**.
Ниже порога он стоит дороже пользы: сама разметка секундная, но следом идут
описания тем, а это часы карты.

Проверка состояния **самой коллекции** — книги, сканы, повторы — делается
отдельной командой `--kb-doctor`: у книг и у графа разные болезни.

### Сверка доктора: `ollscripts/graphdoctorcheck.py`

Доктор — это суждение о состоянии, и верить ему на слово не надо. Рядом лежит
скрипт, считающий те же числа **независимым путём**: он читает сырые файлы графа
сам, не трогая ни строчки кода программы, — двоичные записи по 24 и 12 байт,
`entities.jsonl` построчно, паспорта векторов отдельно.

```bash
ollscripts/graphdoctorcheck.py           # коллекция books по умолчанию
ollscripts/graphdoctorcheck.py мойкорпус
```

Сверка 02.09.2026 сошлась по всем одиннадцати числам: понятия, связи, упоминания,
разобранные куски и их разбивка на «с понятиями / пусто / пропущено», темы и темы
нижнего уровня, кандидаты на описание и описанные, понятия вне тем, векторы понятий
и векторы кусков.

**Чего сверка не доказывает.** Оба пути читают одни и те же файлы: повреждённый
файл они прочтут согласованно. Проверяется верность **толкования**, а не сохранность
данных.

**Одна ловушка, которую стоит помнить.** Совпадение числа понятий может оказаться
пустым: программа считает через свои счётчики, скрипт — вычитая склеенных двойников.
Если склеек нет, оба пути сойдутся, ничего не проверив. В нашем графе 1263 склейки,
и ни одна не удаляет узел (`drop`), поэтому согласие настоящее. В новом корпусе это
стоит проверить заново: `grep -c drop merges.jsonl`.

Лишние проверки графу не вредят: он стоит десятков часов карты, и любое молчаливое
расхождение здесь дороже часа, потраченного на сверку.

### Обновление карты тем: когда граф подрос

Шаги 1–6 выше — первое построение. Дальше граф растёт, и карта тем от него отстаёт:
разбиение считалось по прежнему составу и новых понятий не знает вовсе. Порядок
обновления такой:

```bash
# 1. Стоит ли вообще пересчитывать — процессор, секунды
ollchat --graph-drift books

# 2. Разбиение заново; описания похожих тем переносятся, а не считаются заново
ollchat --graph-communities books

# 3. Описания новых и перекроившихся тем — карта
ollchat --graph-summaries books

# 4. Разборы крупных тем — карта
ollchat --graph-findings books
```

`--graph-drift` ничего не меняет: он строит разбиение **в памяти** и сравнивает
с нынешним. Его вывод и есть основание решать. Замер 02.09.2026 на нашей библиотеке:

```
понятий сейчас 161239, на момент разбиения 62805 (+98434)
связей   820760, на момент разбиения 227064 (+593696)
понятий вне размеченных тем: 101012
описанных тем: 2590 · осталось бы почти как есть: 1006 (39%) · перекроилось бы: 1584
пора пересчитывать: перекроилось бы 61% тем
```

**Число «понятий вне размеченных тем» важнее доли перекроившихся.** 101 тысяча
из 161 — это 63% графа, которого обзор тем не видел вовсе: `graph_overview` работал
по трети, и молча.

Что дал пересчёт на этих числах (02.09.2026, граф в 161 тыс. понятий и 821 тыс. связей):

| шаг | сколько | время |
|---|---|---|
| разбиение | 34 280 тем (32 799 нижнего уровня, 1 481 верхнего) | 48 секунд, процессор |
| перенос описаний | 910 тем получили прежнее описание даром | входит в те же 48 секунд |
| описания | 6 496 тем-кандидатов (уровень 0, не меньше пяти понятий) | около полутора часов карты |
| разборы | считаются только для крупных и высоко оценённых | десятки минут |

Порог переноса описания задаётся `--graph-communities-carry` (по умолчанию 0.7 —
совпадение состава на 70%), а `--graph-communities-fresh` считает начисто, ничего
не перенося.

**Векторы понятий пересчитывать не нужно**: они привязаны к именам, а не к темам.
Но новые понятия, появившиеся после последней сборки, векторов не имеют — их
досчитывает `--graph-embed books` хвостом, и в ночном сценарии это делается само.

**Шаг 6 отвечает на другой вопрос, чем резюме.** Резюме темы говорит, **о чём** она.
Разбор (`--graph-findings`) — **что именно про неё известно**: три-семь выводов, каждый
с пояснением. Это пятый раздел отчёта о сообществе в MS GraphRAG.

Делается он не для всех тем и показывается не в обзоре, и обе оговорки — про цену.
Замер: резюме темы стоит в среднем 216 токенов, все 2 590 тем обошлись в 35 минут карты.
Разбор в нашем исполнении — 581 токен, то есть **дороже в 2.7 раза**, а не в 6–15,
как оценивалось заранее: книга просит выводы «с несколькими абзацами пояснения»,
а наш промпт — по 2–4 предложения. Прогон 337 тем занял 22 минуты. Поэтому
он считается только для крупных тем с высокой оценкой — по нынешнему графу это 337 тем
из 2 590, минуты вместо часов. Сколько их у вас, скажет `--graph-findings-dry`,
не занимая карту.

Показывается разбор по запросу: обзор из пяти тем укладывается в 1.0–1.5 тыс. токенов,
а с разборами занял бы 7–15 тыс. — половину окна, нужного самим книгам и ответу. Обзор
даёт номера тем, а подробности берутся инструментом `graph_topic` — тогда, когда нужны.

**Шаг 5 — про дверь, а не про комнату.** Без него вопрос попадает в граф только
по написанию: слова вопроса сравниваются с именами понятий. Замер на двенадцати живых
русских вопросах показал два промаха, и оба раза знание в графе было — не работал вход:
«чем перераниж**ировать** найденные куски» не находило ничего, а «перераниж**ирование**»
находило `reranking`; «выявление сообществ» не находило, а `community detection` находило.
После счёта векторов — двенадцать попаданий из двенадцати.

Точное написание при этом остаётся главным: понятие, найденное по слову вопроса, стоит
выше найденного по смыслу, а смысловых добавляется не больше половины списка. Векторы
считаются по именам вместе с синонимами, поэтому одно понятие оказывается разом
и в русском, и в английском углу пространства. После каждой докатки графа их надо
пересчитать: у новых понятий векторов нет.

**Шаг 4 нужен не всегда, но объяснить его стоит.** Резюме тем пишутся быстрой моделью
(`graph.summary_model`), и у неё есть слабость: бессвязному набору понятий она охотно
придумывает связное название и ставит высокую оценку — а обзор тем отбирает темы как раз
по оценке, и пустышка попадает в него как настоящая. Поймать это самой моделью нельзя.
Ловится устройством графа: у бессвязного набора связи чаще уходят наружу, чем остаются
внутри. `--graph-recheck` берёт полсотни самых рыхлых тем и передоописывает их моделью
извлечения — той, что честнее и медленнее. Замер: 4.5 минуты на 50 тем, из них одна
оказалась настоящей пустышкой (оценка упала с 8 до 3). Шире охват — 
`--graph-recheck-count 200`.

**Куски, помеченные пустыми.** Модель читает кусок и иногда не находит в нём ничего —
такой кусок помечается пустым и второй раз не берётся. Причин у пустоты две: одни куски
пусты по-настоящему (титульные листы, оглавления, страницы из одних формул), другие
модель просто пропустила. Книги советуют повторный проход именно из-за вторых:
«additional extraction passes on the same document, leads to more entity references
being detected» (*Essential GraphRAG*, 2025, стр. 111).

`--graph-redo-empty` берёт такие куски заново. Ключ нужен не столько ради самих кусков,
сколько ради ответа на вопрос: если второй проход выдаёт понятия из половины пустых —
значит первый теряет много, и повторные проходы по всей библиотеке окупают свои часы.
Если почти ничего — значит пустые честно пусты, и тратить на них время не стоит.

**Цена, которую надо знать до запуска.** Извлечение — один запрос модели на каждый
кусок. Замер: 0.27 куска/с, то есть 22 тысячи кусков — это **22 часа работы видеокарты**.
Ускорить числом потоков нельзя: Ollama отказывает архитектуре модели извлечения
в параллельных запросах (в журнале службы — `model architecture does not currently
support parallel requests`), и `--graph-workers` на ней ничего не меняет. Поэтому граф собирается каталогами (`--graph-folder`),
а не всей библиотекой разом, и запускается сознательно.

Докатка есть: прерванная сборка продолжается той же командой с места обрыва.

Проверить, что вышло:

```
/graph status books        понятия, связи, охват
/graph communities books   темы с описаниями
/graph check books         тот же доктор, что --graph-doctor: покрытие, векторы, промпт, темы, советы
```

### Графом можно пользоваться, пока он строится

Ждать конца сборки не нужно. Файлы графа — журналы с дозаписью: сборщик берёт признак
работы, а читатели его не берут и просто видят текущее состояние. Инструменты открывают
граф на каждый запрос заново, поэтому каждый ответ — свежий срез. Отставание до полусотни
кусков: запись сбрасывается на диск пачками, а не после каждого куска.

| Инструмент | Видит то, что разобрано только что? |
|---|---|
| `kb_search` — поиск по книгам | **да**, сразу после индексации книги |
| `graph_search`, `graph_entity`, `graph_path` | **да**, по мере разбора |
| `graph_overview` — обзор тем | **нет**, до пересчёта разбиения |

**Почему обзор отстаёт.** Разбиение на темы считается по графу и лежит отдельным файлом.
Новые понятия не входят ни в одну тему, пока не запущено `--graph-communities`, а описания
к новым темам — пока не запущено `--graph-summaries`. Обзор в этом случае честно отвечает
«понятия вопроса нашлись, но ни одно не попало в размеченные темы», а не молчит и не врёт.

Пересчитывать темы посреди сборки бессмысленно: через несколько часов придётся повторять.
Это делается после её окончания.

**Что при этом стоит помнить.** «В графе этого нет» во время сборки не означает
«в книгах об этом не пишут». Инструменты говорят это прямо — под каждой выдачей стоит
приписка вида «граф собран по 12% библиотеки: если понятия здесь нет, оно может быть
в неразобранных книгах — поищи kb_search».

Живой пример 26.08.2026: понятие `community hierarchy` («иерархия сообществ») пришло
из книги, разобранной той же ночью, и находилось поиском по графу через несколько часов
после разбора — а в обзор тем не попадало, потому что разбиение считалось днём раньше.

## Шаг 9. Перенести на другую машину

```
/graph pack books.tar books
```

Пакуется **вся коллекция вместе с графом**: граф ссылается на куски, которых без
коллекции нет. Абсолютных путей внутри нет ни одного, поэтому распакованная в любой
каталог коллекция открывается и ищет **без пересборки** — проверено переносом.

## Что во что упирается

| Действие | Команда | Чем считается | Порядок времени |
|---|---|---|---|
| Индексация книг | `--kb-index` | процессор | секунды на книгу |
| Смыслы по кускам | `--kb-embed` | видеокарта | минуты на тысячи кусков |
| Граф: извлечение | `--graph-build` | видеокарта | **часы и сутки** |
| Граф: разбиение на темы | `--graph-communities` | **процессор**, модель не нужна | секунды |
| Граф: **пора ли пересчитывать темы** | `--graph-drift` | **процессор**, модель не нужна | секунды |
| Граф: **что не в порядке и чем чинить** | `--graph-doctor` | **процессор**, модель не нужна | 44 с и 1.5 ГБ на 161 тыс. понятий |
| Граф: описания тем | `--graph-summaries` | видеокарта | 35 мин на 2 590 тем |
| Граф: разбор тем | `--graph-findings` | видеокарта | 22 мин на 337 тем |
| Граф: векторы понятий | `--graph-embed` | видеокарта | 20 мин на 63 тыс. понятий |
| Граф: проверка рыхлых тем | `--graph-recheck` | видеокарта | 4.5 мин на 50 тем |
| Уплотнение коллекции | `--kb-merge` | диск | минуты |

Из таблицы видно главное: **дорого только то, что зовёт модель.** Разбиение на темы
и проверка расхождения считаются на обычном процессоре за секунды — их можно запускать
сколько угодно и когда угодно.

## Сколько осталось по каталогу

Граф собирается каталогами, и вопрос «сколько ещё» встаёт перед каждым. Отвечать
на него оценкой нельзя: книги разной толщины, и среднее по библиотеке врёт. Замер
27.08.2026: каталог оценивался по 1 240 кусков на книгу, а в книгах по информационной
безопасности оказалось 1 750 — срок вырос с четырёх часов до восьми.

Ключ `--graph-folder` работает не только у сборки, но и у состояния:

```
$ ollchat --graph-status books --graph-folder /Infosec/
books: понятий 71998, связей 263564, упоминаний 343302
  разобрано кусков 50890 из 302211 (осталось 251321)
  из них с понятиями 50034, пустых 852, пропущено 4
  модель извлечения: qwen3.8:latest
  каталог /Infosec/: кусков 8764, разобрано 6500, осталось 2264 (74%)
  идёт сборка
```

Считать можно **во время сборки** — состояние читает те же файлы, ничего не занимая.
Умножив остаток на замеренную скорость (0.29 куска/с на нашем стенде), получаем срок
числом, а не на глаз.

Если каталог написан с ошибкой, команда скажет прямо — «кусков не нашлось, проверьте
написание пути», а не покажет ноль как результат.

## Когда пересчитывать темы

Разбиение считается за секунды, но после него **приходится заново описывать всё**:
названия, резюме, оценки и разборы к новому разбиению не переносятся. По нынешнему
графу это 35 минут на резюме, 22 на разборы и 20 на векторы понятий — полтора часа
карты за секундный пересчёт.

Поэтому пересчитывать надо **по накоплению, а не по событию**: одна доложенная книга —
не повод.

**Что при этом не ломается.** Поиск по графу, карточка понятия и путь между понятиями
о разбиении не знают вовсе — новые понятия ищутся сразу после сборки. Обзор тем тоже
не слепнет: понятие, не попавшее в размеченные темы, приводит к теме через соседей.
Отстаёт только **карта тем** — новые понятия не образуют собственных тем.

**Как узнать, пора ли.** Не на глаз и не по росту графа: рост в стороне от размеченных
тем не меняет ничего, а рост внутри них перекраивает всё. `--graph-drift` строит новое
разбиение **в памяти**, ничего не сохраняя, и сравнивает с нынешним:

```
$ ollchat --graph-drift books --graph-drift-show 3
коллекция books
  понятий сейчас 71538, на момент разбиения 62805 (+8733)
  связей сейчас 261674, на момент разбиения 227064 (+34610)
  понятий вне размеченных тем: 11311

  описанных тем: 2590
  осталось бы почти как есть: 2293 (89%)
  перекроилось бы: 297
  (темой «почти как есть» считается совпадение состава от 70%)

можно подождать: перекроилось бы 11% тем

пересчёт сотрёт описания у всех 2590 тем: заново это резюме (~35 мин карты),
разборы (~22 мин) и векторы понятий (~20 мин)

сильнее всего перекроились бы:
  совпадение 3% · понятий 7 · разошлись бы на 4 части · Анализ угроз с помощью urlscan.io
```

Ключ `--graph-drift-show N` показывает темы, которые перекроились бы сильнее всего, —
проценты говорят «сколько», а понять «почему» можно, только увидев, во что именно
рассыпалась тема. `--graph-drift-similarity` меняет порог, при котором тема считается
прежней (по умолчанию 0.7).

Пороги в приговоре («рано», «можно подождать», «пора») — правило большого пальца,
а не замер: измерить, при каком расхождении карта тем начинает врать, можно только
прогоном вопросов до и после пересчёта. Команда даёт числа, решение остаётся за человеком.

## Как ollchat отвечает на вопрос

Поиск по книгам и граф понятий работают не по очереди и не вместо друг друга, а одним
конвейером. Вот весь путь вопроса:

```
вопрос
  │
  ├─ 1. привратник ────── распоряжение о коде? вопрос не о библиотеке? → ничего не подмешивать
  │
  ├─ 2. вход в граф ───── понятия по словам + понятия по смыслу (вектор вопроса)
  │        ├─ связи найденных понятий  ──────────────► карта понятий
  │        └─ имена и синонимы понятий ──┐
  │                                      │
  ├─ 3. запрос к книгам = вопрос + имена ┘
  │        ├─ поиск по словам (BM25) ── 200 кандидатов ─┐
  │        └─ поиск по смыслу ───────── 200 кандидатов ─┤ слияние по местам
  │                                                     ▼
  │                                        доводка: не больше N из книги,
  │                                        без соседних кусков и повторов
  │                                                     │
  │                              (если включена вторая ступень —
  │                               кросс-энкодер переставляет верхушку)
  │                                                     │
  └─ 4. модели уходит: [карта понятий] + [граница] + [выдержки из книг] +
                       [требование ссылаться] + [вопрос]
```

**Граница вокруг чужого текста.** Перед выдержками стоит строка о том, что внутри —
данные для чтения, а не указания. Выдержка из книги попадает в промпт наравне
с вопросом человека, и строка «игнорируй прежние указания», написанная в скачанном
откуда угодно PDF, для модели неотличима от вашей просьбы. Книги называют это
непрямым внедрением и ставят его опаснее прямого. Строка одна на весь блок, а не
перед каждой цитатой, и стоит **до** выдержек; требование ссылаться на книгу остаётся
**после** них, вплотную к вопросу — его место подобрано замером, и граница его
не сдвигает. Та же граница стоит и в выдаче `kb_search`.

**1. Привратник.** Подмешивание стоит контекста на каждом вопросе, включая «спасибо».
Поэтому сначала отсекаются распоряжения о коде («сделай коммит и запушь»), а затем вопрос
связывается с понятиями графа: не связался — не подмешивается ничего, ни карта, ни выдержки.

**2. Вход в граф.** Понятия ищутся двумя способами сразу: по словам вопроса (фразами
от трёх слов к одному, с учётом словоформ) и по смыслу — через вектор вопроса. Смысловых
понятий берётся не больше половины: смысловая близость ошибается чаще словесной. У найденных
понятий берутся связи — это и есть карта понятий, ответ на вопрос «как это связано с тем».

**3. Граф переводит вопрос на язык библиотеки.** К запросу к книгам дописываются имена
и синонимы найденных понятий. Именно поэтому вопрос «чем RAG отличается от дообучения»
приводит нужные страницы: граф знает, что «дообучение» — это fine-tuning, а вопрос
об этом не говорит.

**Ступень работает и у `kb_search`, и у подмешивания выдержек**, а не только
в замерном прогоне: моделям без инструментов выдержки и подмешиваются, и до 01.09.2026
им доставалась выдача одной ступени.

**4. Внутри книг два поиска идут параллельно.** Словесный (BM25) находит точные термины,
смысловой находит написанное другими словами и на другом языке. Каждый даёт свой список,
и списки сливаются **по местам, а не по очкам**: вес BM25 и косинус живут в разных шкалах,
и любая их сумма — подгонка под один корпус. Затем выдача доводится до читаемой: не больше
`kb.max_per_book` кусков из одной книги, без соседних кусков и без повторов одной цитаты.

**4а. Необязательная вторая ступень — переранжирование.** Первая ступень сравнивает вопрос
и кусок порознь: у каждого свой вектор. Кросс-энкодер читает их вместе одним текстом —
точнее, но настолько дороже, что годится только для верхушки. Замер на нашей библиотеке:
верный кусок поднимается с третьего места почти на первое (таблица ниже). Считает его
**отдельная служба** `llama-server` с ключом `--reranking` — Ollama кросс-энкодеры
не обслуживает; адрес в `kb.rerank_url`, пусто — ступени нет. Служба недоступна — выдача
остаётся от первой ступени, поиск не ломается.

**Служба обязана переживать перезагрузку.** Поднятая руками, она однажды
не вернётся, и заметить это нечем: при пустом `rerank_url` поиск просто работает
хуже, ничего не сообщая. Ровно так и случилось: с 30.08 по 02.09 вторая ступень
не работала нигде. Отсюда `--restart unless-stopped` в команде запуска контейнера
и проверка, что docker включён в автозапуск.

Замер на 457 вопросах (библиотека 406 книг, 465 тыс. кусков):

| режим | recall@10 | MRR | nDCG | ср. место | мимо |
|---|---|---|---|---|---|
| слова | 0.129 | 0.092 | 0.101 | 2.1 | 398 |
| векторы | 0.344 | 0.231 | 0.259 | 2.4 | 300 |
| слияние | 0.346 | 0.217 | 0.248 | 2.5 | 299 |
| **слияние + вторая ступень** | **0.365** | **0.300** | **0.317** | **1.6** | **290** |

**5. Модели уходит карта понятий, а выдержки — по надобности.** Модель с инструментами
возьмёт цитаты сама через `kb_search`, когда они понадобятся. Модели без инструментов
выдержки кладутся сразу: дозапросить она не сможет. Под ответом видна серая строка о том,
что реально ушло вместе с вопросом.

Вектор вопроса считается на сервере Ollama моделью `bge-m3` — **0.44 секунды**, единственное
обращение к видеокарте на всём пути; остальное (открытие графа, оба поиска, слияние) считает
процессор. Подробный разбор с числами — в документации проекта, «Как устроен поиск».

## Какая модель за что отвечает

В работе участвуют четыре модели, и каждая выбрана по своей причине. Одна на всё
не годится: задачи разной природы, и то, что решает выбор в одной, в другой не значит
ничего.

**Важность темы.** У каждой темы есть оценка от 1 до 10 — насколько она нужна для
понимания предмета. `graph_overview` показывает её («важность 9 из 10») и не показывает
темы с оценкой ниже `graph.min_rating` (по умолчанию пять): бессвязный набор понятий,
которому модель честно поставила тройку, в обзор не попадает. Так же отбирает темы
MS GraphRAG. Темы, которым резюме ещё не написано, порог не отсекает.

**Порядок связей в выдаче.** Связи идут так, как подтверждены книгами: чем чаще о паре
понятий написано, тем выше она стоит. Настройка `graph.neighbor_sense_weight` включает
пересортировку с оглядкой на вопрос — связь, близкая к нему по смыслу, поднимается наверх.
**По умолчанию она выключена (0), и это результат замера, а не осторожность:** сто вопросов,
слепое судейство в оба порядка — выдача без пересортировки победила 18:5 при вероятности
случайного перекоса 0.011. Пересортировка выбивала конкретное и подтверждённое ради
близкого к теме вообще: `go vet` терял связь с `sync.Locker`, `Init function` — с `Unit tests`.
На другом наборе книг ответ может быть иным, поэтому настройка есть; осмысленное значение
для проб — 1.5, меньше единицы бесполезно.

**Открытый граф между вызовами.** Первое обращение к графу читает его с диска: на коллекции
из 750 тысяч понятий это 11.7 секунды и гигабайт памяти. Дальше граф остаётся открытым,
и следующие вопросы отвечаются за полсекунды — в двадцать раз быстрее. Служба `ollmcp`
держит его час, интерфейс — пять минут, после чего память освобождается. Если граф в это
время дособирается другим процессом, изменение файлов замечается и граф перечитывается.

| Роль | Модель | Настройка | Почему именно она |
|---|---|---|---|
| Чат и агентный режим | `qwen3.8:latest` | `[[servers]] model` | Умеет инструменты, рассуждения и зрение; втрое легче `qwen3.5:122b` при близком качестве |
| Векторы для смыслового поиска | `bge-m3` | `kb.embed_model` | Многоязычная: русский вопрос находит английский текст. Обычная чат-модель тут не годится — нужна эмбеддинговая |
| Извлечение понятий и связей | `qwen3.8:latest` | `graph.model` | Даёт русские синонимы у 51% английских понятий против 3% у glm. Синонимами и связывается русский вопрос с английской книгой |
| Описание тем графа | `glm-4.7-flash:q8_0` | `graph.summary_model` | Умеет параллельные запросы: 2.5x на четырёх слотах. 51 минута против 3.5 часов на 2 590 темах |

**Почему извлечение и описание — разные модели.** При извлечении важен словарь: найдёт ли
модель русское слово к английскому термину. Без этого граф собран из английских понятий,
а спрашивают его по-русски, и связи не находится. При описании темы модель просто пишет
связный абзац по-русски — это умеют обе, и здесь выигрывает скорость.

**Чем платим за скорость.** Быстрая модель охотнее сочиняет: бессвязному набору понятий
она придумывает правдоподобное название и ставит высокую оценку. Замер на одинаковом
входе: `qwen3.8` написала «бессвязный набор терминов… белый медведь, скрапбукинг»
и поставила 2, `glm` — «Искусственный интеллект и тестирование», оценка 8. Поэтому
существует шаг `--graph-recheck`: он передоописывает самые рыхлые темы обратно моделью
извлечения. На 27 темах из 28 модели сходятся в пределах балла — расхождения ровно там,
где кластер и правда мусорный.

## Многопоточность: почему четыре потока бывают одним

Клиент может слать сколько угодно запросов разом — сколько из них будут считаться
одновременно, решает сервер. И увидеть это со стороны клиента нельзя: запросы уходят
и возвращаются, просто медленно.

Два слоя, и оба надо проверять.

**Настройка сервера.** Число слотов задаёт переменная `OLLAMA_NUM_PARALLEL`. Если она
не задана, сервер держит один слот и обрабатывает запросы по очереди. Задаётся в юните
службы и требует перезапуска:

```bash
sudo mkdir -p /etc/systemd/system/ollama.service.d
sudo tee -a /etc/systemd/system/ollama.service.d/override.conf <<'EOF'
[Service]
Environment="OLLAMA_NUM_PARALLEL=4"
EOF
sudo systemctl daemon-reload && sudo systemctl restart ollama
```

Слоты стоят памяти: каждый держит свой контекст, поэтому вчетверо больше слотов — вчетверо
больше памяти под KV-кэш.

**Архитектура модели.** Даже при выставленной переменной Ollama может отказать: для части
архитектур параллельная обработка не поддерживается, и число слотов сводится к единице.
Об этом она честно пишет в свой журнал на каждый запрос:

```
WARN sched.go:509 msg="model architecture does not currently support parallel requests" architecture=qwen35
```

Именно так ведёт себя `qwen3.8`, которой собирается граф. Поэтому `--graph-workers`
на извлечении ничего не меняет, и 22 часа на каталог AI — не потерянное время,
а потолок стенда.

### Как проверить за две минуты

В `ollscripts/` лежит скрипт `ollparallelcheck.sh`. Он шлёт один запрос, потом несколько
разом и сравнивает:

```bash
./ollscripts/ollparallelcheck.sh -m qwen3.8:latest -u http://ollama.example:11434
./ollscripts/ollparallelcheck.sh -m glm-4.7-flash:q8_0 -n 8
```

Ключи: `-m` модель (обязательно), `-u` адрес сервера, `-n` сколько запросов слать разом
(по умолчанию 4), `-p` длина ответа в токенах. Код возврата — 0 параллельность есть,
1 очередь, 2 проверить не удалось; годится для скриптов.

Что он показывает:

```
один запрос:      1.2 с (лучшее из двух)
4 разом:          1.9 с (каждый 1.7–1.9 с)
ускорение:        2.49x из 4 возможных
разброс времён:   1.10x (в очереди стремится к 4, при параллельности к 1)

ВЫВОД: сервер обрабатывает запросы к этой модели параллельно.
```

**Разброс времён важнее ускорения.** В очереди запросы возвращаются лесенкой: первый
за время одиночного, последний — за четыре таких. При настоящей параллельности все
заканчиваются почти вместе. Замеры на стенде: очередь давала ускорение 0.96–1.47 при разбросе 3.1–3.2,
параллельность — 2.49–2.67 при разбросе 1.10. По одному ускорению вердикт уже ошибался:
на очереди он однажды показал 1.47 при пороге 1.5. Поэтому смотрят на оба числа.

Прогрев перед замером обязателен и делается сам: первый запрос грузит модель в память,
и его время к делу не относится.

Если сервер ставит запросы в очередь, скрипт подскажет, где искать причину. Журнал он
читает **только у своей же службы** — сверяя порт: `localhost:11111` сплошь и рядом
оказывается туннелем ssh на другую машину, и журнал местной службы рассказывал бы
про совсем другой сервер.

## Как смысл превращается в числа

Смысловой поиск держится на одном свойстве модели `bge-m3`: **она кладёт смысл выше
языка**. Вот замер, который это показывает нагляднее любого объяснения.

Берём вопросы, считаем их векторы и меряем близость (косинус: единица — одно и то же
направление, ноль — ничего общего):

| близость | пара |
|---|---|
| **0.915** | «как работает сборщик мусора в Go» ↔ «how does the garbage collector work in Go» |
| **0.921** | «как работает сборщик мусора в Go» ↔ «как устроена сборка мусора в Go» |
| 0.904 | «как настроить сеть в Kubernetes» ↔ «how to configure networking in Kubernetes» |
| 0.411 | два **разных** вопроса, оба по-русски |
| 0.374 | два разных вопроса, русский ↔ английский |
| 0.304 | вопрос про Go ↔ рецепт борща |

**Перевод и пересказ различаются на шесть тысячных.** Для модели «как работает сборщик
мусора» и «how does the garbage collector work» — практически одна мысль, а вот другой
вопрос на том же языке уходит вдвое дальше. Именно поэтому русский вопрос находит
английскую книгу.

### Две вещи, которые из этого следуют

**У близости высокий пол.** Совсем чужие тексты дают не ноль, а 0.26–0.41. Поэтому
отсечка «показывать всё, что выше такого-то числа» не работает: у заведомо чужой пары
близость бывает 0.565, а у осмысленной — 0.576. Отбор в графе поэтому **относительный**:
не «выше числа», а «выше середины собственной верхушки».

**Вектор помогает найти, но не склеивает.** Если при извлечении понятий модель завела
«сборщик мусора» и `Garbage collection` **двумя разными понятиями**, у каждого окажется
своя половина связей. Смысловой поиск найдёт одно из них — и покажет половину знания.
Склеивают их синонимы, которые модель извлечения приписывает понятию, а не векторы.

Отсюда и требование к модели извлечения: она должна не только находить понятия, но и
**давать им другие написания**. Замер двух моделей на одинаковых кусках — в индексе
знаний проекта, раздел про выбор модели извлечения.

### `--graph-find` и `/search` — один и тот же поиск

С 02.09.2026 команда `ollchat --graph-find "вопрос"` выполняет **ровно то же**,
что `/search` в интерфейсе, и тем же кодом (`internal/find`): вход в граф,
поиск по книгам словами и смыслом, слияние по местам, `kb.max_per_book`,
вторая ступень, оговорка «искал только по словам, потому что…».

До этого команда звала граф напрямую и печатала лишь **куски-подтверждения**
найденных понятий. Раздел назывался «Подтверждения из книг», и со стороны это
выглядело как плохой поиск по книгам: на вопросе, где граф цеплялся за неудачное
понятие, выдача оказывалась не по делу — при том что тот же вопрос через
`kb_search` находил нужные страницы сразу. Ни `max_per_book`, ни второй ступени
на том пути не было вовсе, поэтому пять выдержек из шести приходили из одной книги.

Заодно обе стороны получили то, что было только у одной:

- в `/search` появилась **выдержка под каждой связью** — фраза из книги, которая
  эту связь подтверждает (раньше её видела только командная строка);
- в `/search` появилась оговорка **«граф собран по N% библиотеки»** с числами —
  без неё «ничего не нашлось» читается как «в книгах об этом не пишут»;
- `--graph-json` теперь отдаёт полную выдачу поиска (понятия, связи, выдержки
  и оговорки), а не только результат обхода графа.

## Двойники в графе: `--graph-resolve`

В графе «сборщик мусора» и `Garbage collection` — **два разных узла**, и у каждого своя
половина связей. Узлы склеиваются только по точному совпадению имени, а перевод,
множественное число и другой апостроф совпадением не считаются.

Команда показывает таких двойников. **Она ничего не меняет** — только печатает.

```bash
ollchat --graph-resolve books                    # по синонимам от модели, доли секунды
ollchat --graph-resolve books --graph-resolve-cross   # только через границу алфавита
ollchat --graph-resolve books --graph-resolve-full    # все пары подряд, минуты процессора
ollchat --graph-resolve books --graph-resolve-out пары.tsv   # весь список в файл
```

Ещё ключи: `--graph-resolve-min-cos` (по умолчанию 0.90), `--graph-resolve-show`
(сколько строк на экран, по умолчанию 40) и `--graph-resolve-min-cos-mutual`
(по умолчанию 0.80) — см. ниже про взаимный синоним.

### Взаимный синоним: почему у него порог ниже

Модель извлечения записывает синонимы каждому понятию. Синоним, названный
**с обеих сторон** (A назвал B, и B назвал A), — это два независимых суждения,
сделанных на разных кусках, а часто и на разных книгах. Замер по всему графу:

| пары | сколько | медиана близости | ≥0.90 | ≥0.80 |
|---|---|---|---|---|
| взаимные | 5 978 | 0.856 | 32% | 69% |
| односторонние | 36 188 | 0.782 | 11% | 44% |
| случайные | 50 000 | 0.425 | 0.00% | 0.00% |

Случайная пара понятий не даёт близости 0.80 **ни разу из пятидесяти тысяч**.
Поэтому для взаимных пар порог опущен до 0.80: при общем пороге 0.90 из разбора
выпадали `горутина ↔ goroutine` (0.857) и `канал ↔ channels` (0.846) — то есть
как раз главные двойники библиотеки. На нашем графе это добавило 2373 пары
к прежним 6652.

**Близость по-прежнему не решает.** Она только отбирает кандидатов: у пары
`Mistral-7B-Instruct-v0.3 ↔ v0.1` близость 0.967, а это разные модели.

### Как читать выдачу

```
  близость  признаки           общих  книги    понятия
     0.997  ~синоним тип≠          7  20/9    REST API ← RESTful API
     0.992  синоним язык           0  13/2    cache ← кэш
     0.971  ~синоним ЦИФРЫ         0   1/1    Mistral-7B-Instruct-v0.1 ↔ v0.3
     0.857  ВЗАИМНЫЙ язык          1  16/54   goroutine ← горутина
```

| признак | что значит |
|---|---|
| `синоним` | модель извлечения сама записала одно имя в синонимы другого |
| `~синоним` | то же, но написание для поиска негодное (разное число слов и т. п.) |
| `тип≠` | у понятий разные типы |
| `ЦИФРЫ` | имена различаются **только цифрами** — почти наверняка **разные** вещи |
| `язык` | пара через границу алфавита |

Стрелка указывает, кого стоило бы оставить главным: у кого больше книг, при равенстве —
упоминаний. Столбец `общих` — сколько соседей по графу у пары общие; прочерк значит
«сравнивать нечего», а не «ноль».

### Две ловушки, обе замеренные

**Порогом близости обойтись нельзя.** `Mistral-7B-Instruct-v0.1` и `v0.3` дают 0.971,
`load_in_4bit` и `load_in_8bit` — 0.929, `2D U-Net architecture` и `3D U-Net` — 0.932.
Это разные вещи, а близость у них выше, чем у многих настоящих двойников. Для того
и метка `ЦИФРЫ`: в прогоне 27.08.2026 все 36 помеченных пар были бы ошибочной склейкой.

**Общим соседям по графу верить нельзя.** Замерено: у **67%** кандидатов общих соседей
нет вовсе — граф разрежен, а двойники приходят из разных книг. Столбец показывается
как справка и в отбор не входит.

### Сколько это стоит

Прогон 27.08.2026 на 76 182 понятиях (62 805 с векторами), 12 ядер:

| | пар | время |
|---|---|---|
| по синонимам от модели | 2 548 | 0.15 с |
| полный перебор (два триллиона умножений) | 8 153 | 4 мин 18 с |

Видеокарта не нужна: векторы уже посчитаны, счёт идёт на процессоре. Полный перебор
находит то, чего синонимы не дают вовсе — `advantage estimate` ↔ `advantage estimation`,
`community summarization` ↔ `community summarisation`, «среднеквадратичная ошибка» ↔
«среднеквадратическая ошибка».

**Понятия без вектора в разбор не попадают.** Граф растёт заходами, и хвост без векторов
есть почти всегда — команда сама скажет, сколько их и какой командой досчитать.

## Связи в выдаче отбираются по вопросу

У понятия десятки связей, а показывается пять. Раньше выбирались пять самых
подтверждённых — то есть тех, о которых в книгах пишут чаще всего, независимо
от того, о чём спросили. На вопрос про cookies наверх выходил
`cookie —часть→ FastAPI`, вытесняя `SameSite` и `same-origin policy`.

Теперь пять выбираются с оглядкой на вопрос:

```
вопрос: как защитить cookie от кражи

было:   HTTP, session_id, secure, HttpOnly, FastAPI
стало:  Cookie Security, secure, session_id, host-only, cookie domain
```

Насколько это важно: замер по 61 понятию из живых выдач — **медиана 34 связи
на понятие при показе пяти**, у `LLM` их 4 421, у `prompt injection` — 186.
Скрыто 96% связей.

**Как выбираются.** Два списка — по числу подтверждений и по близости к вопросу —
сливаются по местам (RRF), с большим весом у близости. Не по порогу близости:
абсолютная отсечка здесь проверена и отвергнута, у заведомо чужой пары близость
бывает выше, чем у осмысленной. Вес не выброшен: при равной уместности впереди
идёт связь, подтверждённая чаще.

**Нужна модель эмбеддингов.** Без неё выдача остаётся прежней, по весу, —
поиск не ломается. Заодно `--graph-find` из терминала научился считать вектор
вопроса: до этого смысловым входом пользовался только инструмент `graph_search`,
и человек, зовущий граф руками, получал заведомо худший поиск, чем модель.

## Выдержка под связью: `relation_snippet`

Строка «горутина —использует→ канал (подтверждений 48)» говорит, **что** связано,
но не говорит, **чем именно**. Под каждой связью печатается фраза из книги:

```
  горутина —использует→ канал (подтверждений 48)
      …Горутины обмениваются данными через каналы, и это основной способ связи…
```

Берётся она из того самого куска, которым связь подтверждена, — окном **вокруг
имени понятия**, а не с начала куска: начало часто попадает на середину чужой
мысли, а рядом с именем стоит ровно то предложение, ради которого связь
и извлекли.

Настройка — `relation_snippet` в разделе `[graph]`: `0` — умолчание (140 знаков),
отрицательное — не показывать вовсе. Выдержка стоит места в контексте модели,
поэтому на коротком окне её разумно выключить.

Печатается она там, где у отрисовки есть доступ к кускам: `graph_search`
и `graph_entity` у модели, `--graph-find` в терминале. В `/search` её нет
намеренно — там выдержки идут ниже одним общим списком, и цитаты не должны
дублироваться.

**Почему выдержка, а не пояснение от модели.** Модель извлечения возвращает
пояснение к каждой связи, но граф его не хранит. Добрать задним числом нельзя:
это повторный прогон по всем разобранным кускам — около 110 часов карты, — и, что
хуже, каталоги, разобранные позже, стали бы богаче разобранных раньше. Выдержка
даёт почти то же самое, работает на всём графе сразу и не стоит ни одного часа
карты.

## Склейка двойников: `--graph-merge`

Когда `--graph-resolve` показал двойников и решение принято, склейка делается так:

```bash
# посмотреть, что склеится, ничего не меняя
ollchat --graph-merge books --graph-merge-file verdicts.tsv --graph-merge-level strict --graph-merge-dry

# склеить
ollchat --graph-merge books --graph-merge-file verdicts.tsv --graph-merge-level strict

# посмотреть, что уже склеено
ollchat --graph-merge books

# снять всё и вернуть граф в прежний вид
ollchat --graph-merge books --graph-merge-drop
```

Уровни строгости `--graph-merge-level`:

| уровень | правило |
|---|---|
| `strict` | вердикт «ДА» + синоним от модели извлечения + близость ≥ 0.95 |
| `alias` | «ДА» + синоним |
| `vector` | «ДА» + близость ≥ 0.95 |
| `mixed` | «ДА» + любое из двух |
| `mutual` | «ДА» + **взаимный** синоним + близость ≥ 0.80 |
| `soft` | «ДА» + близость ≥ 0.92 |
| `all-yes` | любое «ДА» |

Пары, у которых имена различаются **только цифрами**, не склеиваются ни на одном
уровне: это разные версии одного и того же (`load_in_4bit` и `load_in_8bit`).

### Склейку можно отменить, и это главное её свойство

По смыслу склейка необратима: два понятия становятся одним. Поэтому решения
**не пишутся в реестр**, а лежат рядом отдельным журналом `merges.jsonl`
и надеваются на граф при чтении. Убрали файл — граф прежний.

Поглощённое понятие не исчезает бесследно: его имя и синонимы достаются
выжившему, так что прежнее написание по-прежнему находится. Связи и упоминания
обеих половин сходятся у одного узла — ради этого всё и делается.

### Отдельный порог для пар внутри одного языка

Ключ `--graph-merge-min-cos-same` задаёт **свой порог близости для пар, где оба
имени на одном языке**. Основание — замер: перевод и пересказ различаются
на шесть тысячных, то есть смена языка модели почти ничего не стоит, а смена
предмета уводит вдвое дальше. Поэтому «граф знаний» и `knowledge graph`
при близости 0.90 — почти наверняка одно и то же, а `Agentic systems`
и `Agentic AI Systems` при той же близости — скорее широкое и узкое.

```bash
ollchat --graph-merge books --graph-merge-file verdicts.tsv \
        --graph-merge-level alias --graph-merge-min-cos-same 0.92
```

### Что это дало на нашем графе

604 склейки уровня `strict`, замер на тридцати вопросах — спрашивали именем
той половины пары, что беднее книгами:

| показатель | до | после |
|---|---|---|
| книг-источников | 115 | **316** (+175%) |
| подтверждений связей | 175 | **901** (+415%) |
| связей | 105 | 143 (+36%) |
| цитат из книг | 143 | 178 (+24%) |

Книг стало больше **у 30 вопросов из 30**, ни одного ухудшения. Слепое сравнение
выдач моделью (в случайном порядке, без указания, какая какая) — **28 побед
«после», 0 «до», 2 ничьи**.

Наглядно на одном вопросе:

```
до:      virtual machines — упоминаний 39 в 8 книгах, 5 связей
после:   виртуальная машина — упоминаний 80 в 14 книгах,
         он же: virtual machine, virtual machines, ВМ
```

Затем ещё 659 склеек уровня `alias` с порогом 0.92 внутри языка — всего
поглощено **1 263** понятия. Замер на тридцати других вопросах: книг 137 → 326,
подтверждений 215 → 453, слепое сравнение **25 «после», 1 «до», 4 ничьи**.

**Чего склейка НЕ чинит.** Связей у понятия становится больше, а в выдаче
их по-прежнему пять. Единственный проигрыш замера — именно это: для вопроса
про `cookies` в верхнюю пятёрку вместо `SameSite` попал `FastAPI`. Связи
ранжируются по весу, а не по отношению к вопросу.

## Долить и сразу досчитать: `--kb-refresh`

Куски и смыслы устаревают по-разному, и это расхождение молчаливое: `--kb-sync`
добавляет куски, а смысловой поиск их не видит, пока не посчитаны векторы, —
**и не сообщает об этом**, он просто их не находит.

Одна команда вместо двух:

```bash
ollchat --kb-refresh projectdocs     # долить новое и сразу досчитать векторы(смыслы)
```

### Чем `--kb-refresh` отличается от `--kb-sync`

`--kb-refresh` — это **`--kb-sync` плюс счёт смыслов**. Первая половина у них общая,
буквально один и тот же код:

| | `--kb-sync` | `--kb-refresh` |
|---|---|---|
| пометить книги, пропавшие с диска | да | да |
| прочитать новые и изменившиеся книги | да | да |
| посчитать векторы(смыслы) новым кускам | **нет** | да |

Разница безобидна ровно до тех пор, пока смысловой поиск не включён. А если включён —
`--kb-sync` оставляет новые книги видимыми **только словесному поиску**, и никто об этом
не сообщает: выдача выглядит нормальной, просто часть библиотеки в неё не попадает.
Так 28.08.2026 набежало 15% кусков коллекции документации.

**Поэтому по умолчанию берите `--kb-refresh`.** `--kb-sync` остаётся для случая, когда
смыслы считать сейчас нечем: видеокарта занята сборкой графа, сервер эмбеддингов
недоступен, а куски нужны прямо сейчас. Тогда векторы досчитываются потом отдельной
командой `--kb-embed` — она берёт только то, чего ещё нет.

Смыслы считаются только новым кускам: покрытие всегда начальный отрезок, потому
что куски дописываются в конец. Поэтому доливка десятка файлов стоит секунды,
а не пересчёта всей коллекции.

Если смыслы не настроены (`kb.embed_model` пуст или `semantic = false`) — команда
просто доливает и молчит: словесный поиск работает и без них.

### Что видно, пока она идёт

Состав работы объявляется **до** её начала, а не после: доливка по большой библиотеке
идёт минутами, и человек, положивший книги в каталог, вправе сразу увидеть, что
программа нашла именно их.

```
к разбору 3 книги:
  · Go в действии 2024.txt
  · Kubernetes на практике 2025.txt
  · Linux изнутри 2023.txt

коллекция proba: добавлено книг 3
  + Kubernetes на практике 2025 · 2025 г. · кусков 27
  + Go в действии 2024 · 2024 г. · кусков 27
  + Linux изнутри 2023 · 2023 г. · кусков 27
всего: книг 3, кусков 81, термов 1118, на диске 0.1 МБ, за 0s
```

Оба списка печатаются **целиком**, без «и ещё N»: их читают глазами, сверяя с тем,
что клали в каталог, — обрезанный список для этого негоден.

Книга, которую нашли, но не смогли прочитать, попадает в итог отдельным числом
и не теряется молча:

```
коллекция proba: добавлено книг 0, пропущено 1
причины по каждой книге: ollchat --kb-doctor proba
```

## Первый вопрос долго молчит: модель грузится в память карты

Ollama держит модель в памяти ограниченное время и выгружает её. Первый вопрос после
запуска (или после перерыва) заставляет сервер прочитать веса с диска и перенести их
в видеопамять. На большой модели это десятки секунд, и всё это время `/api/chat`
не отдаёт **ни куска** ответа.

Со стороны это неотличимо от зависания: нажал Enter — и тишина. Разумная реакция —
нажать Ctrl+C, то есть отменить загрузку; следующий вопрос начнёт её заново, и так
по кругу.

Поэтому ollchat спрашивает сервер (`/api/ps`), что у него загружено, — и **сразу при
запуске**, не дожидаясь первого вопроса. Иначе ответ приходил бы уже посреди ожидания,
когда человек успел решить, что программа зависла: сам запрос идёт доли секунды, но эти
доли складываются с тем, что и так выглядит зависанием.

Если модели в памяти нет, об этом сказано ещё до того, как вы начали печатать:

```
△ Модели qwen3.5:122b сейчас нет в памяти сервера. Первый вопрос будет ждать, пока
  Ollama прочитает её веса с диска и перенесёт в видеопамять: на больших моделях это
  десятки секунд. Ответа всё это время не будет — это не зависание.
```

Проверка повторяется при смене сервера и модели: у другого сервера своя память карты,
а про новую модель прежний ответ не говорит ничего.

Пока загрузка идёт, в строке состояния стоит другое слово, со счётчиком:

```
safe · ctx ≈8.1k/32k ███░░░░░░░ 25% · ⣾ загружается в память карты… 42 с  Esc — прервать
```

Счётчик важен не меньше слова: неподвижная надпись сама по себе читается как зависание.

Если ожидание перевалило за четыре секунды, в ленте появляется пояснение — что именно
происходит и что программа не зависла. Раньше четырёх секунд его нет намеренно:
маленькая модель встаёт за пару секунд, и объяснение успело бы только замусорить ленту.
Дважды одно и то же не говорится: предупредили при запуске — посреди ожидания молчим,
а вот после того как модель побывала загруженной, о следующей выгрузке скажем снова.

**Настройка `general.startup_hints = "off"` гасит предупреждение при запуске** — это
строка на каждый пуск программы, ровно та, ради которой настройку и заводили.
Объяснение посреди настоящего ожидания она не трогает: там человек уже сидит и смотрит
в тишину, и это не совет, а ответ на вопрос «что происходит».

Как только приходит первый кусок ответа, надпись становится обычной — «думает…».
Первый кусок вернее любого опроса сервера: тот говорит, что было секунду назад,
а кусок — что происходит сейчас.

**Если сервер не ответил на `/api/ps`, программа молчит и пишет «думает…».** «Не знаю»
и «не загружена» — разные вещи, и показать «загружается» там, где просто оборвалась
сеть, значит соврать о причине ожидания.

## Проверка коллекции: `--kb-doctor`

Тихие потери — худшее, что может случиться с базой знаний: книга не прочиталась, скан не дал
текста, файл переехал, а поиск просто ничего не находит и объяснить это нечем. Доктор
превращает молчание в список:

```bash
ollchat --kb-doctor books        # одна коллекция
ollchat --kb-doctor all          # все
ollchat --kb-doctor books --kb-quick   # без сверки содержимого, быстрее
```

То же в диалоге — `/kb doctor`. Отчёт один и тот же: реализация общая, чтобы ответ не зависел
от того, откуда спросили.

**Изменившиеся после индексации файлы — отдельной строкой.** Книга, чей файл на диске
новее записи в индексе, показывается не среди «в индексе их нет», а под заголовком
«Изменились на диске после индексации»: поиск по ней работает и отдаёт **прежний** текст,
а ссылки на строки могут вести в никуда. Правка без изменения размера отмечается
особо — «размер тот же, новее только время»: именно такая правка однажды уехала мимо
индекса молча и нашлась глазами. Совет в конце отчёта — `--kb-refresh`, он перечитает
изменившиеся и посчитает им смыслы.

**Сводка идёт первой** — отчёт по живой библиотеке занимает сотню строк, а вопрос к нему
обычно один: «всё ли в порядке». Ответ виден сразу, без чтения всего отчёта:

```
Проверка коллекции books

Коротко (подробности ниже, команды в конце):
     2  не в индексе — поиск их не находит
    15  помечены удалёнными (место на диске)
    18  сегментов: каждый добавляет проход при поиске
```

Строки идут по важности для выдачи, а не по порядку разделов: непрочитанная книга
не находится вовсе, и это хуже, чем лишний сегмент. У здоровой коллекции сводки нет —
вместо неё «Всё в порядке».

Отсюда и способ посмотреть состояние одним взглядом — `head`, а не `grep` по заголовкам
разделов:

```bash
ollchat --kb-doctor books --kb-quick 2>/dev/null | head -8
```

`2>/dev/null` выбрасывает поток ошибок: туда идёт бегущая полоса хода, и в конвейере
она мешает. `--kb-quick` снимает два долгих шага. **Не выбирайте строки по `grep`
с текстом заголовков** — заголовки меняются, и такой конвейер однажды молча покажет
«чисто» там, где чисто не было.

**Названия книг светло-жёлтые** — в списке из сотни строк, где вперемешку идут пути,
пояснения и советы, книга должна находиться глазом без чтения. Цвет появляется только
в терминале: `--kb-doctor books > отчёт.txt` даёт чистый текст без управляющих
последовательностей.

**Пока проверка идёт, внизу движется полоса хода** со шагом и временем:

```
открываю граф [░░░░░░░█░░░░░░░░░░░░] · 6 с
проверяю книги на месте [████████████████████] 100% 379/379 · 16 с
сверяю книги по содержимому [░░░█░░░░░░░░░░░░░░░░] · 16 с
```

На живой библиотеке проверка занимает около семнадцати секунд, и большая часть — открытие
графа ради одной пометки `[в графе]`. Без полосы программа всё это время молчит,
и отличить её от зависшей нечем. Где шагов посчитать нельзя (открытие графа — это одно
чтение файла на гигабайт), полоса бежит туда-обратно: она говорит «работа идёт»,
не обещая знать, сколько осталось. Ключ `--kb-quick` снимает оба долгих шага.

Что он находит:

| | |
|---|---|
| **лежат в каталогах, но не в индексе** | книгу положили, а проиндексировать забыли — поиск не находит её вовсе; читает `--kb-refresh` |
| **лежат в каталогах копиями** | тот же файл уже в индексе под другим именем: доливка их пропускает намеренно, лечится удалением копии |
| **пропавшие с диска** | поиск по ним ещё работает — текст лежит в базе; убрать `--kb-sync` |
| **сканы без текста** | страницы можно показать модели с `vision` через `/addimg` |
| **не прочитались** | зашифрованный PDF, нечитаемый текстовый слой — с причиной |
| **одна книга под разными именами** | побайтово одинаковые файлы, с готовой командой удаления |
| **разные издания одной книги** | по схожести названия |
| устаревшие правила разбора, много сегментов, помеченное удалённым | |

**Про повторы отдельно.** Одна и та же книга, разложенная по двум каталогам, — ошибка, от
которой не застрахован никто: книгу копируют, а не ссылаются, и через месяц никто не помнит,
что она лежит дважды. Вред прямой: две одинаковые выдержки занимают два места из восьми
в выдаче, вытесняя другие книги, а граф считает понятие встреченным в двух книгах вместо одной.

Ищутся такие повторы **по содержимому, а не по имени**: копию почти всегда переименовывают.
Сначала отбираются книги совпадающего размера, и только они сравниваются побайтово — иначе
проверка перечитывала бы всю библиотеку.

Эта же проверка работает **при индексации**: повтор не разбирается вовсе, и в отчёте видно,
какая книга пропущена и с чем совпала. Различаются два случая — «уже проиндексирована»
и «то же, что новая»: для человека это разные новости.

Удалять книги программа не станет — она показывает и даёт готовую команду. Программа,
стирающая файлы из чужой библиотеки по своему разумению, однажды сотрёт не то.

**«Не в индексе» и «копия на диске» — разные вещи, и путать их нельзя.** Первое лечится
доливкой, второе — нет: индексация побайтовые копии пропускает намеренно, и совет
«долить» здесь замкнул бы круг — выполнил, вернулся к проверке, увидел тот же список.
Поэтому копии идут отдельным разделом, с указанием, с чем совпал файл и сколько места
он занимает. Удалять его программа не станет: файлов из чужой библиотеки она не трогает.

**Проверка идёт в обе стороны.** Реестр против диска — на месте ли книги, о которых
коллекция знает; и диск против реестра — не появилось ли в каталогах книг, которых
она не читала. Вторая половина важнее первой: книгу положили, проиндексировать забыли,
поиск её не находит — и объяснить это нечем, потому что раньше отчёт в таком случае
отвечал «всё в порядке».

## Смыслы устаревают молча

Смысловой поиск работает по заранее посчитанным векторам. Кусок или понятие, которых
там нет, **просто не находятся по смыслу** — и программа об этом не предупреждает.
Выдача выглядит нормальной, только часть библиотеки в неё не попадает.

Так и вышло 27.08.2026: доиндексация добавила 68 книг, и 70 тысяч кусков остались видны
одному словесному поиску. Заметить это можно было только сравнив два числа.

### Два разных набора векторов

Векторов в программе два вида, и это первое, что стоит понять: команды у них разные,
файлы разные, и одна не заменяет другую.

**Векторы кусков** считаются для *фрагмента текста книги* — страницы, абзаца. Лежат
в сегментах коллекции рядом с самим текстом. Ими работает **смысловой поиск по книгам**:
русский вопрос находит английский абзац, «горутина» приводит к тексту про `goroutine`.
Их столько же, сколько кусков в коллекции, — сотни тысяч.

**Векторы понятий** считаются для *имени понятия графа* — «горутина», `goroutine`,
«сборщик мусора». Лежат в `graph/entities.vec`. Ими работает **смысловой вход в граф**:
вопрос превращается в вектор, и по нему находятся понятия, даже если ни одного слова
из имени понятия в вопросе нет. Их столько же, сколько понятий, — десятки тысяч коротких
строк, поэтому считаются они заметно быстрее.

Посчитать только первые — вход в граф не увидит новых понятий. Только вторые — поиск
по новым книгам останется словесным. Общее у них ровно одно: обе работы идут через
эмбеддер и просят видеокарту, поэтому запускать их одновременно смысла нет.

### Путь вопроса

```
вопрос → вектор вопроса
   ├─→ векторы ПОНЯТИЙ → понятия графа → связи → карта понятий
   └─→ векторы КУСКОВ  → фрагменты книг ⊕ BM25 → выдержки со ссылками
```

Оба плеча работают на один ответ: граф отвечает на «как это связано с тем», книги —
на «где про это написано». Отстало любое из них — ответ станет беднее молча.

### Что от чего зависит

| что устарело | от чего | чем чинить | сколько стоит |
|---|---|---|---|
| векторы **кусков** | добавления **книг** (`--kb-sync`, `--kb-index`) | `--kb-embed` | минуты на тысячи кусков |
| векторы **понятий** | роста **графа** (`--graph-build`) | `--graph-embed` | 20 мин на 63 тыс. понятий |

Эти две вещи не связаны между собой, и путать их — значит делать лишнюю работу:

- **сборка графа кусков не добавляет** — после неё `--kb-embed` не нужен;
- **доиндексация книг понятий не добавляет** — после неё не нужен `--graph-embed`.

### Как проверить, всё ли на месте

```
ollchat --graph-status books
```

Строки со смыслами показывают, сколько посчитано и сколько всего. Если чисел не хватает,
команда так и скажет — и назовёт, чем чинить.

### Когда считать

**Векторы кусков** — сразу после того, как доложили книги. Иначе новые книги существуют
только для поиска по словам.

**Векторы понятий** — не после каждой сборки. Команда пересчитывает всё заново, а не
только новое: при сборке заходами по два часа это двадцать минут накладных на каждые
сто двадцать. Разумнее раз в несколько заходов — до тех пор новые понятия находятся
по написанию, только не по смыслу.

## Порядок, который нельзя путать

1. **Перечитать книги** (`--kb-reindex`) — если изменился разбор.
2. **Досчитать смыслы** (`--kb-embed`) — у новых кусков их нет.
3. **Догнать граф** (`--graph-build`) — новые куски он не видит.
4. **Пересобрать темы** (`--graph-communities`) — разбиение считается по графу
   и после его роста устаревает.
5. **Описать новые темы** (`--graph-summaries`) — берутся только темы без заголовка.

Нарушение порядка не ломает данные, но заставляет переделывать: собрали граф до того,
как перечитали книги, — и сутки работы карты ушли на текст с мусором.

# Разделы ниже — справочник

## Подготовка: разрешить каталоги с книгами

Книги лежат вне рабочего каталога, поэтому песочница на них не распространяется. Разрешение даёт
только файл настроек — ни модель, ни команда его не расширяют.

```toml
[kb]
dir   = "~/.local/share/ollchat/kb"                  # где держать индексы
roots = ["/mnt/books",      # откуда разрешено брать книги
         "/mnt/books2"]
```

Без `roots` любая попытка индексации отклоняется с указанием, где разрешать каталоги.

## Добавить книги

```
/kb add books /mnt/books
```

Каталог обходится целиком, включая подкаталоги. Что происходит с каждой книгой:

- **PDF и EPUB с текстом** — разбираются, режутся на куски ~1200 символов с перекрытием,
  индексируются по словам;
- **сканы без текстового слоя** — помечаются `scan` и пропускаются, их число видно в итоге;
- **повреждённые** — помечаются `broken`, работа продолжается;
- **крупнее `max_book_mb`** (512 МБ) — пропускаются.

Индексация идёт в фоне: чат при этом работает, ход виден в строке состояния. Прервать — `Esc`
или `/kb stop`: текущая книга доводится до целого состояния, остальное продолжится со следующего
запуска.

Замер на живой библиотеке: **198 книг → 249 056 кусков, 124.7 МБ, 2 мин 21 с.**

Долгую индексацию удобнее гонять без интерфейса:

```bash
nohup ./ollchat --kb-index books /mnt/books &
```

## Проверить состояние

```
/kb                    состояние всех коллекций одной строкой
/kb list books         книги в коллекции
/kb stats books        подробности: куски, термы, сегменты, смыслы, место
/kb doctor books       что не так: пропавшие книги, сканы, сбои, дубликаты
```

`/kb stats` — главная команда для понимания, в каком всё состоянии:

```
Коллекция books
  книг: 205 (с текстом 198, сканов 5, со сбоями 2, убрано 0)
  кусков: 249056, термов: 464802, сегментов: 2
  на диске: 379.9 МБ
  правила разбора: ru-en-v1
  смыслы: посчитаны целиком, модель bge-m3, размерность 1024
  собрана из: /mnt/books
  разрешено:  /mnt/books, /mnt/books2
  состав:
    Coding                         94 книг, кусков 121645, без текста 1
    OS                             39 книг, кусков 50844, без текста 2
    DevOps                         33 книг, кусков 32832
    IoT                            18 книг, кусков 21456, без текста 3
    DataBases                       6 книг, кусков 7049
    (в корне)                       5 книг, кусков 3015, без текста 1
    Infosec                         5 книг, кусков 8764
    AI                              4 книг, кусков 2526
    Monitoring                      1 книг, кусков 925
```

Три строки здесь стоит различать:

| Строка | Что означает |
|---|---|
| `собрана из` | откуда книги **фактически** взяты — записано в самой коллекции |
| `разрешено` | `kb.roots` из конфига: откуда брать **можно**; коллекция может использовать не всё |
| `состав` | разбивка по первому уровню подпапок |

**Состав важнее, чем кажется.** «Книг: 205» не говорит ни о чём: от того, что в этой библиотеке
шесть книг по Go и шестьдесят шесть по C#, прямо зависит, чего ждать от поиска. Запрос про каналы
упирается в те шесть, а вопрос про потоки утонет в справочниках по C# — и это не дефект поиска,
а состав библиотеки.

Строка «смыслы» принимает четыре вида:

| Что написано | Что делать |
|---|---|
| `не настроены (kb.embed_model пуст)` | задать модель, см. ниже |
| `не посчитаны — /kb embed books` | посчитать |
| `92% (229000 из 249056) … досчитать` | доложены книги, нужен досчёт |
| `посчитаны целиком, модель bge-m3` | всё в порядке |

Без интерфейса: `./ollchat --kb-list`.

## Посчитать смыслы

Модель эмбеддингов должна быть на сервере (`ollama pull bge-m3`), затем:

```toml
[kb]
semantic         = true
embed_model      = "bge-m3"                    # пусто — смыслового поиска нет вовсе
embed_url        = "http://ollama.example:11434"    # пусто — тот же сервер, что для чата
embed_batch      = 128
embed_workers    = 4
embed_keep_alive = "5m"
```

**Всегда начинайте с оценки** — она делает настоящий замер на пробе, а не берёт числа из таблицы:

```
/kb embed books --dry-run
```

```
осталось кусков 249056 из 249056 · размерность 1024 · ориентировочно 1h31m ·
на диске ещё 255 МБ · модель bge-m3
```

Затем счёт:

```
/kb embed books                      # с прогрессом и остановкой по Esc
./ollchat --kb-embed books           # без интерфейса, можно под nohup
```

Замер на стенде: **249 056 кусков за 22 мин 26 с, 255 МБ.**

Прерывать безопасно в любой момент. Счётчик сохраняется после каждой волны, повторный запуск
продолжит с того же места; цена обрыва — одна волна (`embed_batch × embed_workers` кусков).

## Доложить книги

```
/kb sync books                 # или ./ollchat --kb-sync books
```

Сверка идёт по размеру и времени файла, без чтения содержимого. Новые книги индексируются,
пропавшие помечаются удалёнными. **Работа стоит ровно столько, сколько новых книг** — замерено:
возврат одной книги в коллекцию из 198 занял 1 секунду.

Смыслы при этом не считаются. После доливки — `/kb embed books`, он обработает только новые куски.
Приложение само напомнит при запуске:

```
△ База знаний:
    books: векторы(смыслы) посчитаны для 92% кусков — /kb embed books
```

Чтобы оно ещё и сверяло папки при каждом запуске: `sync_on_start = true` (только сообщать,
не индексировать).

## Удалить книгу или коллекцию

```
/kb rm books --book /путь/к/книге.pdf     убрать одну книгу
/kb rm books                              удалить коллекцию целиком
```

Книга **сразу** пропадает из выдачи — это одна строка в служебном файле. Но её куски и векторы
остаются на диске до уплотнения: сегменты индекса неизменяемы, и именно поэтому доливка книг
стоит дёшево.

## Уплотнить (освободить место)

```
/kb merge books                # или ./ollchat --kb-merge books
```

Хранилище переписывается без удалённого, сегменты сливаются в один, векторы переезжают вместе
с кусками. Ссылки вида `books/12#37` из старых ответов модели остаются верными.

Когда пора — подскажет `/kb stats`: «удалённое занимает 23% кусков» или «сегментов 9».
Автоматически не запускается: 249 тыс. кусков — 2 мин 13 с. Прерывание безопасно: коллекция
остаётся либо прежней целиком, либо новой целиком.

## Пересчитать заново

| Что изменилось | Что делать |
|---|---|
| Сменили `embed_model` | `/kb embed books --recount` — смыслы разных моделей несравнимы |
| Изменились правила разбора (`/kb stats` пишет «правила изменились») | `/kb rm books` и собрать заново |
| Книга изменилась на диске | `/kb sync books` заметит по размеру и времени |

Пока модель в настройках не совпадает с той, которой считали, векторы **не используются молча** —
поиск идёт по словам и говорит об этом с готовой командой для починки.

## Искать своими глазами

`/search` ищет **по графу и по книгам сразу и не спрашивает модель**: ни ожидания
ответа, ни расхода контекста. Показывает понятия по вопросу, связи между ними
и выдержки из книг со ссылкой на книгу, год и страницу.

```
/search как связаны RAG и дообучение
/search -f 3 goroutine scheduler      куски целиком, три штуки
/search -r запрос                     со второй ступенью отбора (реранкером)
/graph find <вопрос>                  то же самое другим именем
```

| Ключ | Что делает |
|---|---|
| `-f`, `--full` | показать куски целиком, а не короткими выдержками |
| `-r` | вторая ступень отбора; без настроенного `kb.rerank_url` скажет об этом |
| `N` | сколько выдержек показать; по умолчанию `kb.top_k`, потолок 50 |

Голое число считается количеством, **только если за ним есть текст**: `/search 2026` —
это вопрос про 2026 год.

Под каждой выдержкой стоит её идентификатор вида `books/331#446`:

```
/read books/331#446    кусок целиком вместе с соседями (kb.read_around)
/read 3                третий из последней выдачи
Ctrl+F                 список найденного: ↑↓ выбрать, Enter прочитать,
                       Ctrl+O открыть книгу во внешней программе, Esc закрыть
```

**Пока карта занята сборкой графа, смысловой поиск не работает** — сервер в это время
не отдаёт эмбеддинги вовсе. Поиск не виснет и не молчит: он ищет по словам и говорит
об этом второй строкой, называя срок (`kb.query_timeout`, по умолчанию 15 с; `"0"` —
не ждать вовсе).

Поиск только по книгам, без графа, остался прежним:

```
/kb search буферизированный канал
/kb search goroutine scheduler -c books
```

Отдать поиск модели:

```
/kb use books          выбрать коллекцию по умолчанию
/kb auto on            подмешивать найденное перед каждым вопросом
```

При `auto on` перед каждым вашим вопросом делается поиск, и найденное уходит модели отдельным
сообщением с требованием ссылаться на источники. Работает даже с моделями без поддержки
инструментов.

Модель может искать и сама — инструментами `kb_search` и `kb_read`. Инструмента индексации у неё
нет и не будет: иначе она сможет запустить многочасовую задачу и прочитать всё, до чего дотянется.

## Проверить, хорошо ли ищется

«Поиск работает» — это не измерение. Оно не отличает выдачу, где нужный кусок стоит
первым, от выдачи, где он восьмой, и не даёт сравнить два способа искать. А без такого
сравнения любая правка поиска остаётся верой: сделал — вроде получше.

Замерный набор — это список вопросов, у каждого из которых **заранее известен правильный
ответ**. Прогон задаёт их поиску и считает, насколько часто и насколько высоко правильный
ответ находится.

### Собрать набор

```
ollchat --kb-eval-gen my.toml --kb-eval-gen-n 400 --kb-seed 20260827
```

Команда берёт куски **вслепую** — равномерной выборкой по всей коллекции — и просит модель
составить к каждому вопрос, какой задал бы человек, книги не читавший. Правильным ответом
считается ровно тот кусок, по которому вопрос составлен.

Слепота тут принципиальна. Если отбирать куски поиском, набор подсунет ровно то, что поиск
и так находит, и замер подтвердит сам себя. Зерно случайности (`--kb-seed`) задаётся явно
и записывается в шапку набора: замер обязан повторяться, иначе разницу между двумя
прогонами не отличить от случайности.

Служебные страницы — оглавления, списки литературы, обрывки кода — отсеиваются: модель
сама помечает их пропуском, а что не пометила, ловится по виду вопроса.

Если вопросы хочется написать своей рукой, `--kb-sample books --kb-eval-gen-n 50` отдаст
слепую выборку кусков в JSON, а дальше дело ваше.

### Прогнать

```
ollchat --kb-eval my.toml
```

```
режим        recall@K      MRR     nDCG  ср. место     мимо
слова           0.131    0.098    0.106        1.9      397
смыслы          0.363    0.248    0.276        2.3      291
слияние         0.363    0.186    0.228        3.4      291
```

Что означают числа:

- **recall@K** — доля вопросов, где нужный кусок попал в первые K (по умолчанию десять).
  Отвечает на «нашлось ли вообще».
- **MRR** — насколько высоко он стоит: единица, если всегда первым.
- **nDCG** — то же, но с плавным падением цены места.
- **ср. место** — на каком месте оказывался найденный. Главное число, когда речь о том,
  что увидит модель: она читает первые несколько кусков, а не десять.
- **мимо** — на скольких вопросах не нашлось вовсе.

Три строки — три способа искать: только по словам (BM25), только по смыслу (векторы)
и слияние обоих. Порознь они ничего не значат, сравнение — всё.

### Зачем нужны два набора

Набор из переформулированных вопросов **смещён в пользу смыслового поиска**: точных
терминов в нём нет вовсе. Судить по нему одному — значит подтвердить то, во что и так
веришь.

Поэтому рядом нужен второй, из **точных терминов** — `compose.yaml`, `nodeSelector`,
имя модуля, код ошибки. Это то, в чём словесный поиск незаменим.

Насколько это важно, показывает наш собственный случай. На 22 терминах выходило, что
слияние проигрывает чистым словам, и вывод напрашивался сам. На 120 — ровно наоборот,
слияние лучшее по всем трём мерам. **Малая выборка не просто шумит, она врёт в одну
сторону и читается как результат.** Десятки наблюдений решают «мерить ли дальше», сотни —
«делать ли работу».

### Подобрать настройки

Замер годится не только для «стало ли лучше», но и для выбора значений:

```
ollchat --kb-eval my.toml --kb-eval-weight 1.5   вес смыслового списка
ollchat --kb-eval my.toml --kb-eval-only слияние  мерить один режим — втрое быстрее
ollchat --kb-eval my.toml --kb-eval-rerank        добавить вторую ступень
```

Так и выбран нынешний вес слияния: перебором по обоим наборам сразу. Значение 1.5
оказалось единственным, которое улучшает порядок выдачи **на обоих**; при большем
точные термины резко проседают.

### Вторая ступень: переранжирование

Первая ступень сравнивает вопрос и кусок порознь — у каждого свой вектор. Так можно
перебрать 300 тысяч кусков за десятки миллисекунд, но модель ни разу не видит вопрос
и кусок рядом. Кросс-энкодер читает их **вместе** и переставляет верхушку выдачи.

Что это даёт, по замеру на 457 вопросах:

| | без второй ступени | с ней |
|---|---|---|
| нужный кусок в среднем на месте | 2.6 | **1.7** |
| nDCG | 0.263 | **0.344** |
| полнота recall@10 | 0.365 | **0.396** |

Разница не косметическая: модель читает первые несколько найденных кусков. Когда нужный
третий, она тратит окно на два лишних и может до него не дойти; когда первый — отвечает
по существу.

Считает переранжирование **отдельная служба**: Ollama кросс-энкодеры не обслуживает.
Поднимается контейнером:

```bash
docker run -d --name llama-rerank --restart unless-stopped --gpus all \
  -p 127.0.0.1:8378:8080 -v ~/models:/models:ro \
  ghcr.io/ggml-org/llama.cpp:server-cuda \
  -m /models/bge-reranker-v2-m3.gguf --reranking --host 0.0.0.0 --port 8080 \
  -c 8192 -b 8192 -ub 8192 --n-gpu-layers 99
```

Размер пачки (`-b`) обязан вмещать самую длинную пару «вопрос + кусок». С умолчанием 512
служба отвечает `input is too large to process`, и переранжирование молча работает только
на коротких выдержках.

В конфиге достаточно адреса:

```toml
[kb]
rerank_url = "http://localhost:8380"   # пусто — вторая ступень выключена
```

Умолчания подобраны замером: двадцать кандидатов, куски целиком. Восемьдесят кандидатов
дают большую полноту, но худшее место и вчетверо большую цену — а для ответа по книгам
важнее место. Подробности и полная таблица — в документации проекта, «Смысловой поиск по книгам».

Сбой службы не ломает поиск: выдача первой ступени остаётся как есть.

### Три вещи, которые сломают замер

**Занятая карта.** Прогон, сделанный, пока видеокарта занята чем-то ещё, может дать числа,
в точности равные словесному режиму: запросы к эмбеддеру не проходят, и смыслового списка
просто нет. Поиск при этом ведёт себя правильно, а замер становится негодным. Мерить
только на свободной карте; совпадение с чистым BM25 — признак того, что смыслов не было.

**Абсолютные числа.** Они занижены нарочно: на общий вопрос вроде «какая команда выводит
текст на экран» в библиотеке отвечают десятки кусков, а засчитывается один. Для сравнения
способов это не мешает — занижение одинаково для всех, — но само по себе значение recall
ни о чём не говорит.

**Набор, собранный под ответ.** Если вопросы писались, глядя на выдачу поиска, замер
покажет отличные числа и не будет значить ничего.

## Как модель отвечает по книгам

Найденные фрагменты — это опора для ответа, а не сам ответ. Каким получится ответ, задаёт
настройка `answer_style`:

```toml
[kb]
answer_style = ""     # пусто — встроенный текст
```

Встроенный текст:

> Отвечай своими словами и объясняй по существу — пересказ цитат ответом не считается.
> Взятое из книги помечай ссылкой с её названием: («Название книги», автор, год, стр. N) —
> или номером `[1]`, если в конце ответа перечислишь эти книги с названиями. Название
> обязательно: одних фамилий мало, по ним книгу не найти, а слово «книга» вместо названия
> ссылкой не считается. Собственные пояснения и примеры приветствуются; нельзя лишь
> приписывать книгам того, чего в них нет. **Если приводишь цитату не на русском — под ней
> дай перевод, оригинал оставь: по нему проверяют. Термины без устоявшегося русского слова
> не переводи.** Если во фрагментах ответа нет — скажи об этом и ответь сам. Книга описывает
> своё время: держи в уме год издания и сегодняшнюю дату; где расхождение вероятно — скажи
> об этом прямо.

Две последние правки текста стоит объяснить, потому что обе выстраданы.

**Название книги.** Прежний образец звучал «помечай `[1]` или (книга, стр. N)» — и модель
понимала его буквально: в сохранённом ответе стояло `[книга, стр. 191]`, а где она всё же
называла источник, оставались одни фамилии: «(Raieli & Iuculano, 2025, стр. 180)». По фамилии
книгу на полке не найти, тем более что у одного автора их бывает несколько.

**Перевод цитат.** Библиотека английская, разговор русский, и цитата без перевода заставляет
спотыкаться о язык посреди мысли. Оригинал при этом обязан остаться: по нему проверяют ответ,
перевод идёт следом, а не вместо. Термины вроде `reranking` и `embeddings` не переводятся
намеренно — выдуманный русский термин хуже английского.

Посмотреть действующий текст, не открывая исходник:

```
/kb style
```

Команда печатает политику целиком и говорит, откуда она взята — из `answer_style`
или встроенная. Отсюда её удобно скопировать, поправить пару слов и вписать в конфиг,
ничего не потеряв по дороге.

Он уходит модели в трёх местах сразу: в описании инструмента `kb_search`, в подписи под его
результатами и в шапке подмешивания при `/kb auto on`. Своё значение заменяет встроенное
целиком и действует без пересборки.

**Осторожно с формулировками.** Требование ссылаться нужно уравновешивать требованием объяснять.
Первая версия встроенного текста звучала так:

> В ответе **ОБЯЗАТЕЛЬНО** ссылайся на источники… Если во фрагментах ответа нет — скажи об этом
> прямо, **не додумывай**.

Задумывалось «не приписывай книгам того, чего в них нет», а модель прочла буквально — как запрет
говорить от себя. На вопрос «как работают горутины» она выдала подборку выдержек без единой
собственной мысли. После правки на тот же вопрос та же модель отвечает своей структурой, своим
примером кода и сравнением с потоками ОС, а ссылки `[1]`, `[2]` ставит только там, где факт взят
из книги.

Порознь эти требования дают беду с двух сторон: одно требование ссылаться — цитатник, одно
требование объяснять — выдумки со ссылками на несуществующие страницы.

**Что настройкой не меняется** — договор инструмента: что он принимает, что возвращает, как
называются параметры. Это живёт в коде рядом с реализацией: разъедется текст с поведением, и модель
начнёт вызывать инструмент неверно.

## Граф понятий: команды в чате

```
/graph                состояние графа выбранной коллекции: понятия, связи, охват
/graph auto on|off    подмешивать карту понятий к каждому вопросу
/graph status [имя]   то же по названной коллекции
/graph archive [имя]  снять архив коллекции с графом в фоне (см. ниже)
/graph archives [имя] какие архивы есть
/graph review [--judge] [имя]  разобрать пары, в которых машина усомнилась (см. ниже)
```

**Разбор пар: `/graph review`.** Связывание новых имён при сборке опытного графа
(`--graph-link-new`) и ночной разбор двойников отдают спорное не в корзину, а человеку:
пары с вердиктом арбитра «?» ложатся в `links.jsonl` рядом с графом. Окно показывает их
списком: имена с числом упоминаний, близость, причина сомнения, книга и страница
куска-источника. `y` — одно и то же (склейка узлов, обратимая, как все склейки),
`n` — разные, пробел — позже, `Enter` — прочитать кусок целиком, `u` — вернуть пару
в список, `Esc` — закрыть. Решения пишутся сразу, по одному. `--judge` открывает второй
режим: проверка решений арбитра «ДА» глазами; `n` там отменяет решение на будущее,
уже отданные узлу упоминания назад не переносятся. Доктор и подсказка при запуске
называют размер очереди. Схема всего пути — в документации проекта, «Здоровье графа», глава «Связывание
новых сущностей при сборке и очередь человеку».

Сборки среди команд чата нет намеренно: она занимает карту на часы и запускается
отдельным запуском — `ollchat --graph-build books --folder AI`, лучше под `tmux`.
Модели инструмент сборки тоже не дают: она не должна уметь занять машину на сутки.

## Архив коллекции с графом и восстановление

Рабочий граф — недели работы видеокарты, и портится он молча: неудачное уплотнение,
склейка не тех двойников, сбой диска. Лучше старый рабочий граф, чем никакой, поэтому
ollchat снимает архив **сам**, пока запущен: раз в сутки, в фоне, чат при этом работает.
Пока архив идёт, в строке состояния горит `⛁ архив books 37s`; итог появляется
заметкой в ленте (не посреди ответа модели — после него).

**Что в архиве.** Коллекция целиком — куски книг, их векторы и все графы в ней
(рабочий и опытные рядом), — обычным `tar.gz`. Только граф без коллекции был бы втрое
меньше, но бесполезен после пересборки коллекции: граф ссылается на книги по номерам,
а номера раздаёт индексация — пересобранная из тех же книг коллекция раздала бы их
иначе, и граф молча указывал бы не на те книги. Замер на живой библиотеке
(198 книг, 1.15 ГБ на диске): около 600 МБ, 53 секунды. В архив не идут замки, признаки
работ и резервные копии реестра `*.bak-*`.

**Когда снимается.** Раз в пять минут проверяется каждая коллекция, у которой есть граф:
если новейший её архив старше `archive_every` и с коллекцией никто не работает —
снимается новый. Работой считаются сборка графа, счёт векторов, разметка и описания тем,
разборы, склейки, уплотнение, скрытие книги, группы и индексация коллекции: каждая из них
ставит признак (`LOCK`, `WORK-<pid>` в каталоге графа, `LOCK` коллекции), и архив под ними
не начинается, а ждёт следующей проверки. Наоборот тоже: работа, начатая во время архива,
ждёт его окончания до двух минут, а не отказывает — ночная сборка по cron не должна
срываться из-за секунд архива. Признак брошенного процесса снимается сам.

```toml
[graph]
archive_dir   = "~/.local/share/ollchat/kb_archives"
archive_every = "24h"     # как часто; "off" — только руками
archive_keep  = 7         # сколько последних хранить; 0 — все
```

Расписание работает, пока запущен ollchat. Если он запускается не каждый день,
добавьте в конец ночной цепочки шаг `ollchat --graph-archive books`.

```bash
ollchat --graph-archive books           # снять архив сейчас (отказ, если идёт работа)
ollchat --graph-archives books          # что есть; all — по всем коллекциям
ollchat --graph-restore books-20260904-111305.tar.gz   # восстановить
```

**Восстановление** — командой, не из чата: это редкое и намеренное действие. Перед ним
закройте ollchat и ollmcp, держащие коллекцию открытой: они продолжат читать прежние файлы.
Команда показывает, что в архиве и что на диске (понятия, связи, охват, дата), спрашивает
подтверждение словом `ДА` (в скрипте — `--graph-restore-yes`), **сначала снимает нынешнюю
коллекцию в архив с пометкой `before-restore`** — ничего не теряется, — распаковывает
рядом и подменяет каталог переименованием, целиком и разом. Под идущей работой
восстановление отказывает. Снимки `before-restore` в ротацию не входят: убирайте их сами.

## Подмешивание: карта понятий и выдержки к вопросу

Модель с инструментами добывает знание сама — зовёт `kb_search` и `graph_search` там, где
они нужны. Но два случая инструментами не закрываются: модель может их **не уметь**
(у `deepseek-r1` в сборке нет ни RENDERER, ни PARSER, что бы ни говорил `ollama show`)
или **не догадаться** позвать — тогда она отвечает по памяти, уверенно и без ссылок.

Поэтому ollchat умеет искать сам и класть найденное отдельным сообщением перед вопросом.
Настройки собраны в отдельный раздел, потому что это единственное, что тратит контекст
на **каждый** вопрос:

```toml
[mix]
books     = false       # выдержки из книг к каждому вопросу (обычный RAG)
graph     = true        # карта понятий из графа (GraphRAG)
entities  = 6           # сколько понятий брать в карту
neighbors = 4           # сколько связей показывать у каждого
quotes_without_tools = 3  # выдержек модели, которая не умеет инструментов
```

Переключается на лету: `/kb auto on|off` — книги, `/graph auto on|off` — граф.
Прежнее имя настройки `kb.auto` продолжает работать и означает то же, что `mix.books`.

**Привратник.** Перед подмешиванием вопрос проверяется дважды, и обе проверки местные,
без сервера и эмбеддингов:

1. Распоряжения о здешнем коде («перепиши эту функцию», «сделай коммит и запушь»)
   и вопросы не о предмете («какой сейчас год», «спасибо») отсеиваются сразу.
2. Вопрос связывается с понятиями графа. Не связался ни с одним — не подмешивается
   ничего, даже при включённом `mix.books`.

Без этого каждое «спасибо» стоило бы двух тысяч токенов. Проверка стоит 0.0–0.3 мс.

**Что уходит модели.** Карта понятий: понятия, их синонимы и связи между ними,
две-три сотни токенов, без цитат — за цитатами модель зовёт `kb_search`. Если модель
инструментов не умеет, к карте добавляются две-три выдержки: дозапросить ей нечего,
и без выдержек ей не на что сослаться. Поиск выдержек идёт по вопросу **плюс имена
найденных понятий и их синонимы** — граф работает переводчиком вопроса на язык книг:
он знает, что «дообучение» в книгах называется fine-tuning.

**Что видно человеку.** Под вопросом печатается серая строка о том, что реально ушло:

```
подмешано к вопросу ≈1.4k токенов
  граф: понятий 2, связей 8 — /graph auto off отключает
  книги: фрагментов 3, 2026 г. (модель без инструментов — сама не дозапросит)
```

Иначе расхождение между тем, что видит человек, и тем, что получила модель, ничем
не объяснить.

## Сегодняшняя дата и возраст книг

Модель не знает, какое сегодня число: в весах остался предел её обучения. На прямой вопрос
`deepseek-r1` отвечает «2023 год». Ollama дату не подставляет, поэтому это делает ollchat:

```toml
[general]
today = true          # добавлять сегодняшнюю дату в системное сообщение
```

Вместе с датой уходит оговорка, что знания модели заканчиваются раньше и ответ, зависящий
от времени, надо помечать. Дата считается заново на каждый запрос — сеанс, переживший
полночь, не врёт, — и не попадает ни в `/system`, ни в сохранённую сессию.

Знание из книги тоже датировано, а в ответе выглядит вечным. Поэтому у книг определяется
**год издания** и печатается рядом со ссылкой:

```
[1] Hands-On RAG for Production · Ofer Mendelevitch and Forrest Sheng Bao · 2026 г. · стр. 104
```

Год берётся из трёх источников по убыванию доверия: имя файла (в библиотеке владельца
он есть у 94% книг), копирайт с первых страниц, метаданные файла. Метаданные последние
намеренно: `/CreationDate` — дата **файла**, а у скана старой книги она новее лет
на двадцать. Год никогда не отбраковывает книгу — только добавляет к выдаче одну оговорку
на всю подборку, и только если самой старой книге больше трёх лет.

Книгам, собранным до появления этого поля, год проставляет отдельный проход — переиндексация
для этого не нужна:

```
/kb years books              проставить год там, где его нет
/kb years books --recount    перечитать год у всех книг
ollchat --kb-years books     то же без интерфейса
```

На библиотеке из 228 книг проход занял 1.6 секунды: 220 книг получили год, из них 208 —
прямо из имени файла.

## Перечитать книги заново

Когда меняются **правила разбора** (а не сами книги), доливка их пропустит: она смотрит
на размер и время файла. Для таких случаев есть отдельная команда:

```
/kb reindex books /путь/к/книге.pdf …
ollchat --kb-reindex books /путь/к/книге.pdf
```

Перечитанная книга получает новый номер, а прежние её куски помечаются удалёнными: поиск
сразу перестаёт их выдавать, место освободит `/kb merge`.

**Если по коллекции собран граф понятий, уплотнение отклоняется.** Не предупреждением,
а отказом: `/kb merge` уменьшает число кусков, и граф после него не открывается вовсе,
пока его не пересоберут. Размен плохой в обе стороны — уплотнение освобождает десятки
мегабайт, пересборка графа стоит часов работы видеокарты, — поэтому решение вынесено
из памяти человека в код.

```
ollchat: по коллекции books собран граф понятий, и уплотнение сделает его нечитаемым.
Граф лежит в …/collections/books/graph и стоит часов работы видеокарты.
Если он больше не нужен — уберите каталог и повторите; если нужен — уплотнять нельзя
```

Осознанный обход — `--kb-merge-force` в командной строке или `/kb merge <имя> force`
в приложении. Нужен он в одном случае: граф решено собирать заново, и старый не жаль.

Перечитанная книга мягче, но тоже бьёт по графу: ссылки на её прежние куски теряют
название и страницу. Порядок такой: перечитать → догнать графом новые куски → уплотнять
только вместе с полной пересборкой графа.

# Журнал и сессии

```
/log [on|off]     путь к журналу, включение и выключение
/id               идентификатор обмена — по нему обмен ищется в журнале
/save             сохранить текущую сессию
/resume [id]      восстановить сессию (без id — выбор из списка)
/config           путь к файлу настроек
```

Журнал пишется дозаписью в файл; существующий файл никогда не затирается. Настраивается
разделом `[log]`: `enabled`, `dir`, `file_pattern`, `log_thinking`, `log_tools`,
`steps_file_pattern`.

## Сжатие истории сводкой

В чате история сжимается сама: когда последний ответ сервера показал, что окно
заполнено на долю `agent.compact_at` (по умолчанию 0.75), перед следующим вопросом
старые сообщения уходят модели одним запросом «сожми в сводку», сводка ложится в
историю первым сообщением, а последние `agent.compact_keep` сообщений (по умолчанию 6)
остаются дословно. Сводку пишет та же модель, что отвечает, либо `agent.compact_model`.
Под вопросом появляется серая строка «история сжата: N сообщений → сводка». Если сводка
не удалась (сервер занят), история обрезается как по `/compact`, и об этом сказано.

В агентном режиме сжатия нет: сводка теряет точность истории вызовов, и модель потом
ссылается на файлы, которых в сводке нет. При заполнении выше порога ход не начинается,
а в ленте подсказка: `/compact`, `/clear` или `/context add 32k`. Ноль в `compact_at`
выключает автоматику.

## Журнал шагов

Рядом с журналом чата пишется журнал шагов — по строке JSON на каждый обмен с моделью,
каждый вызов инструмента и каждый поиск по книгам. Имя файла задаёт `steps_file_pattern`
(тот же шаблон strftime, по умолчанию `steps-%Y-%m-%d_%H-%M-%S.jsonl`; `"off"` — не писать).
У обмена с моделью записаны модель, токены и время; у вызова инструмента — имя, аргументы
(до 512 байт), исход (`ok`, `invalid`, `denied`, `rejected`, `cancelled`, `failed`) и время;
у поиска — время ступеней и число найденного. Идентификатор обмена тот же, что в журнале чата.

По сотне таких строк видно, какие инструменты выбирает модель и на чём спотыкается:
столбец `tool`, не совпадающий с вопросом, — беда имени и описания инструмента; столбец
`outcome=invalid` с одним и тем же полем — беда схемы аргументов. Служба `ollmcp` пишет
тот же журнал по своим вызовам (`src=ollmcp`).

```bash
jq -r 'select(.kind=="tool") | [.turn, .step, .tool, .outcome, .ms] | @tsv' \
  ~/.local/share/ollchat/logs/steps-2026-09-04_10-00-00.jsonl
```

## Идентификатор обмена

Каждая запись начинается идентификатором обмена: `k7f3-01` — четыре знака на запуск ollchat
плюс номер вопроса внутри него. Вопрос, вызовы инструментов, рассуждения и ответ на него
помечены одним значением, поэтому обмен виден целиком, даже если между вопросом и ответом
модель сходила десяток раз в инструменты:

```
[k7f3-00] 2026.08.20 10:30 ----- Система
[k7f3-01] 2026.08.20 10:46 ----- Вопрос
[k7f3-01] 2026.08.20 10:47 ----- Инструмент
[k7f3-01] 2026.08.20 10:49 (qwen3.8:latest) ----- Ответ
[k7f3-02] 2026.08.20 10:52 ----- Вопрос
```

Номер `00` означает «вне обмена»: начало сеанса, смена сервера или модели, приложение файла
к контексту. Записи, сделанные до появления идентификаторов, остаются как были — без скобок.

Достать обмен из файла целиком:

```bash
grep -A 200 '^\[k7f3-01\]' ~/.local/share/ollchat/logs/chat-2026-08-20_10-30-11.md
```

Где идентификатор виден, не выходя из программы:

- тусклой строкой под ответом в ленте — в том числе у старого ответа, если отлистать вверх;
- по команде `/id` — сеанс, число обменов, последний идентификатор, путь к журналу
  и готовая команда `grep`;
- в строке состояния внизу, если `show_turn_id = true` в разделе `[general]` (по умолчанию так).

Копирование ответа с вопросом (`Shift+F5`) отдаёт текст в формате журнала, поэтому
идентификатор попадает и в буфер обмена.

Имя файла задаёт `file_pattern` — шаблон в духе strftime:

| Директива | Что подставляет |
|---|---|
| `%Y` | год: `2026` |
| `%y` | год двумя знаками: `26` |
| `%m` | месяц: `08` |
| `%d` | день: `20` |
| `%H` | часы, 24-часовые: `14` |
| `%M` | минуты: `30` |
| `%S` | секунды: `05` |
| `%%` | знак процента |

От набора директив зависит, как часто заводится новый файл:

| Шаблон | Что получается |
|---|---|
| `chat-%Y-%m-%d_%H-%M-%S.md` (по умолчанию) | свой файл на каждый **запуск** ollchat: `chat-2026-08-20_14-30-05.md` |
| `chat-%Y-%m-%d.md` | один файл на **день**, с ротацией в полночь |
| `chat.md` | один общий файл |

Файл на запуск нужен потому, что на одной машине под одной учётной записью нередко работает
несколько экземпляров ollchat разом — в разных сеансах ssh или окнах tmux. В общий файл они
писали бы вперемешку. Если два экземпляра запущены в одну и ту же секунду, второй получает имя
с суффиксом: `chat-2026-08-20_14-30-05-2.md`. Имя фиксируется на старте, поэтому экземпляр,
проработавший через полночь, продолжает писать в свой файл.

Устаревшая настройка `pattern` — раскладка времени Go вида `chat-2006-01-02.md` — продолжает
работать, чтобы не ломать конфиги, созданные прежними версиями. Она действует, только когда
`file_pattern` не задан; если заданы обе, действует `file_pattern`, а ollchat показывает
подсказку при запуске. Текущий файл и действующий шаблон всегда видны по `/log`.

# Оформление ответов

Ответы модели рендерятся как markdown. Раздел `[theme]`:

| Настройка | По умолчанию | Что задаёт |
|---|---|---|
| `style` | `"auto"` | база оформления: `auto` (по цвету фона терминала), `dark`, `light`, `dracula`, `tokyo-night`, `pink`, `notty`, `ascii` |
| `code_theme` | `"gruvbox"` | подсветка синтаксиса в блоках кода — любая тема chroma: `monokai`, `nord`, `dracula`, `github-dark`, `solarized-dark`, `tokyonight-night`, `catppuccin-mocha`, `onedark`, `vulcan` и ещё полсотни. Пусто — цвета базового стиля |
| `code_bg` | пусто | заливка блока кода; пусто — фон терминала |
| `inline_code` | `"179"` | цвет кода в тексте (обратные кавычки) |
| `inline_code_bg` | пусто | заливка кода в тексте; пусто — без заливки |
| `italic` | `"auto"` | курсив в заметках, рассуждениях и выделении: `auto` (по терминалу), `on`, `off` |
| `[theme.tokens]` | `NameTag = "#83a598"` | цвета отдельных видов токенов поверх темы |

Цвета задаются номером ANSI 256 (`"179"`) или записью вида `"#d7af5f"`.

Почему умолчания именно такие. Встроенный тёмный стиль библиотеки glamour рисует код
в тексте цветом ANSI 203 на заливке 236 — это ровно тот красный, которым в ленте пишутся
ошибки, и код в предложении читается как ругань. Заливка же вырезает прямоугольник в фоне
терминала, если у него обои или включена прозрачность. Поэтому по умолчанию код песочный
и без заливки, а блоки кода подсвечиваются темой gruvbox, с которой снята её собственная
заливка.

### Курсив и терминалы, которые его не умеют

Заметки (`/help` и прочие) и рассуждения модели рисуются курсивом. Терминал, который курсива
не умеет, показывает вместо него **инверсию** — строки выглядят залитыми серым, будто у ленты
испортился фон. Классический случай: ollchat по ssh внутри tmux с `TERM=screen-256color`,
у которого в терминфо нет возможности `sitm` (курсив) — проверено: у `screen`
и `screen-256color` её нет, у `tmux-256color` и `xterm-256color` есть.

Поэтому при `italic = "auto"` ollchat сам не выводит курсив там, где терминал о нём не заявляет:
`screen*`, `linux`, `vt100`, `dumb`. Настройка `on` или `off` решает вопрос вручную.

Лечится это и со стороны tmux — тогда курсив вернётся настоящим, наклонным.
Рекомендуемые настройки — в разделе [«Работа в tmux»](#работа-в-tmux).

### Цвета отдельных токенов

Тема раскрашивает код целиком, но иногда мешает один цвет. Живой пример: gruvbox красит
токен `NameTag` в свой `#fb4934` — в этой теме цвет предназначался тегам HTML, а тем же
токеном лексер размечает **ключи YAML и JSON**, и файл GitLab CI в ответе выглядит так,
будто в нём всё сломано. Хуже того, в 256-цветной палитре этот красный попадает ровно
в ANSI 203 — тот самый цвет, которым ollchat пишет ошибки.

Поэтому по умолчанию ключи перекрашены в синий из той же палитры gruvbox:

```toml
[theme.tokens]
NameTag = "#83a598"
```

Перекрасить можно любой вид токена chroma. Ходовые имена:

| Имя | Что красит |
|---|---|
| `NameTag` | ключи YAML и JSON, теги XML и HTML |
| `Keyword` | ключевые слова языка |
| `KeywordType` | имена типов |
| `LiteralString` | строки |
| `LiteralNumber` | числа |
| `Comment` | комментарии |
| `NameFunction` | имена функций |
| `NameVariable` | переменные |
| `Operator` | операторы |
| `Punctuation` | скобки и знаки препинания |

Два правила, оба закреплены проверкой при запуске:

- **Только запись вида `#83a598`.** Номера ANSI здесь не работают: chroma читает значение
  как шестнадцатеричное число, и `"179"` молча превратилось бы в `#000179` — тёмно-синий.
- **Раздел действует только вместе с `code_theme`.** Без темы подсветку рисует сам glamour
  своим набором цветов, и точечные правки туда не ложатся.

Раздел, оставленный пустым, означает «цвета темы как есть» — так возвращается родной вид
темы, включая красные ключи. Начертание (жирность, курсив), заданное темой, при смене цвета
сохраняется.

Мелочь, которую стоит знать: блоки кода рисует форматтер chroma `terminal256`, поэтому
точный hex приводится к ближайшему цвету 256-цветной палитры. Это сделано ради терминалов,
которые не умеют truecolor, — по той же причине и остальная палитра ollchat задана номерами
ANSI.

Вернуть прежний вид можно, ничего не пересобирая:

```toml
[theme]
code_theme     = ""      # цвета базового стиля glamour
code_bg        = "#373737"
inline_code    = "203"
inline_code_bg = "236"

[theme.tokens]           # пустой раздел — без правок
```

Неизвестное имя темы — ошибка запуска со списком доступных, а не тихая подмена: сама
chroma на опечатку не ругается и молча берёт запасную тему.

# Работа в tmux

ollchat часто запускают по ssh внутри tmux — и там он выглядит хуже, чем на своей машине,
если tmux не настроен. Настройки ниже проверены в бою на машине, где ollchat пользуются
одиннадцать человек.

```bash
# ~/.tmux.conf

# Курсив. В терминфо screen (умолчание многих сборок tmux) нет возможности sitm,
# и tmux рисует курсив инверсией — заметки и справка выглядят залитыми серым.
set -g default-terminal "tmux-256color"

# Полный цвет наружу: темы подсветки кода заданы шестнадцатеричными цветами,
# иначе они квантуются в палитру 256. Перечислены терминалы, которые RGB
# точно умеют, — включать его всем подряд нельзя, у остальных цвета поедут.
set -as terminal-features ",xterm*:RGB,alacritty*:RGB,foot*:RGB,wezterm*:RGB,kitty*:RGB,ghostty*:RGB"

# Задержка распознавания Esc. Умолчание 500 мс делает Esc в TUI вялым,
# а в ollchat им прерывают ответ модели.
set -s escape-time 10
```

Что даёт каждая строка:

| Строка | Без неё | С ней |
|---|---|---|
| `default-terminal "tmux-256color"` | справка и рассуждения на серой заливке (курсив подменяется инверсией) | курсив рисуется курсивом |
| `terminal-features … RGB` | цвета подсветки кода округляются до палитры 256 | темы выглядят так, как задуманы |
| `escape-time 10` | `Esc` срабатывает с задержкой в полсекунды | ответ модели прерывается сразу |

**Проверить, что действует именно то, что нужно** — первые две команды выполняются
**внутри сеанса tmux**, без запущенного сервера они отвечают «no server running»:

```bash
tmux show -gv default-terminal          # ожидается tmux-256color
tmux show -sv escape-time               # ожидается 10
infocmp tmux-256color | grep -c sitm    # 1 — описание с курсивом на месте
infocmp screen-256color | grep -c sitm  # 0 — вот почему screen не годится
```

Если последняя команда отвечает `0`, в системе нет описания `tmux-256color` — в Debian
и Ubuntu оно лежит в пакете `ncurses-term`.

**Смотреть надо не на версию tmux, а на свой конфиг.** В Ubuntu 24.04 сборка tmux 3.4 уже
использует `tmux-256color` по умолчанию, но собственная строка `set -g default-terminal
"screen-256color"` в `~/.tmux.conf`, оставшаяся с давних времён, перебивает это — и серая
заливка возвращается.

**Уже запущенный tmux файл настроек не перечитывает.** Выдать настройки живому серверу
можно на ходу:

```bash
tmux set -g default-terminal "tmux-256color"
tmux set -s escape-time 10
```

Существующие панели при этом не меняются — `TERM` выдан им при создании. Новое окно или
панель получат правильный терминал сразу, перезапускать tmux целиком незачем.

Про мышь: `set -g mouse on` в tmux совместим с ollchat — события уходят приложению,
которое их запросило, а ollchat как раз запрашивает. Если мышь всё-таки понадобилась
терминалу (выделить и скопировать текст), `F2` в ollchat отдаёт её обратно.

# Файл настроек

Формат TOML, путь по умолчанию `~/.config/ollchat/config.toml`, создаётся `--init-config`.

| Раздел | Что настраивает |
|---|---|
| `[general]` | `default_server`, `mode`, `render_markdown`, `show_thinking`, `show_turn_id`, `startup_hints`, `token_speed`, `today`, `vram_profile` |
| `[theme]` | оформление ответов: `style`, `code_theme`, `code_bg`, `inline_code`, `inline_code_bg` |
| `[input]` | `mouse` — у кого мышь при запуске; `command_rows` — высота меню команд; `[input.cursor]` — `shape`, `blink`, `color` |
| `[log]` | журнал чата |
| `[agent]` | `enabled`, `tools`, `max_iterations`, `max_retries`, `bash_timeout`, `max_output_kb` |
| `[permissions]` | `allow`, `ask`, `deny` |
| `[sandbox]` | `root`, `allow_outside`, `follow_symlinks`, `max_file_kb`, `max_pdf_mb` |
| `[web]` | `searxng_url`, `timeout` — поиск в сети |
| `[kb]` | база знаний, см. таблицу выше; `embed_check` — как часто проверять модель эмбеддингов |
| `[graph]` | граф понятий: модель извлечения, темы, `neighbor_sense_weight`, `neighbor_pool`, `relation_snippet` |
| `[mix]` | подмешивание знаний к вопросу с привратником |
| `[confluence]` | чтение страниц корпоративной вики |
| `[viewers]` | чем открывать книгу по `Ctrl+O`: `pdf`, `epub`, `md`; пусто — системный просмотрщик |
| `[[servers]]` | по блоку на сервер: `url`, `model`, `timeout`, `stall_timeout`, `chat_timeout`, `keep_alive`, `system_prompt`, `think`, `headers`, `options`, `vram_gib` |

### Открыть саму книгу: `[viewers]`

В панели найденного (`Ctrl+F`) `Enter` читает кусок в ленте, а `Ctrl+O` открывает **саму
книгу** во внешней программе. По умолчанию — тем же, чем открывает файл проводник
(`xdg-open`), и настраивать для этого ничего не надо.

Настройка нужна там, где хочется попадать сразу на нужную страницу: системный просмотрщик
страницу не знает, а `zathura` и `okular` знают.

```toml
[viewers]
pdf  = "zathura -P {page} {file}"   # или "okular -p {page} {file}"
epub = "foliate {file}"
md   = "ghostwriter {file}"
```

`{file}` — путь к книге; без него путь дописывается в конец команды. `{page}` — страница
из выдачи. Довод со страницей выбрасывается целиком, когда страница неизвестна: у книги
EPUB единица ссылки не страница, а раздел, и `--page-index=` без значения сломал бы запуск.

Просмотрщик уходит в собственную группу процессов, поэтому `Ctrl+C` в ollchat его не
закроет, а его собственные предупреждения не лягут поверх ленты.

## Спросить модель из командной строки

Кроме диалога, ollchat умеет отвечать без интерфейса — это нужно для замеров: числа отбора
подбираются только прогоном, а прогон должен идти скриптом, а не руками.

```bash
ollchat --ask "как связаны RAG и дообучение"
ollchat --ask-stdin < вопрос.txt
ollchat --questions вопросы.txt --json > ответы.jsonl
```

**Ключи замера.** Все числа отбора задаются прямо в командной строке, поэтому один и тот же
вопрос можно прогнать при разных значениях подряд:

| ключ | что задаёт |
|---|---|
| `--graph-sense 1.5` | вес уместности связи против её подтверждённости книгами |
| `--graph-pool 8` | во сколько раз шире показанного брать пул для пересортировки |
| `--mix off\|graph\|books\|all` | что подмешивать к вопросу |
| `--mix-entities`, `--mix-neighbors` | размер карты понятий |
| `--kb-topk`, `--kb-max-per-book` | сколько фрагментов книг и сколько из одной |
| `--kb-min-cosine`, `--kb-semantic-weight` | порог смысла и его вес против слов |
| `--kb-use <коллекция>` | по какой коллекции искать |
| `--temperature`, `--seed`, `--num-ctx`, `--think on\|off` | параметры запроса |
| `--repeat N` | повторить вопрос N раз — виден разброс от сэмплирования |
| `--show-mix` | напечатать подмешанное вместе с ответом |
| `--json` | строка JSON на ответ: текст, счётчики, подмес и **чем считали** |

`--graph-sense` и `--graph-pool` действуют и на `--graph-find`, так что выдачу поиска можно
смотреть теми же ключами, что и ответы.

**Температура по умолчанию 0.** В диалоге она берётся из конфига, а здесь ставится в ноль:
сравнивать ответы при чужой температуре значит мерить сэмплирование, а не настройку.
Проверено на стенде: два одинаковых запроса с `--temperature 0 --seed 7` дают побайтово
одинаковый ответ, включая рассуждения.

**Инструменты по умолчанию выключены.** Агент без человека не может ответить на запрос
подтверждения, а `bash` и `write_file` в цикле замера — способ однажды снести чужую работу.
Включаются явным `--tools`, и тогда любое действие, требующее подтверждения, **отклоняется**:
спросить некого. Правила `deny` и песочница действуют как обычно.

Пример замера: один вопрос при двух значениях веса связи, по три прогона на каждое.

```bash
for w in 0 1.5; do
  ollchat --questions вопросы.txt --mix graph --graph-sense $w --repeat 3 --json
done > out.jsonl
```

## Общая библиотека организации

По умолчанию коллекции лежат файлами рядом с вами, и это главный сценарий: один бинарь,
ни служб, ни портов, ни бэкапов. Но там, где людей много, собирать индекс на каждом рабочем
месте расточительно — он строится часами на видеокарте, а держать его в общей папке нельзя:
поиск читает индекс целиком в память.

Тогда библиотека собирается **один раз** и раздаётся по сети. Для сотрудника при этом
**ничего не меняется**: те же команды, та же выдача со ссылками на книгу и страницу,
тот же граф понятий. Отличие только в том, что считает не его машина.

### Что ставится на сервер

**Тот же самый `ollchat`.** Отдельной серверной программы нет намеренно: администратор
уже держит этот бинарь — им он индексирует книги, считает смыслы и строит граф. Второй
файл означал бы вторую версию и вторую возможность их рассогласовать.

```
машина-сервер
├── ollchat                                  ← один статический бинарь
├── /srv/ollchat/kb/collections/books/       ← индекс, векторы, graph/
└── доступ к Ollama                          ← bge-m3 и модель извлечения
```

Ollama нужна серверу дважды: при **сборке** графа (извлекает понятия) и на **каждый вопрос**
(считает вектор запроса). Стоять она может где угодно — хоть на отдельной машине с картой.

### Настройка сервера

Обычный файл настроек ollchat, ничего особенного:

```toml
[general]
default_server = "gpu"

[kb]
dir         = "/srv/ollchat/kb"
default     = "books"
embed_model = "bge-m3"

[graph]
model = "qwen3.8:latest"

[[servers]]
name = "gpu"
url  = "http://ollama.example:11434"
```

Собрать знание (один раз, часы на видеокарте) и поднять службу:

```bash
ollchat --kb-add books /srv/книги      # проиндексировать
ollchat --kb-embed books               # посчитать смыслы
ollchat --graph-build books            # собрать граф понятий

OLLMCP_TOKEN=длинная-случайная-строка ollchat --serve 0.0.0.0:8377
```

**Ключ доступа задаётся только через окружение.** Не флагом — он виден в `ps` любому
пользователю машины; не в файле настроек — файл копируют и пересылают. Без ключа служба
поднимется, но скажет об этом при запуске: `ключ доступа НЕ ЗАДАН`.

### Служба systemd

Отдельный пользователь, ключ отдельным файлом, ограничения по возможностям:

```bash
sudo useradd --system --home-dir /srv/ollchat --shell /usr/sbin/nologin ollchat
sudo install -d -o ollchat -g ollchat /srv/ollchat/kb
sudo install -d -m 750 -o root -g ollchat /etc/ollchat

# ключ доступа — файлом, права 640, читает только служба
printf 'OLLMCP_TOKEN=%s\n' "$(openssl rand -hex 32)" | \
  sudo install -m 640 -o root -g ollchat /dev/stdin /etc/ollchat/service.env
```

`/etc/systemd/system/ollchat-kb.service`:

```ini
[Unit]
Description=ollchat — служба знаний
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=ollchat
Group=ollchat

# Ключ отдельным файлом, а не строкой Environment= в юните: файлы юнитов
# в /etc/systemd/system читаются всеми, и ключ в них виден любому на машине.
EnvironmentFile=/etc/ollchat/service.env

ExecStart=/usr/local/bin/ollchat -c /etc/ollchat/config.toml --serve 0.0.0.0:8377 --mcp
Restart=always
RestartSec=5s

# ВАЖНО: каталог библиотеки должен быть доступен на ЗАПИСЬ, хотя служба
# только читает. Журналы графа открываются в режиме добавления уже при
# открытии графа. Без этой строки служба поднимется и будет отвечать
# по книгам, а на первом вопросе к графу откажет с «permission denied».
ReadWritePaths=/srv/ollchat/kb

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ProtectKernelTunables=true
ProtectKernelModules=true
RestrictNamespaces=true
RestrictSUIDSGID=true
LockPersonality=true
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM

# Библиотека держится в памяти целиком: индекс, векторы и граф — около
# гигабайта на крупную коллекцию. Предел с запасом: ядро, снявшее службу
# посреди ответа, выглядит как «поиск иногда не работает».
MemoryMax=8G

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ollchat-kb
curl -s http://localhost:8377/health
```

Проверять надо **не только что поднялось, но и что раздаётся**:

```bash
curl -s -H "Authorization: Bearer $КЛЮЧ" -X POST http://localhost:8377/mcp \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | grep -o '"name":"[a-z_]*"'
```

Должны быть только чтение — `kb_search`, `kb_read`, пять `graph_*` и `web_search`.
Если там оказался `bash` или `write_file`, служба собрана неправильно и её надо
остановить немедленно.

### Настройка клиента

Три строки, и никакой библиотеки на диске:

```toml
[kb]
server_url        = "http://kb.corp.local:8377"
server_token_file = "~/.config/ollchat/kb-token"   # права 600
```

Всё. Ни каталога с книгами, ни адреса Ollama для эмбеддингов, ни имени модели —
это забота сервера. Ключ в файле настроек не хранится; способов три, как у токена
Confluence: `server_token_file`, `server_token_env`, `server_token_cmd`.

### Что при этом работает

| | |
|---|---|
| словесный поиск (BM25) | да |
| смысловой поиск (векторы) | да |
| слияние того и другого | да, теми же подобранными числами |
| ссылки на книгу, страницу, год | да |
| `kb_read` — фрагмент целиком с соседями | да |
| граф понятий: `graph_search`, `graph_entity`, `graph_path`, `graph_overview`, `graph_topic` | да |
| карта понятий в подмешивании к вопросу | да |

Инструменты графа выполняются на сервере и возвращают клиенту **тот же текст**, который
модель увидела бы локально: реализация одна, второй нет. Разбор доводов, описания для модели
и подтверждения действий при этом остаются на машине сотрудника — отклонить неверный довод
надо сразу, а спрашивать человека можно только у него самого.

### Что остаётся у администратора

**Пишет только он и только локально.** Индексация, счёт смыслов, сборка графа, уплотнение —
действия над файлами. Служба поднимается лишь из инструментов чтения, и другого набора
у неё нет: клиент не то что не должен, а физически не может испортить общий индекс.

**Устаревание замечается само.** Каждый ответ службы несёт признак поколения индекса;
долил администратор книги — признак сменился, и клиент перечитывает состав. Без этого
служба неделями отдавала бы вчерашние цифры, ничего об этом не говоря.

### Оговорки, которые стоит знать заранее

**Первый вопрос к графу после запуска службы долгий.** Граф читается в память целиком —
на большой библиотеке это секунды и около гигабайта. Дальше он остаётся открытым, и
следующие вопросы отвечаются сразу. На занятой машине первое открытие может занять минуты.

**Служба держит библиотеку в памяти.** Индекс, векторы и граф — считайте по гигабайту
на крупную коллекцию.

### Если нужен ещё и протокол MCP

Сторонние клиенты (Claude Code и подобные) говорят по протоколу MCP. Он поднимается
на **том же порту** — двух служб с двумя ключами ради этого заводить не надо:

```bash
OLLMCP_TOKEN=ключ ollchat --serve 0.0.0.0:8377 --mcp
```

Клиенты ollchat ходят в `/api/v1`, клиенты MCP — в `/mcp`.

**По MCP раздаётся только чтение**, и набор задан перечислением, а не вычитанием опасных
из всех: `kb_search`, `kb_read`, пять инструментов графа и `web_search`. Ни `bash`, ни записи
файлов там нет и появиться не может — служба работает без человека, подтвердить опасное
действие некому, а ключ есть у всех сотрудников. Новый инструмент по умолчанию в службу
**не** попадает.

**Отдельная программа `ollmcp` нужна ровно для одного** — режима stdio, когда клиент MCP
запускает службу сам и говорит с ней через стандартные потоки. Так она подключается,
например, к Claude Code:

```json
"ollchat-kb": {"type": "stdio", "command": "/usr/local/bin/ollmcp"}
```

Внутри у неё тот же самый код. По сети (`ollmcp --http`) она раздаёт оба протокола так же,
как `ollchat --serve --mcp`, — выбирайте что удобнее.

## Подбор чисел отбора на ходу

Числа, которыми отбирается материал для ответа, подбираются только замером — угадать их нельзя.
Чтобы не править конфиг и не перезапускать программу ради одной пробы, они меняются командами
**на сеанс**:

```
/graph tune                    показать нынешние значения и то, что в конфиге
/graph tune sense 1.5          вес уместности связи против её подтверждённости
/graph tune pool 8             во сколько раз шире показанного брать пул
/graph tune reset              вернуть значения из конфига

/kb tune top_k 12              сколько фрагментов возвращать
/kb tune max_per_book 3        не больше стольких из одной книги
/kb tune min_cosine 0.35       порог смысловой близости
/kb tune semantic_weight 1.5   вес смысла против совпадения слов
/kb tune reset                 вернуть значения из конфига
```

Значения действуют сразу на все три дороги: поиск командой, инструменты модели и подмешивание
к вопросу. В конфиг ничего не пишется — понравилось, перенесите руками.

**Смотреть надо на материал, а не на ответ модели.** Ответ меняется и сам по себе, от температуры:
два запуска с одинаковыми настройками дадут разный текст, и разница отбора в нём утонет. Поэтому
есть команда, которая печатает то, что реально ушло бы модели, **не обращаясь к ней**:

```
/mix show как связаны RAG и дообучение
```

Она показывает карту понятий и выдержки целиком, а под ними — нынешние числа отбора. Покрутили,
посмотрели, сравнили. Ответы модели сравнивать имеет смысл только при температуре 0.

И оговорка, купленная замером: значение, выбранное на трёх вопросах, в конфиг попадать не должно.
Прогон на тридцати вопросах у нас однажды дал ответ, обратный прогону на ста.

**Команды скрываются вместе с ненастроенными возможностями.** Нет раздела `[kb]` в файле
настроек — в меню по `/` и в справке не будет ни `/kb`, ни рассказа о базе знаний; нет
`[graph]` — не будет `/graph`; нет `[confluence]` — не будет `/confluencetoken`. Считается
именно **наличие раздела в файле**, а не значения настроек: умолчания подставляются всем,
и по ним «не настраивал» от «настроил так же» не отличить. Если файла настроек нет вовсе
(первый запуск), показывается всё — прятать от нового пользователя половину команд незачем.

**`general.startup_hints`** — показывать ли советы при запуске: о выключенных инструментах
(«они есть в сборке, но не перечислены в `agent.tools`»), об устаревших настройках конфига
и подобные. По умолчанию `"on"`. Они помогают, пока конфиг отстаёт от программы, и мешают там,
где он сокращён намеренно: на машине без книг и графа совет дописать `kb_search` бесполезен,
а читается он при каждом запуске. Ошибок и предупреждений по ходу работы настройка не касается.
Опечатка в значении — ошибка запуска, а не тихое включение обратно.

**`servers.stall_timeout`** — сколько поток ответа может молчать, прежде чем обмен считается
оборванным. Отдельно от `chat_timeout`, который ограничивает всё ожидание целиком.

Курсор в поле ввода рисует сам терминал: форма (`block`, `underline`, `bar`), мигание и цвет
задаются в `[input.cursor]`. Символ под курсором остаётся виден. Недопустимая форма или цвет —
ошибка запуска с именем настройки, а не тихая замена на значение по умолчанию.

**Параметры модели** задаются в `[servers.options]` — эта таблица уходит серверу как есть,
поэтому там работает любой параметр Ollama: `temperature`, `top_p`, `top_k`, `min_p`,
`repeat_penalty`, `num_predict`, `seed`, `stop` и параметры загрузки вроде `num_ctx`,
`num_batch`, `num_gpu`. Все они перечислены с описаниями в шаблоне конфига, а разбор каждого
с замерами на четырёх моделях — в документации проекта, «Параметры моделей».

Две ловушки оттуда стоит знать сразу: неизвестное имя параметра сервер **молча игнорирует**
(опечатка ничем себя не проявит, ищется только в его журнале), а неверный тип даёт ошибку
на каждом запросе — дробным параметрам нужна точка, `temperature = 1.0`, а не `1`.

# Что делать, если что-то не так

**Модель не видит инструментов.** `/tools` покажет включённые и выключенные. Конфиг, созданный
прежней версией, новые инструменты не подхватывает — их надо дописать в `agent.tools` руками.
Там же видно, поддерживает ли выбранная модель вызов инструментов вообще.

**Справка и заметки выводятся на сером фоне.** Это не заливка, а курсив, который терминал
не умеет и подменяет инверсией. Бывает в tmux с `TERM=screen-256color`. ollchat снимает курсив
сам (`theme.italic = "auto"`), а чтобы вернуть его настоящим — настройте tmux, см. раздел
[«Работа в tmux»](#работа-в-tmux). Принудительно: `italic = "off"` или `"on"` в `[theme]`.

**Сборка ругается на версии зависимостей.** Не выставлен `PATH` на Go 1.26.5.

**`/kb add` отказывает на любом каталоге.** В `kb.roots` пусто или каталог вне списка.

**Смыслы считаются втрое медленнее, чем должны.** Ollama размещает модель по свободному месту
**в момент загрузки** и обратно не переселяет. Достаточно один раз запустить рядом большую модель,
чтобы эмбеддинги навсегда остались считаться в оперативной памяти. Приложение предупреждает
об этом перед долгой работой; проверить и вылечить самому:

```bash
curl -s http://СЕРВЕР:11434/api/ps                          # смотреть size_vram, а не size
curl -s -X POST http://СЕРВЕР:11434/api/embed \
  -d '{"model":"bge-m3","input":["x"],"keep_alive":0}'      # выгрузить, чтобы встала заново
```

**Векторизация оборвалась с `400 Bad Request … EOF`.** Это упал внутренний обработчик модели
у Ollama, а не ошибка запроса. Приложение такие сбои повторяет само, а при нехватке видеопамяти
ещё и уменьшает пачку на ходу. Посчитанное не теряется — запустите ту же команду снова.

**Ответ оборвался ошибкой разбора XML.** Дефект на стороне Ollama при разборе вызовов инструментов
у некоторых моделей. Обмен повторяется автоматически (`agent.max_retries`), потому что до ошибки
не приходит ни куска ответа и не выполняется ни одного инструмента.

**После переключения модели всё падает с «Multimodal data provided».** Было до версии
с вычисткой картинок из истории; сейчас приложение убирает их из запроса само и сообщает об этом.

**Диалог обрывается по таймауту на длинных контекстах.** Ollama не шлёт ни байта ответа
`/api/chat`, пока не обработает весь промпт — на большом или только что расширенном окне контекста
это может честно занять много минут при живом и работающем сервере. За это отвечает отдельная
настройка `chat_timeout` в `[[servers]]` (по умолчанию 30 минут, не путать с коротким `timeout`
для списка моделей и версии сервера) — если её не хватает на вашем стенде, увеличьте. Разбор
причины и журнал стенда — в документации проекта, «Разбор обрыва по таймауту».
