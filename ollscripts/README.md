# ollscripts — обслуживание Ollama и раскладка клиента

Здесь лежат скрипты, которыми пользуются снаружи: установка и обновление Ollama,
поисковик для `web_search`, замер параллельности сервера и сверка доктора графа.

## ollmanageubuntu.sh

Установка, обновление и удаление Ollama на Ubuntu. Запускается через `sudo`
на самом сервере.

```bash
sudo ./ollmanageubuntu.sh                    # поставить, а если стоит — обновить
sudo ./ollmanageubuntu.sh -del               # удалить, сохранив конфиги и модели
sudo ./ollmanageubuntu.sh -restore КАТАЛОГ   # вернуть конфиги из копии
./ollmanageubuntu.sh -h                      # справка
```

Ключ `-y` отключает вопросы — нужен при запуске по ssh без терминала.

Рабочая копия лежит на стенде в `~/bin/ollmanageubuntu.sh` учётки обслуживания
(её имя — в приватных заметках, в репозитории учёток нет).
Исходник здесь; при доработке заменяйте копию на сервере целиком и сверяйте
`sha256sum`.

### Что скрипт делает

* **Без ключей.** Нет Ollama — ставит последнюю выпущенную версию. Есть —
  сверяет с последней и обновляет, если есть что обновлять. Повторный запуск
  на свежей версии ничего не делает и так и говорит.
* **Драйверы.** Перед установкой проверяет NVIDIA: если карта есть, а рабочего
  драйвера нет, ставит рекомендованный через `ubuntu-drivers install` и
  предупреждает, что нужна перезагрузка.
* **Служба.** Ставит Ollama службой systemd с автозапуском, после установки
  печатает, где лежат настройки и как службой управлять.
* **Удаление.** Пакетную установку сносит через `apt purge`, ручную — файлами.
  Перед этим снимает резервную копию настроек.

### Три вещи, которые скрипт бережёт

1. **Каталог моделей не трогает никогда.** На стенде это 127 ГиБ; выкачивать
   заново — часы. Удаление сносит программу, но не данные.
2. **Системного пользователя `ollama` не удаляет.** Каталог моделей принадлежит
   ему по uid; удалить пользователя — осиротить 127 ГиБ по правам доступа.
   При установке скрипт наоборот проверяет владельца и выправляет его.
3. **Настройки сохраняет и возвращает.** Перед удалением копирует unit-файл,
   `override.conf`, `/etc/default/ollama` и манифест (версия, пути, переменные,
   список моделей) в `~/ollobackups/ГГГГ-ММ-ДД_ЧЧ_ММ` того пользователя, который
   запустил `sudo` — не root. При следующей установке предлагает вернуть
   переопределения оттуда: без них потеряется `OLLAMA_HOST`, и сервер станет
   слушать только себя.
4. **Чужие настройки не перезаписывает.** Если `override.conf` уже есть — свой
   или восстановленный из копии, — скрипт его не трогает. Свои значения он
   кладёт только когда файла нет вовсе.

### Что попадает в `override.conf` при чистой установке

```ini
[Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="OLLAMA_CONTEXT_LENGTH=32768"
```

`OLLAMA_HOST` — иначе Ollama слушает только `127.0.0.1`, и по сети к ней
не подключиться.

`OLLAMA_CONTEXT_LENGTH` — окно контекста для запросов, которые его не задали.
Умолчание Ollama (ноль) означает «выбрать по видеопамяти», и на большой карте
сервер берёт максимум модели — 256k у нынешних. Крупная модель с таким окном
перестаёт помещаться в видеопамять: замерено, что у `qwen3.5:122b` на карте
оказывались 49 слоёв из 50, а скорость падала с 82 токенов в секунду до долей
токена. Разбор параметров и замеры — в документации проекта.

Имя переменной именно `OLLAMA_CONTEXT_LENGTH`. Похожей на вид `OLLAMA_NUM_CTX`
не существует, а незнакомые переменные Ollama принимает молча — такая опечатка
три месяца стояла в настройках стенда и ничего не делала. Проверять надо не
файл, а то, что сервер сам сообщает о себе при запуске:

```bash
journalctl -u ollama | grep "server config" | tail -1
```

### Чего скрипт не умеет

* Ветка удаления через `apt` написана, но **не проверена**: официального
  пакета Ollama в репозиториях нет, а на стенде установка ручная.
* Установка драйверов не проверена: на стенде драйвер 595.84 уже стоял,
  и скрипт правильно это увидел и ничего не делал.

## ollparallelcheck.sh — считает ли сервер запросы параллельно

Клиент может слать сколько угодно запросов разом, но сколько из них обрабатываются
одновременно, решает сервер. Со стороны клиента разницы не видно: запросы уходят
и возвращаются, просто медленно. Скрипт отвечает на этот вопрос замером.

```bash
./ollparallelcheck.sh -m qwen3.8:latest -u http://ollama.example:11434
./ollparallelcheck.sh -m glm-4.7-flash:q8_0 -n 8
```

| Ключ | Что задаёт |
|---|---|
| `-m` | модель, обязательно |
| `-u` | адрес сервера; по умолчанию `$OLLAMA_URL` или `http://localhost:11434` |
| `-n` | сколько запросов слать разом, по умолчанию 4 |
| `-p` | длина ответа в токенах, по умолчанию 120 |

Код возврата: `0` параллельность работает, `1` очередь, `2` проверить не удалось
(нет модели, сервер не отвечает, не задан `-m`).

### Как он судит

Меряются два числа, и второе надёжнее первого.

**Ускорение** — во сколько раз выше пропускная способность против одиночного запроса.
**Разброс времён** — отношение самого долгого запроса к самому быстрому. В очереди
запросы возвращаются лесенкой: первый за время одиночного, последний за N таких,
поэтому разброс стремится к N. При настоящей параллельности все заканчиваются почти
вместе, и разброс около единицы.

Замеры на стенде 26.08.2026 (A100, Ollama 0.32.13, `OLLAMA_NUM_PARALLEL=4`):

| Модель | Ускорение | Разброс | Вывод |
|---|---|---|---|
| `qwen3.8:latest` | 0.96–1.47x | 3.1–3.2 | очередь |
| `glm-4.7-flash:q8_0` | 2.49–2.67x | 1.10 | параллельно |

Вердикт ставится по обоим числам: ускорение от 1.8 **и** разброс не выше 2.5. По одному
ускорению он уже ошибался — на очереди однажды вышло 1.47 при пороге 1.5.

### Две причины, по которым запросы идут в очередь

**Не задана `OLLAMA_NUM_PARALLEL`** — сервер держит один слот. Лечится юнитом службы
и перезапуском; каждый слот стоит памяти под свой контекст.

**Архитектура модели не поддерживается.** Тогда Ollama сводит число слотов к единице
независимо от настройки и пишет об этом в журнал на каждый запрос:
`model architecture does not currently support parallel requests`. Настройка сервера
тут ни при чём, и никакие потоки на стороне клиента не помогут.

Скрипт различает эти случаи сам, но только когда работает **на той же машине**, что
и сервер. Локальность он определяет не по имени хоста, а сверяя порт службы с портом
запроса: `localhost:11111` сплошь и рядом оказывается туннелем ssh на другую машину,
и журнал местной службы рассказывал бы про совсем другой сервер. Если сервер удалённый,
скрипт печатает две команды, которые надо выполнить на нём.

## searxngmanage.sh — поисковик для web_search

Ставит SearXNG контейнером и заводит службу systemd. Нужен инструменту `web_search`: публичные
поисковики запросы от программ отклоняют (DuckDuckGo отдаёт заглушку со второго запроса, публичные
экземпляры SearXNG — 403 и 429), поэтому нужен свой.

```bash
sudo ./searxngmanage.sh              поставить, а если стоит — обновить образ
sudo ./searxngmanage.sh -del         удалить, сохранив настройки
sudo ./searxngmanage.sh -restore КАТАЛОГ
sudo ./searxngmanage.sh -p 8080      другой порт (по умолчанию 8888)
```

Что делает установка:

1. кладёт `settings.yml` в `/opt/searxng` — главное там `search.formats: [html, json]`,
   без этой строки наружу идёт только HTML и `web_search` получит вёрстку вместо данных;
2. заводит `docker-compose.yml` и службу `searxng`;
3. загружает образ, запускает, **проверяет, что JSON действительно отдаётся**;
4. печатает готовую строку для конфига ollchat.

Ставится туда, где запущен: на сервер — через `scp` и `ssh`, локально — прямо из каталога проекта
(нужен `sudo apt install docker.io docker-compose-v2`, если Docker ещё не стоит).

**Про `secret_key`.** Скрипт создаёт его при первой установке и при обновлении берёт из прежних
настроек, а не создаёт заново. SearXNG подписывает им cookie с настройками пользователя, ссылки
на картинки и значки сайтов через встроенный прокси (HMAC-SHA256) и использует как пароль к кэшу.
Для работы ollchat это почти безразлично — мы ходим в JSON API без cookie, прокси картинок
выключен, — но у тех, кто открывал поисковик браузером, смена ключа сбрасывает настройки
и ломает ранее выданные ссылки на картинки.

Правила те же, что у `ollmanageubuntu.sh`: настройки не теряются. Перед изменением они копируются
в `~/searxngbackups/ГГГГММДД-ЧЧММСС` того, кто запустил `sudo`, а секретный ключ подписи при
обновлении берётся из прежних настроек — иначе разойдутся уже выданные ссылки.

Проверить вручную:

```bash
curl -s 'http://СЕРВЕР:8888/search?q=golang&format=json' | head -c 200
```

## graphdoctorcheck.py — сверка доктора графа

Считает те же числа, что `ollchat --graph-doctor`, но независимым путём: читает
сырые файлы графа сам, не трогая кода программы. Нужен затем, что доктор — суждение
о состоянии, и верить ему на слово не надо.

```bash
ollscripts/graphdoctorcheck.py           # коллекция books
ollscripts/graphdoctorcheck.py мойкорпус
```

Сверка 02.09.2026 сошлась по всем одиннадцати числам. Подробности и оговорки —
в README проекта, раздел «Сверка доктора».
